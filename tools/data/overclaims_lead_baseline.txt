Chapters/19_Techniques--Concurrency.md	[LEAD] Three issues separate a process pool from the in-process tools in this chapter, and all three appear in CODE: -> The CODE guard keeps each worker from building a pool of its own. To create a worker, the operating system starts a fresh Python interpreter, and that interpreter imports this module, the program's main module, before it runs any work. During the import the module's name is not CODE, so the worker skips the guarded block. If you leave out the guard, each worker re-runs the block, tries to build a pool of its own, and dies with CODE. The parent sees the worker's death as CODE, with the worker's own CODE traceback printed above it by the failing child process. Before 3.14 the guard was a Windows and macOS concern only, because Linux forked the parent process instead of importing anything. Since 3.14 no platform forks the parent by default. Linux now uses CODE, which forks each worker from a server process that has imported this module. macOS and Windows use CODE, which starts each worker fresh. Every platform therefore requires the guard.
Chapters/21_Patterns--Design_Patterns.md	[LEAD] *GoF Design Patterns* discusses 23 patterns and sorts them under three purposes, each named for what its patterns do: -> **Creational**: how to create an object. When you isolate the details of object creation, your code stops depending on which object types exist. Adding a type then leaves that code unchanged. *Singleton* counts as a Creational pattern. Factory covers the other four: *Factory Method*, *Abstract Factory*, *Prototype*, and *Builder*.
