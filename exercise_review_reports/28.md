## Findings

### 1. Exercise 2's solution doesn't make handlers report *why* they failed, and its one canned message is factually wrong for bisection

- **Severity:** wrong
- **Where:** `Chapters/28_Patterns--Function_Objects.md:621-622`
  (exercise 2) and `Solutions/28_Patterns--Function_Objects.md:128-139,
  149-155` (solution + rationale)
- **Exercise says:** "Rewrite `chain.py` so each handler also reports
  why it failed, and the solver prints every attempt before returning
  the winner."
- **What actually happens:** The solution's `solve()` prints a single
  fixed string, `f"{finder.__name__} failed: could not converge"`, for
  *every* handler's failure, regardless of the actual reason, and its
  own prose says this was a deliberate choice not to have handlers
  report a separate explanation: "so `solve()` prints that outcome as
  it checks each return value, rather than asking each handler for a
  separate explanation" (Solutions:149-152). That message is also
  factually wrong for the case the listing itself demonstrates: I
  traced `bisection(f, 1.0, 1.3)` — `f(1.0) = -1.0`, `f(1.3) =
  -0.30999999999999983`, product `= 0.30999999999999983 > 0` — so
  `bisection()` returns `None` on its very first line,
  `if f(a) * f(b) > 0: return None`, never entering the iteration loop
  at all. It did not fail "to converge"; it failed a precondition
  check before attempting anything. Confirmed by running:
  `uv run python -c "def f(x): return x*x-2; print(f(1.0)*f(1.3))"` →
  `0.30999999999999983` (positive, so the bracket check trips
  immediately).
- **Solution does:** Leaves `bisection`, `secant`, and `newton`
  themselves unchanged and has `solve()` alone print a uniform,
  reason-free message on any `None` return. The exercise's premise —
  that each *handler* reports why — is not implemented; the solution
  substitutes a differently-scoped answer (solve() narrates outcomes)
  and says so explicitly, but the substitute message is also wrong in
  the one case the listing prints.
- **Suggested fix:** Either reword the exercise to ask only for
  per-attempt narration by the solver (dropping "each handler also
  reports why", since that's not what gets built), or have the
  solution's handlers actually distinguish their failure modes (e.g.
  bisection returns/signals "interval does not bracket a root" instead
  of a bare `None`, distinct from secant's "flat step" or an
  iteration-limit case) so `solve()` can print a real reason. At
  minimum, if the current design is kept, the printed message should
  not claim "could not converge" for a handler that never iterated.

## Notes

None of the other five exercises produced a reproducible defect.
Exercise 1 ("Add an undo capability to `command.py`") makes the
solution invent new domain commands (`Deposit`/account balance)
rather than adding `undo()` to the chapter's own `loony`/`new_brain`/
`afford` print-commands; I considered flagging this, but undoing a
`print()` call is not a coherent operation, the chapter's own prose
sets up exactly this tension ("A callable alone cannot express a
second operation, `undo()`..."), and the exercise's own second
question ("What do the commands need to become...?") invites exactly
this kind of redesign. This reads as a legitimate design choice, not a
defect, so I left it out of Findings.

Exercise 4's "Confirm both drop into `chain.py`'s `solve()` with no
change to `solve()`" is not literally demonstrated against the real
`chain.py` — the solution copies `solve()` locally, per this book's
established house style for self-contained solution listings (stated
explicitly in exercise 2's own solution prose: "The listing copies
them from `algorithms.py` rather than importing them, because each
solution runs on its own"). I independently re-ran the exercise against
the actual, unmodified `chain.py`/`algorithms.py` and confirmed the
claim holds: both the closure and the `functools.partial` strategy
produce `1.500000` through the real `solve()` with zero edits to it.
