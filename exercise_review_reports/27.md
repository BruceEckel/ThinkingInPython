### 1. Solution to exercise 3 omits the entire `games2.py` half of the exercise

- **Severity:** drift (exercise asks two things, solution answers one)
- **Where:** `Chapters/27_Patterns--Factory.md:902-905` (and `Solutions/27_Patterns--Factory.md`,
  "## 3. `GnomesAndFairies`" section)
- **Exercise says:** "Add a new type of `GameElementFactory` called `GnomesAndFairies`, first to
  `games.py` and then to `games2.py`. In `games2.py`, leave out `make_obstacle()` at first and
  confirm the error your type checker reports. Then add it."
- **What actually happens:** The solution's `exercise_3.py` implements only the `games.py`-style
  (ABC/`raise NotImplementedError`) version. `grep -n "games2\|Protocol\|BrokenFactory\|ty:"
  Solutions/27_Patterns--Factory.md` finds no `games2`-based `GnomesAndFairies`, no `Protocol`-based
  `GameElementFactory`, and no `ty` error transcript anywhere in the chapter's solution section. The
  second half of the exercise (the `games2.py` Protocol version, and the "leave out
  `make_obstacle()`, confirm the type-checker error, then add it" step) is never performed. I did
  perform it myself: adding `GnomesAndFairies` to a copy of `games2.py` without `make_obstacle()`
  and running `uv run ty check games2.py` reports
  `protocol member make_obstacle is not defined on type GnomesAndFairies`, exactly the shape of
  error the exercise expects; adding `make_obstacle()` back then makes `ty check` and the script
  both pass clean. So the exercise is fully doable — the solution just doesn't do half of it.
- **Solution does:** One combined-looking listing that only matches `games.py`'s structure (and
  even that isn't a literal edit of `games.py`: `GameEnvironment` there stores `self.p`/`self.ob`
  instead of `games.py`'s `self.character`/`self.obstacle`).
- **Suggested fix:** Add a second code block (or extend `exercise_3.py`) covering `games2.py`:
  define `GnomesAndFairies` there with only `make_character()`, show the `ty check` failure
  (`protocol member make_obstacle is not defined on type GnomesAndFairies`), then add
  `make_obstacle()` and show it passing.

### 2. Solution to exercise 6 silently renames `registry.py` to `shape_registry.py`

- **Severity:** drift
- **Where:** `Chapters/27_Patterns--Factory.md:913-916` (and `Solutions/27_Patterns--Factory.md:326`,
  "## 6. A registry whose classes live somewhere else")
- **Exercise says:** "Move `Circle` and `Square` out of `registry.py` into a new module,
  `extra_shapes.py`. Confirm that `make("Circle")` now raises `KeyError` until something imports
  `extra_shapes`, and explain which line of which file registers the class, and when it runs."
  (`registry.py` is the chapter's own listing at `Chapters/27_Patterns--Factory.md:182`.)
- **What actually happens:** The solution never shows an edited `registry.py`. Instead it
  introduces a new, differently named module, `shape_registry.py`
  (`Solutions/27_Patterns--Factory.md:326`), and every subsequent reference in the solution's prose
  and driver code uses that new name (`Solutions/27_Patterns--Factory.md:347,360,362,365,372,374,383`).
  I reproduced the exercise literally, keeping the module named `registry.py` (only moving `Circle`
  and `Square` out into `extra_shapes.py`), and it works exactly as the exercise and the solution's
  prose describe: `Shape.registry` starts `{}`, `make("Circle")` raises `KeyError: 'Circle'`, then
  after `import extra_shapes`, `sorted(Shape.registry)` is `['Circle', 'Square']` and
  `make("Circle").draw()` prints `Circle.draw`. So the rename isn't required by the mechanics; the
  solution just uses a different filename than the one the exercise names three times. (One
  possible motivation: the chapter's own `test_registry.py` at
  `Chapters/27_Patterns--Factory.md:266` does `from registry import Circle, Shape, Square, make`,
  which would break if `registry.py` really lost `Circle`/`Square` — but the solution never mentions
  this, and solutions live in a separate generated tree from chapter listings, so reusing the name
  `registry.py` there does not collide with the chapter's own file.)
- **Solution does:** Builds `shape_registry.py` + `extra_shapes.py` + `exercise_6.py`, all internally
  consistent and correct, just under a name the exercise never mentions.
- **Suggested fix:** Either rename the solution's module back to `registry.py` (matching the
  exercise's wording), or add a sentence explaining the rename (e.g., noting the collision with the
  chapter's `test_registry.py`) so a reader isn't left looking for an edited `registry.py` that
  never appears.
