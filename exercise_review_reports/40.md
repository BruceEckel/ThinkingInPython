## Findings

### 1. Exercise 7's second instruction has no referent after its first instruction is followed

- **Severity:** minor
- **Where:** `Chapters/40_Functional--Foundations.md:669-673`
- **Exercise says:** "In `higher_order.py`, replace the `map()` and
  `filter()` calls with comprehensions, and the `sorted(key=len)` call with
  one that sorts by last letter. Then delete the `list()` around the `map()`
  call, print the result, and say what you see and why."
- **What actually happens:** Performing the first sentence literally
  removes every `map()` call from the file (`squares = list(map(lambda n: n
  * n, numbers))` becomes `squares = [n * n for n in numbers]`). After that
  edit the file contains zero `map(` calls (`grep -c "map(" ex7_full_step1.py`
  → `0`), so "the `list()` around the `map()` call" the second sentence
  names no longer exists to be deleted. A reader following the two
  sentences in order, on the same file, hits a dead end at the second one.
  The exercise is still completable — go back to the pre-comprehension code
  for that one demonstration — but that is not what either sentence says to
  do, and nothing in the chapter or exercise flags it as a separate,
  parallel mini-experiment rather than a continuation of the same edit.
- **Solution does:** `Solutions/40_Functional--Foundations.md:213-224`
  resolves the ambiguity by silently starting over from the *original*
  `numbers`/`map()` code (`raw = map(lambda n: n * n, numbers)`), not from
  the comprehension it just built two paragraphs above, and further shows
  that a second `list(raw)` call returns `[]` — a demonstration the exercise
  text never asked for (it only asks to print the result and explain it
  once).
- **Suggested fix:** Reword the second sentence to make explicit that it
  works from the original `map()`/`filter()` code, not the comprehension
  version just built, e.g. "Separately, in the original `map()` line, delete
  the `list()` around it, print the result, and say what you see and why."

## Notes

- Exercise 6 ("change the annotation so appending *is* rejected") is
  answerable only by following the chapter's own prescription two paragraphs
  above the exercise (`Final[tuple[int, ...]]` with a tuple value, chapter
  lines 188-194 and confirmed with `ty` in scratch: `tuple[int, ...]`
  correctly rejects `.append()`). A reader who instead reaches for
  `Final[Sequence[int]] = [1, 2]` — the pattern the chapter *just* used for
  `total()`'s parameter two pages earlier, and the more obvious-looking fix —
  will find `ty 0.0.75` reports **no error** on `CONFIG.append(3)` in that
  case: confirmed with `uv run ty check` on a scratch file, `CONFIG:
  Final[Sequence[int]] = [1, 2]; CONFIG.append(3)` passes clean, while the
  same annotation on a *function parameter* (`def f(values: Sequence[int]):
  values.append(4)`) is correctly rejected. `ty` narrows a directly
  assigned module-level `Sequence[int]`-annotated name to the literal's own
  type (`list[int]`), but does not narrow a parameter the same way. This is
  not a book error — the exercise's intended path (tuple) works exactly as
  claimed and the solution uses it — but it is a plausible wrong turn a
  careful reader could take and get silently no error where they expect
  one. Flagging in case a future edit wants a guardrail sentence.

  found. All eight solutions answer their own exercise number, no more and
