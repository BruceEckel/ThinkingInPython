## Findings

### 1. Exercise 5 asks for the first design; the solution uses the second

- **Severity:** drift
- **Where:** `Chapters/31_Patterns--State_Machines.md:890-892`
  (`Solutions/31_Patterns--State_Machines.md:271-329`)
- **Exercise says:** "Modify the 'mood' exercise (exercise 1) so that it
  becomes a state machine using `state_machine.py`, the first design,
  where each state decides the next one."
- **What actually happens:** The exercise names `state_machine.py`
  explicitly, i.e. the each-state-decides design built from `state.py` +
  `state_machine.py` (`State.next()` returning the next `State`). I
  built exactly that cold — three `State` subclasses (`Happy`, `Grumpy`,
  `Prozac`) each with `run()`/`next()`, driven by
  `UnpredictablePerson(StateMachine)` — and ran it:
  `uv run python exercise_5_cold.py` produced
  `Great to see you! / annoy / What do you want? / pill / Everything is
  wonderful. Just wonderful.`, i.e. the exercise is entirely doable as
  literally stated.
  `Solutions/31_Patterns--State_Machines.md`'s own section 5, however, is
  titled "The mood machine, rebuilt on `table_machine.py`" and its code
  opens with `from table_machine import StateMachine, Table` — the
  **second**, table-driven design, the one exercise 5 explicitly says
  *not* to use. `MoodMachine` has no per-state `next()` at all; a
  `Table` dict drives every transition, and `MoodState` is a behaviorless
  `Enum`, the table-driven shape described earlier in the chapter, not
  the each-state-decides shape the exercise names.
- **Solution does:** Solves the "rebuild the mood machine as a state
  machine" problem, but with the table-driven engine (`table_machine.py`)
  instead of the named `state_machine.py`.
- **Suggested fix:** Either rewrite `Solutions/31_Patterns--State_Machines.md`
  section 5 to use `state.py`/`state_machine.py` (the version I ran
  above shows the shape), or change the exercise text to ask for the
  table-driven design instead of naming `state_machine.py`. Given the
  exercise's own point — contrasting with exercise 1's *State* surrogate
  by driving the same moods through the other design in this chapter —
  the first design is what exercise 1 already *doesn't* use, so the
  fix that keeps the pedagogical contrast is rewriting the solution, not
  the exercise.

### 2. Exercise 9 says to edit `vending_machine.py`; the solution never touches it

- **Severity:** drift
- **Where:** `Chapters/31_Patterns--State_Machines.md:905-908`
  (`Solutions/31_Patterns--State_Machines.md:552-641`)
- **Exercise says:** "Add a `Nickel` class deriving from `Money` to
  `vending_machine.py` and feed one to the machine without touching the
  table."
- **What actually happens:** Read literally, "the machine" is the
  `VendingMachine` in `tabledriven/vending_machine.py`. I tried it cold:
  added a `Nickel(Money)` dataclass, fed `Nickel("nickel", 5)` to a real
  `VendingMachine()` after inserting a quarter, without touching its
  table. `uv run python ex9_cold.py` gave
  `State.COLLECTING 25` then
  `NoTransition: no transition from <State.COLLECTING: 2> on Nickel`
  — the exact exception and message shape the solution's prose explains,
  so the exercise is directly doable against the named file.
  `Solutions/31_Patterns--State_Machines.md` section 9 instead defines a
  brand-new, unrelated two-state `Machine` class (`State.QUIESCENT`/
  `State.COLLECTING` only, one `Money` row) from scratch and never
  imports anything from `vending_machine.py`. The solution's own prose
  even cites `vending_machine.py`'s `FirstDigit`/`SecondDigit` as the
  contrasting case, while the code beside it never touches that file.
- **Solution does:** Demonstrates the same exact-type-dispatch lesson
  (`NoTransition`, then "add a row" vs. "use a `Money` instance instead
  of a subclass") on a toy machine it invents, rather than on
  `vending_machine.py` as the exercise names.
- **Suggested fix:** Rewrite the solution to import `VendingMachine`,
  `Money`, `State`, etc. from `vending_machine.py` and add the `Nickel`
  row(s) to its real table (my `ex9_cold.py` shows this reproduces the
  same exception cleanly), or reword the exercise to say "add a `Nickel`
  class to a table-driven machine like `vending_machine.py`'s" if the
  simplified machine is the intended answer.
