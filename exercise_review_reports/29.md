## Findings

### 1. Exercise 3 says "its classes" (plural); `facade.py` has exactly one

- **Severity:** minor
- **Where:** `Chapters/29_Patterns--Changing_the_Interface.md:416-419`
  (and `Solutions/29_Patterns--Changing_the_Interface.md:92-119`)
- **Exercise says:** "Rewrite `facade.py` as a module façade. Put its
  classes behind leading-underscore names in one module, expose
  functions that build them, and import only those from a second file."
- **What actually happens:** `facade.py` (build/examples/29.../facade.py)
  defines exactly one class besides the `Facade` wrapper itself: `A`.
  The comment `# Other classes that aren't exposed by the facade go
  here ...` is a comment, not code; nothing else is defined. I wrote the
  exercise cold using only what's in `facade.py`
  (`my_shop.py`/`my_ex3.py` in scratch work dir) — one hidden class
  `_A`, one factory function `make_a`, one import line — and it does
  everything the exercise asks:
  `uv run python my_ex3.py` → `_A(x=1)` and
  `['dataclass', 'make_a']`. The plural "classes"/"functions" in the
  exercise text does not match the singular content of the listing it
  names.
- **Solution does:** `Solutions/29...md`'s `shop.py` invents a second,
  entirely new class/function pair, `_B`/`make_b`, with no basis in
  `facade.py` (which never mentions a `B`), apparently to make the
  plural wording literally true. The solution's closing claim — "A
  caller sees nearly the same names in both versions" — is then not
  quite apples-to-apples: the original `facade.py` exposes one public
  name (`Facade`, via `make_a`), the module version exposes two
  (`make_a`, `make_b`).
- **Suggested fix:** Either singularize the exercise text ("Put its
  class behind a leading-underscore name... expose a function that
  builds it") to match `facade.py` as written, or extend `facade.py`
  itself to have a second class so the plural is accurate and the
  solution's `_B`/`make_b` has a referent. The former is the smaller
  change.
