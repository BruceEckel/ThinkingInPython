## Findings

### 1. Exercise 6 tells the reader to verify with `display_object()`; the solution never calls it

- **Severity:** minor
- **Where:** `Chapters/12_Techniques--Data_Classes_as_Types.md:1571`
  (and `Solutions/12_Techniques--Data_Classes_as_Types.md:340-395`, code at 372-375)
- **Exercise says:** "Predict whether it appears in the generated `__init__()`'s
  parameter list before you run it, then check with `display_object()`."
- **What actually happens:** The solution's `exercise_6.py` checks the prediction
  with `inspect.signature(Stars.__init__)` and `dataclasses.fields(Stars)` instead,
  and never imports or calls `display_object()`. I confirmed `display_object()`
  (the chapter's own tool, `from display import INTERESTING_DUNDERS,
  display_object`) does exactly what the exercise asks and would have worked
  fine here:
  ```
  display_object(Stars, INTERESTING_DUNDERS)
  #: [Attributes]
  #:   • built: typing.ClassVar[int] = 0 [CV]
  #: [Methods]
  #:   • __eq__(self, other)
  #:   • __hash__(self)
  #:   • __init__(self, number: int) -> None
  #:   • __repr__(self)
  ```
  This confirms `built` is absent from `__init__`'s parameter list, the same
  fact the solution establishes with `inspect.signature`, so the solution's
  conclusion is correct; it just doesn't use the named tool.
- **Solution does:** Uses `inspect.signature()` and `fields()`, both of which
  answer the same question the exercise poses but are not `display_object()`.
- **Suggested fix:** Either swap the verification call to
  `display_object(Stars, INTERESTING_DUNDERS)` (or plain `display_object(Stars)`,
  since `__init__` is one of the defaults it shows), or reword the exercise to
  not name `display_object()` specifically if `inspect.signature()` is the
  intended answer.
