## Findings

### 1. Exercise 1 tells the reader to run `recycle_dict.py` over `plastic.dat`, then to confirm that `recycle_dict.py` needs no changes

- **Severity:** wrong (the two halves of the instruction contradict each
  other; the prior sweep's finding is still present verbatim)
- **Where:** `Chapters/37_Patterns--Pattern_Refactoring.md:536-538`
  (and `Solutions/37_Patterns--Pattern_Refactoring.md:50-51`)
- **Exercise says:** "Add a `Plastic` material to `trash.py`, then run
  `recycle_dict.py` over `plastic.dat`. Confirm that `recycle_dict.py`
  and `parse_trash.py` need no changes"
- **What actually happens:** `recycle_dict.py` hardcodes its data file:
  line 8 is `for t in parse("trash.dat"):`. There is no argv handling
  and no other entry point. With `class Plastic(Trash): value = 0.15`
  added to `trash.py`, running the script unmodified reads `trash.dat`,
  which contains no `Plastic:` lines, so no plastic appears:

  ```
  (cd <scratch> && uv run python recycle_dict.py)
  --- Glass ---
  ... Total value = 88.78
  --- Paper ---   ... Total value = 21.20
  --- Aluminum ---... Total value = 584.50
  --- Cardboard --- ... Total value = 120.08
  ```

  Changing the one string literal to `"plastic.dat"` produces what the
  exercise is after:

  ```
  --- Glass ---
  weight of Glass = 10.0
  Total value = 2.30
  --- Plastic ---
  weight of Plastic = 20.0
  weight of Plastic = 40.0
  Total value = 9.00
  --- Aluminum ---
  weight of Aluminum = 30.0
  Total value = 50.10
  ```

  So the reader must edit the file the very next clause says needs no
  edit. The rest of exercise 1 checks out: `parse_trash.py` genuinely
  needs no change; the lost plastic is 20.0 + 40.0 = 60 lb, worth $9.00,
  and `plastic_dropped.py` reports `parsed 4, binned 2`; and
  `test_subclasses_self_register` is the one failing test
  (`Extra items in the left set: 'Plastic'`, 1 failed, 3 passed).
- **Solution does:** repeats the claim ("`recycle_dict.py` needs no
  change because `bins[type(t)].append(t)` keys on whatever type `t`
  actually is") and sidesteps the problem: `exercise_1.py` is a
  self-contained listing that builds its own two-item list and never
  runs `recycle_dict.py` or reads `plastic.dat` at all. The claim is
  true of the *sorting loop*, false of the *script*.
- **Suggested fix:** smallest change that makes it true is to scope the
  no-change claim to the loop and drop it from the run instruction, e.g.
  "Add a `Plastic` material to `trash.py`, then point `recycle_dict.py`
  at `plastic.dat` and run it. Confirm that its sorting loop and
  `parse_trash.py` need no other changes, ..." (Alternative, if the
  literal "no changes" is the point worth keeping: have the exercise
  say to add `Plastic:` lines to `trash.dat` instead of switching data
  files, but that invalidates the `#:` markers on `recycle_dict.py` and
  `recycle_rtti.py`, so the wording fix is the cheaper one.)

### 2. Exercise 4 says to run `recycling_note.py` "over data", but that listing reads no data file

- **Severity:** wrong (it can be done, but the chapter describes its own
  listing incorrectly)
- **Where:** `Chapters/37_Patterns--Pattern_Refactoring.md:546`
- **Exercise says:** "Derive `CrushedAluminum` from `Aluminum` and run
  both `recycle_dict.py` and `recycling_note.py` over data containing
  it."
- **What actually happens:** `recycling_note.py` never calls `parse()`
  and never opens a file. Its driver is
  `for cls in Trash.registry.values(): print(recycling_note(cls(1.0)))`.
  There is no data to run it over: a `CrushedAluminum` reaches it purely
  by having its `class` statement execute, which registers it. With
  `class CrushedAluminum(Aluminum): value = 1.50` added to `trash.py`,
  `uv run python recycling_note.py` prints a fifth line,
  `Aluminum: crush and bale`, with no data file involved. Only
  `recycle_dict.py` needs a data file (and, as in finding 1, needs its
  hardcoded `"trash.dat"` changed, or `CrushedAluminum:` lines added to
  `trash.dat`).

  The exercise's stated outcome does hold. Exact-key binning gives
  `CrushedAluminum` its own bin:

  ```
  --- Aluminum ---       weight 30.0   Total value = 50.10
  --- CrushedAluminum -- weight 20.0   Total value = 30.00
  --- Glass ---          weight 10.0   Total value = 2.30
  ```

  and `singledispatch` resolves it through the MRO to `Aluminum`'s note.
  A parent-sharing key that names no material in the loop also works;
  I used an MRO walk (`while cls.__base__ is not Trash`), Solutions uses
  a `bin` class variable. Both give `['Aluminum', 'Glass']`.
- **Solution does:** `exercise_4.py` is self-contained: it builds
  `pieces` as a literal list, bins it twice (by `type(t)` and by
  `t.bin`), and calls `recycling_note()` directly. It never mentions
  data files, so it does not inherit the error.
- **Suggested fix:** drop the data framing for the second script:
  "Derive `CrushedAluminum` from `Aluminum`, add it to the data
  `recycle_dict.py` reads, and run both that and `recycling_note.py`."
