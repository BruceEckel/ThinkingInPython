## Findings

### 1. Exercise 3 asks which of three exception conversions applies to a side effect and a side cause; the chapter says none of them does

- **Severity:** wrong
- **Where:** `Chapters/44_Effects--Effect_Management.md:926-927`
  (and `Solutions/44_Effects--Effect_Management.md:153-160,171-195`)
- **Exercise says:** "Classify every Effect in `slope_catch.py`, `withdraw()`
  ... and `Thermometer` ...: side effect, side cause, or exception. Which of the
  three conversions from [Converting Effectful to Pure] applies to each?"
- **What actually happens:** the chapter introduces those three conversions as
  three ways to remove *one* Effect. Line 122: "Transforming the exception
  Effect in `slope()` from `divide_by_zero_impurity.py` makes the function
  pure. Here are three ways to do it." And line 419-421 states it flatly:
  "Every technique in [Converting Effectful to Pure] manually manages one
  Effect, the exception. A `Result` tracks failure in the return type. A `try`
  binds the failure to a handler. A restrictive type removes the failure at
  construction." The chapter's technique for a side effect or a side cause is a
  different one, introduced two paragraphs later under `Effects by Hand`: "pass
  the implementation in as a parameter" (line 422-428, and the `ask_tell.py`
  listing). `Subdividing the Impure Portion` (line 315-332) says the same:
  exceptions become data via a `Result`, side causes become replaceable inputs,
  side effects become replaceable outputs.
  So of the six rows the exercise asks for, only the two exception rows have an
  answer among "the three conversions"; the four side-effect/side-cause rows do
  not.
- **Solution does:** answers "Return a result type" for all four of the
  side-effect/side-cause rows (`Solutions:157-160`), and then describes
  something that is not the chapter's Result conversion at all: for
  `withdraw()`, "take the balance as a parameter and return the new one"
  (`Solutions:178-181`); for `Thermometer`, "returns each reading as a value
  from the temperature source, and the caller folds new readings into whatever
  state it keeps" (`Solutions:191-193`). Neither uses `Result`, `Ok`, `Err`, or
  `@safe`, which is what `Return a Result Type` means in the chapter
  (`slope_result.py`). The solution's own table therefore contradicts line
  419-420 of the chapter.
- **Suggested fix:** a judgment call between two shapes.
  (a) Narrow the question: "Which of the three conversions from [Converting
  Effectful to Pure] applies to the exceptions, and which technique from
  [Effects by Hand](#effects-by-hand) applies to the others?" and change the
  four solution rows to name the parameter-passing technique.
  (b) Widen it to "which by-hand technique from this chapter" and keep one
  table, again with the four rows answering "pass the implementation in as a
  parameter."
  Either way the four rows currently reading "Return a result type" need to
  change, since the chapter defines that phrase as the `Result` container.

### 2. Exercise 2 asks for a count the solution does not produce

- **Severity:** minor (drift)
- **Where:** `Chapters/44_Effects--Effect_Management.md:917-920`
  (and `Solutions/44_Effects--Effect_Management.md:121-131`)
- **Exercise says:** "Now add a `Log` Effect (a protocol with `log(message)`)
  used by a new helper that `greet()` calls. Count the signatures you had to
  edit, and note how many of them mention an Effect they never use."
- **What actually happens:** I wrote the exercise cold, exactly as worded: the
  new helper `format_greeting(name, log)` is the only function that calls
  `log.log()`, and `greet()` merely hands the `Log` down. Command:
  `uv run python .../ch44/ex2.py` →
  `LOG: formatting greeting for Alice` / `['Hello, Alice!']`.
  Signatures I had to *edit*: `greet()`, `session()`, `menu()`, `main()` = four.
  The helper is newly written, not edited. Of those four, all four mention an
  Effect none of them ever calls, so the literal answer is "four edits, four of
  them never use it."
- **Solution does:** counts five ("Five signatures had to change, and only two
  of them wanted to ... Three of five is the number worth sitting with"). It
  gets there two ways the exercise did not ask for: it counts the brand-new
  `format_greeting()` as a changed signature, and it adds
  `log.log("greet started")` inside `greet()` (`Solutions:85`) so that `greet()`
  counts as a user of the Effect rather than a pure pass-through. The exercise
  assigns the `Log` to "a new helper that `greet()` calls," not to `greet()`.
- **Suggested fix:** smallest change is to the exercise, so the counts line up:
  "...used by a new helper that `greet()` calls, and by `greet()` itself. Count
  the signatures that had to change, including the new helper, and note how many
  of them mention an Effect they never use." Alternatively drop
  `log.log("greet started")` from the solution and restate its numbers as four
  edits, four of them pass-throughs, which weakens the "only two of them wanted
  to" contrast the solution builds on.

### 3. Exercise 3 names `Thermometer` in chapter 30, where three different classes have that name

- **Severity:** minor
- **Where:** `Chapters/44_Effects--Effect_Management.md:924`
  (and `Solutions/44_Effects--Effect_Management.md:183-190`)
- **Exercise says:** "`Thermometer` from [Observer](30_Patterns--Observer.md)"
- **What actually happens:** chapter 30 defines `Thermometer` three times:
  `classic_observer.py:61`, `observers.py:118`, and `async_observers.py:333`
  (line numbers in `Chapters/30_Patterns--Observer.md`). The first one holds no
  state at all (`def set_celsius(self, value): self.notify(value)`), so it has
  no `_celsius` and no `celsius` property. A reader who classifies the first
  `Thermometer` (the one the chapter presents first) cannot find the side cause
  the solution's answer is built on.
- **Solution does:** answers about the `observers.py` version specifically: "The
  `celsius` setter writes `_celsius` ... Reading `celsius` is a side cause",
  and the table row reads "`_celsius` read by `celsius`". Those claims hold for
  `observers.py` and `async_observers.py`, not for `classic_observer.py`.
- **Suggested fix:** name the listing in the exercise, e.g. "`Thermometer` from
  `observers.py` in [Observer](30_Patterns--Observer.md#...)".
