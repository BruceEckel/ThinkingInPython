## Findings

### 1. Exercise 1's edit, applied to `parallel_pure.py` as written, fails the listing's own `assert`

- **Severity:** wrong
- **Where:** `Chapters/43_Functional--Confidence.md:373` (listing at
  `:104-127`); `Solutions/43_Functional--Confidence.md:5-27`
- **Exercise says:** "Change `count_primes()` to return
  `(count, os.getpid())` and print the distinct process IDs alongside the
  counts."
- **What actually happens:** `parallel_pure.py` computes `serial` in the
  parent process and `parallel` in workers, then asserts they are equal.
  Once `count_primes()` returns a tuple carrying `os.getpid()`, the
  serial results carry the parent's PID and the parallel ones carry
  worker PIDs, so the assert fails. Making only the change the exercise
  names:

  ```
  $ uv run python work/43/ex1_literal.py
  Traceback (most recent call last):
    File "...ex1_literal.py", line 18, in <module>
      assert parallel == serial
             ^^^^^^^^^^^^^^^^^^
  AssertionError
  ```

  The exercise does not mention that the `assert` must go or be narrowed
  to the counts. (Exercise 2 then masks the problem: with
  `ThreadPoolExecutor` every PID is the same, so the untouched assert
  passes.)
- **Solution does:** silently drops both `serial` and the `assert`, and
  restructures into a `main()`. Its prose even alludes to the removal
  ("`assert parallel == serial` alone could never prove it") without
  telling the reader the edit was needed.
- **Suggested fix:** add a clause to the exercise, e.g. "…and narrow the
  `assert` to compare only the counts", or "…dropping the `assert`, which
  the process IDs now break."

### 2. Solution 5's stated counterexample for the broken `group_rounds()` never occurs

- **Severity:** wrong
- **Where:** `Solutions/43_Functional--Confidence.md:320-332`
- **Solution says:**

  ```text
  E           AssertionError: assert ['a', 'b'] == ['a', 'b', 'c']
  E             Right contains one more item: 'c'
  E           Failing test case: test_every_student_appears_once_per_round(
  E               names=['a', 'b', 'c'],
  E               size=2,
  ```

  and then "`['a', 'b', 'c']` is the simplest such roster the alphabet
  allows."
- **What actually happens:** I took `build/solutions/43_.../test_group_rounds.py`
  verbatim, deleted exactly the leftover-placement loop the solution says
  to delete, and ran it. Eight runs (three with the example database
  warm, five with `.hypothesis/` deleted first) produced only two
  answers, never `['a', 'b', 'c']`:

  ```
  E               names=['a', 'b', 'aa'],
  E               size=2,
  ```
  (5 of 8 runs; message `assert ['a', 'b'] == ['a', 'aa', 'b']`,
  "Right contains one more item: 'b'")

  ```
  E               names=['a', 'aa'],
  E               size=3,
  ```
  (3 of 8 runs)

  Hypothesis's shrinker prefers repeating the first alphabet character
  over advancing to a later one, so `'aa'` beats `'c'`. The quoted block
  and the sentence explaining it are both wrong.
- **Suggested fix:** replace the quoted block with a real run's output
  (`names=['a', 'b', 'aa'], size=2`) and reword the sentence: three
  students in groups of two is still the smallest roster that leaves
  anyone over, but the third name Hypothesis picks is `'aa'`, not `'c'`.
  Note also that the shrunk case varies between two shapes on a cold
  database, so the prose should not present one as inevitable.

### 3. Solution 7's `object` claim does not match what `ty` reports

- **Severity:** wrong
- **Where:** `Solutions/43_Functional--Confidence.md:457-467`
- **Solution says:** "Without that decorator a type checker must allow
  for a class inheriting from both, so a positive `isinstance()` leaves
  the intersection of the two alive and `result.answer` comes back as
  `object`."
- **What actually happens:** I ran `uv run ty check` (ty 0.0.75, the
  pinned version) on the solution's `describe_isinstance.py` with
  `reveal_type()` inserted, once as published and once with both `@final`
  decorators removed:

  ```
  with @final:     result.answer -> `float`
  without @final:  result.answer -> `float | Unknown`
  ```

  The rest of the paragraph checks out: the error branches reveal
  `ValueError`, `ZeroDivisionError & ~ValueError`, and
  `Exception & ~ValueError & ~ZeroDivisionError` in both files, and the
  `float` answer under `@final` matches the chapter body's claim at
  `Chapters/43_Functional--Confidence.md:165-170`.
- **Suggested fix:** change `object` to `float | Unknown`, or state the
  measurement without naming a type ("`result.answer` stops being plain
  `float`"). If the version matters, this is the shape the book pins
  elsewhere with "under `ty` 0.0.75".

### 4. Solution 7 says the two `describe()` versions are "the same length in statements"; they are not

- **Severity:** minor
- **Where:** `Solutions/43_Functional--Confidence.md:445-446`; exercise at
  `Chapters/43_Functional--Confidence.md:396-398` ("Count the lines")
- **What actually happens:** counting the two `describe()` bodies
  (chapter 42's `matching_errors.py` and the solution's
  `describe_isinstance.py`) with `ast`:

  ```
  match:      physical lines=12   ast statements=7
  isinstance: physical lines=9    ast statements=9
  ```

  Neither counting makes them equal, and the exercise explicitly asks the
  reader to count lines, where the gap is largest.
- **Suggested fix:** give the real numbers (the `match` is three lines
  longer, the `isinstance()` chain has two more statements) instead of
  claiming parity, or drop the length sentence and keep the repetition
  argument that follows it, which is the real point.

### 5. Exercise 4's "the minimal counterexample" is not a single value

- **Severity:** minor
- **Where:** `Chapters/43_Functional--Confidence.md:381-384`;
  `Solutions/43_Functional--Confidence.md:160-175`
- **Exercise says:** "Report the minimal counterexample Hypothesis
  finds"; the solution answers with `s = 'µ'` and builds
  `test_case_mapping.py` on that character.
- **What actually happens:** twelve pytest runs of the solution's own
  test, each with `.hypothesis/` deleted first:

  ```
  7  s = 'µ'
  4  s = 'ß'
  1  s = 'ﬀ'
  ```

  So `'µ'` is the usual answer, not the answer. (The solution does
  discuss `ß` later, so the Unicode explanation survives; only the
  presentation of one inevitable shrunk value is off.)
- **Suggested fix:** in the exercise, "Report the minimal counterexample
  your run finds"; in the solution, one clause noting that the shrunk
  character varies between `'µ'`, `'ß'`, and `'ﬀ'`, and that `'µ'` is the
  most common.
