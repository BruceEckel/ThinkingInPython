## Findings

### 1. Solution 6 renames `self_link()` to `pair_link()`, which the exercise did not ask for

- **Severity:** minor
- **Where:** `Chapters/10_Foundations--Cleanup.md:437-439` (exercise 6)
  and `Solutions/10_Foundations--Cleanup.md:273` (`def pair_link()`)
- **Exercise says:** "In `cycle.py`, change `self_link()` to build a
  two-object cycle (`a.peer = b` and `b.peer = a`) instead of a
  self-reference."
- **What actually happens:** The exercise's wording asks for the body of
  `self_link()` to change, not for the function to be renamed. The
  solution instead defines a new function `pair_link()`
  (`Solutions/10_Foundations--Cleanup.md:273-279`) and calls
  `pair_link()`, not `self_link()`. I performed the exercise literally
  (kept the name `self_link()`, changed only its body) and it works
  identically: both finalizers run at `gc.collect()`, in creation order
  (`a finalized` then `b finalized`), confirmed by running the edited
  copy with `uv run python`. So the rename doesn't affect correctness,
  it's just a name the exercise never asked to change.
- **Solution does:** Renames the function to `pair_link()` throughout its
  listing and prose.
- **Suggested fix:** Either rename back to `self_link()` in the
  solution to match the exercise literally, or note in the exercise
  that the function may be renamed to reflect its new behavior (a
  legitimate judgment call, since "self_link" no longer describes what
  the function builds). Cosmetic; does not affect the exercise's
  premise or outcome.
