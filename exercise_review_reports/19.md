## Findings

### 1. The chapter and solution 7 give different Python versions for the same fact

- **Severity:** wrong (one of the two statements is false; they cannot
  both be right)
- **Where:** `Chapters/19_Techniques--Concurrency.md:1209` and
  `Solutions/19_Techniques--Concurrency.md:342`
- **Exercise says:** exercise 7 (`:2299`) tells the reader to "Explain,
  using [The GIL Does Not Prevent Races]", so the reader is sent
  straight at the sentence the solution then contradicts.
- **What actually happens:** the chapter reads "Since 3.10 the
  interpreter switches threads only at a function call or at the jump
  that closes a loop iteration". Solution 7 reads "Since 3.11, the
  interpreter only considers switching threads at a function call or at
  the jump that closes a loop iteration". Same claim, same wording,
  different release.
- **Solution does:** asserts 3.11.
- **Suggested fix:** pick one and use it in both places. The eval-breaker
  reduction that this describes landed in CPython 3.10, so the chapter's
  number is the likelier correct one, but this is a fact to confirm
  rather than take from me: I did not reproduce the version boundary,
  only the contradiction.

### 2. Exercise 5 tells the reader to keep the name `lock`, then tells them to call `semaphore.release()`

- **Severity:** minor
- **Where:** `Chapters/19_Techniques--Concurrency.md:2290` and `:2293`
  (solution at `Solutions/19_Techniques--Concurrency.md:204`, `:238`)
- **Exercise says:** "replace `lock = asyncio.Lock()` with `lock =
  asyncio.Semaphore(1)`. ... Then add one stray `semaphore.release()`
  before the `gather()` call".
- **What actually happens:** the replacement text the exercise gives
  binds the name `lock`, and `async with lock:` in `increment()` is left
  untouched, so no name `semaphore` exists. A reader who pastes the
  exercise's own line and then its own `semaphore.release()` gets
  `NameError: name 'semaphore' is not defined`. I ran the intended
  program with the binding renamed and with it left as `lock`; both give
  `400`, and both give `200` with the stray release, five runs each, so
  only the name is wrong, not the outcome.
- **Solution does:** silently renames the binding to `semaphore`
  throughout.
- **Suggested fix:** write the replacement as `semaphore =
  asyncio.Semaphore(1)` and say the `async with` uses the new name, or
  else say `lock.release()` in the second half.

### 3. Solutions 1, 7, and 8 answer a restructured listing, so the reader's output does not match the solution's

- **Severity:** minor (drift; the substance of each answer is correct)
- **Where:** `Solutions/19_Techniques--Concurrency.md:6` (ex 1), `:319`
  (ex 7), `:358` (ex 8)
- **Exercise says:** each of the three is a localized edit to a named
  chapter listing ("add a fourth call ... to the `gather()` line";
  "remove the `time.sleep(0.000_001)` call"; "add a third thread
  submitting `[(1, "zzz"), (3, "aaa")]`").
- **What actually happens:**
  - Ex 1: `async_mechanics.py` opens with `x = fetch("a", 0.03)` and
    `print(type(x).__name__)`, so the edited program prints `coroutine`
    first. I get nine lines; the solution's `#:` block has eight and
    begins at `a: started`, because the solution deleted `x` and the
    `type()` print the exercise never mentioned.
  - Ex 7: the exercise edits `gil_race.py`, which uses
    `ThreadPoolExecutor`. The solution's listing uses bare
    `threading.Thread` objects and a different final `print`. Both forms
    give the same answer (I ran the executor form 10/10 and the
    solution's form 8/8, all `400`), but they are not the same program.
  - Ex 8: the exercise edits `priority_queue.py`, whose pool is
    `ThreadPoolExecutor(max_workers=2)`. Adding a third `pool.submit()`
    without also raising `max_workers` gives three *submissions* on two
    threads, not "a third thread". The solution avoids the question by
    replacing the executor with three `threading.Thread` objects and
    renaming `enqueue()` to `submit()`, which also drops the chapter
    listing's deliberate `p.result()` producer-failure surfacing. The
    drain order is the same either way (I ran the `max_workers=3` form
    3/3).
- **Suggested fix:** two independent choices. For ex 8, add "and raise
  `max_workers` to `3`" to the exercise (the smallest change, and it
  makes "a third thread" literally true). For ex 1 and 7, either have
  the solutions edit the chapter listing as the exercise says, or say in
  the solution's prose that the listing was reduced for presentation
  (solution 2 has the same reduction but there the restructuring is
  genuinely required by the exercise).
