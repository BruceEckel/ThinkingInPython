## Findings

### 1. Exercise 7's second half produces nothing observable as stated; the solution silently adds a step

- **Severity:** wrong (the exercise can be done, but its stated result
  cannot be reached from its stated steps)
- **Where:** `Chapters/36_Patterns--Memento.md:617-621`
  (and `Solutions/36_Patterns--Memento.md:452`)
- **Exercise says:** "Save a `Drawing` with `pickle`, then add a field with
  a default to `Drawing` and load the old bytes. Does the default appear?
  Now add a `__post_init__()` that rejects an empty title, and load again.
  What did pickle skip, and what would `copy.replace()` have caught?"
- **What actually happens:** the reader saves *a* `Drawing`. Every `Drawing`
  the chapter builds has a nonempty title (`Drawing("Duck")`). Loading those
  bytes under a class carrying a `__post_init__()` that rejects an empty
  title is indistinguishable from loading them under the class without it,
  so nothing shows that `__post_init__()` was skipped. Performed exactly as
  written (`work/36/ex7/literal.py`, `uv run python literal.py`):

  ```
  step 1: DrawingV2 1 False
  step 2: DrawingV3 'Duck' 1
  identical outcome to step 1: True
  ```

  The demonstration requires bytes for an object that *would* fail the new
  validation, i.e. a `Drawing` saved with an empty title before the
  validation existed. The exercise never says to save one.
- **Solution does:** `exercise_7.py` quietly pickles a second object the
  exercise never mentions, `blank = pickle.dumps(Drawing("", ("circle",)))`,
  and does the whole second half against `blank`, not against `blob`.
- **Suggested fix:** name the empty title in the exercise's first sentence,
  e.g. "Save two `Drawing`s with `pickle`, one of them with an empty title"
  (then "load the blank one again" for the second half). Everything else in
  exercise 7 checks out: the default *does* appear (class attribute lookup),
  `restored.__dict__` has no `layer`, `copy.replace()` on the blank one
  raises `ValueError`, and the solution's `default_factory` aside is true
  (verified: `AttributeError: 'DrawingV2' object has no attribute 'layer'`).

### 2. Solution 3's claim that the uncompensated reconstruction "fails `ty check`" is false

- **Severity:** wrong (the solution states something false about its own code)
- **Where:** `Solutions/36_Patterns--Memento.md:253-257`
  (exercise at `Chapters/36_Patterns--Memento.md:603-605`)
- **Solution says:** "`Drawing` declares `strokes` as `tuple[str, ...]`, so a
  `Drawing` built with a `list` there fails `ty check`."
- **What actually happens:** "there" is `Drawing(data["title"], data["strokes"])`
  where `data = json.loads(as_json)`. `json.loads()` returns `Any`, so `ty`
  sees nothing to complain about. Dropping the `tuple(...)` from
  `exercise_3.py` and running `uv run ty check probe.py`:

  ```
  All checks passed!
  ```

  `ty` does flag a statically-typed list (`literal_list: list[str]` passed to
  `Drawing` gives `error[invalid-argument-type]: Expected tuple[str, ...],
  found list[str]`), so the claim is true in general and false at the call
  site the solution is describing. The runtime consequences the solution also
  cites are real and reproduced: without `tuple(...)`,
  `reconstructed == drawing` prints `False`, and `hash(reconstructed)` raises
  `TypeError: unhashable type: 'list'`.
- **Suggested fix:** drop the `ty check` sentence, or reword it to the true
  version, e.g. "`ty` cannot help here, because `json.loads()` returns `Any`;
  the mismatch shows up only at runtime, where `reconstructed == drawing` is
  `False` and the `Drawing` is no longer hashable." The following sentence
  about hashability already carries the real point.
