## Findings

### 1. Solution 4 renames an existing attribute the exercise didn't ask to touch

- **Severity:** minor
- **Where:** `Chapters/22_Patterns--Data_Transfer_Objects.md:314-317` (exercise 4)
  and `Solutions/22_Patterns--Data_Transfer_Objects.md:98-124`
- **Exercise says:** "In `display_namespace.py`, add a fourth attribute to `m`
  by passing it to the constructor, then add it by assignment after the
  existing `m.more = 11` instead. Confirm `vars(m)` reports the same four
  attributes either way, and note whether they come out in the same order."
- **What actually happens:** `display_namespace.py`'s `m` has attributes
  `info`, `tags`, then `more` (via assignment). Performing the exercise as
  stated — keeping `info`/`tags`/`more` and adding a fourth, e.g. `tag=12`,
  once via the constructor and once via assignment after `m.more = 11` —
  reproduces the claimed result exactly:
  ```
  {'info': 'Spam', 'tags': ['urgent', 'todo'], 'more': 11, 'tag': 12}
  {'info': 'Spam', 'tags': ['urgent', 'todo'], 'more': 11, 'tag': 12}
  True
  ['info', 'tags', 'more', 'tag']
  ['info', 'tags', 'more', 'tag']
  ```
  (run via `uv run python`, scratch file `ex4_mine.py`).
- **Solution does:** renames the listing's `tags` attribute to `b` in both
  of its constructed objects (`SimpleNamespace(info="Spam", b=["x", "y"],
  more=11, tag=12)`), something the exercise never asks for. The final
  answer and its claims (`vars(built) == vars(assigned)` is `True`, same
  insertion order) are still correct under the renamed field, just not a
  literal continuation of the chapter's own `m`.
- **Suggested fix:** keep `tags=["urgent", "todo"]` (the listing's actual
  field) instead of introducing `b`. Cosmetic; does not change any printed
  claim or the type-checking story.
