## Findings

### 1. Solution 8 names the wrong row for the largest `tottime`

- **Severity:** wrong
- **Where:** `Solutions/18_Techniques--Performance.md:287-290` (exercise at `Chapters/18_Techniques--Performance.md:1495-1497`)
- **Exercise says:** "Name the function with the largest `tottime` and the one with the largest `cumtime`"
- **Solution says:** "The largest `cumtime` belongs to `exec`, then `<module>`, then `outer`. The largest `tottime` belongs to the generator expression inside `inner()`, where the arithmetic happens."
- **What actually happens:** the largest `tottime` belongs to `{built-in method builtins.sum}`, not to the generator expression. The genexpr is second, by a stable margin of roughly 35%.

  ```
  $ (cd build/solutions/18_Techniques--Performance && uv run python -m cProfile -s tottime exercise_8.py)
     ncalls  tottime  percall  cumtime  percall filename:lineno(function)
          2    0.020    0.010    0.034    0.017 {built-in method builtins.sum}
     200002    0.014    0.000    0.014    0.000 exercise_8.py:3(<genexpr>)
  ```

  Seven consecutive runs, `tottime` for `sum` against the genexpr: 0.020/0.014, 0.021/0.015, 0.020/0.015, 0.021/0.016, 0.020/0.015, 0.020/0.015, 0.020/0.015. `sum` leads in 7 of 7, and the ordering never came close to flipping. This is not scheduler noise: cProfile charges the C `sum` frame with the cost of driving the generator, so `sum` outranks the genexpr by construction. The chapter's own sample table at `Chapters/18_Techniques--Performance.md:159-164` shows the same shape, with `builtins.sum` at tottime 0.001 above the genexpr's 0.000.

  The `cumtime` half of the answer is correct: `exec` (0.033), then `<module>` (0.033), then `outer` (0.033).
- **Suggested fix:** either correct the sentence to name `{built-in method builtins.sum}` as the `tottime` leader (and say that a C builtin absorbs the cost of the iterator it drives, which is itself a useful profiling lesson), or change `exercise_8.py` so the arithmetic really is the top `tottime` row, replacing `sum(i * i for i in range(100_000))` with an explicit Python accumulation loop inside `inner()`. Note that the solution counts `exec`, also a builtin, as its `cumtime` answer, so excluding builtins is not a consistent reading of the current text.

### 2. Solution 3 never shows the peak the exercise asks it to measure

- **Severity:** minor

- **What actually happens:** `exercise_3.py` starts `tracemalloc`, binds `_, peak = tracemalloc.get_traced_memory()`, and then never uses `peak`. Its entire output is the fruit of the comprehension:


- **Suggested fix:** print `peak` behind the `--numbers` guard that the sibling solutions in this same file already use (`exercise_1.py` at line 27, `exercise_9.py` at line 322, `ch18_join_vs_concat.py` at line 368), or print a machine-independent threshold in the chapter's usual style, measuring both variants in the one script and comparing them.
