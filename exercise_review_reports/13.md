## Findings

### 1. Exercise 4's solution drops two of the three existing channels, and never shows the `cost()` case

- **Severity:** drift
- **Where:** `Chapters/13_Techniques--Pattern_Matching.md:850` (and
  `Solutions/13_Techniques--Pattern_Matching.md:129-155`)
- **Exercise says:** "Add a `Webhook` channel to `notifications_match.py`: a
  data class with a `url` field, added to the `Notification` union. Run `ty`
  before adding its `case` to `render()` and `cost()`, and read the errors.
  Then add both cases and confirm `ty` passes."
- **What actually happens:** The chapter's `notifications_match.py` defines
  `type Notification = Email | Sms | Push`. Doing the exercise as stated
  (extending that file) gives `type Notification = Email | Sms | Push |
  Webhook`, and running `uv run ty check notifications_match.py` before
  adding the `Webhook` case reports **two** diagnostics, one in `render()`
  and one in `cost()`:
  ```
  error[type-assertion-failure]: Argument does not have asserted type `Never`
    --> notifications_match.py:32:13
                             Inferred type of argument is `Webhook & ~Email & ~Sms & ~Push`
  error[type-assertion-failure]: Argument does not have asserted type `Never`
    --> notifications_match.py:43:13
                             Inferred type of argument is `Webhook & ~Email & ~Sms & ~Push`
  Found 2 diagnostics
  ```
  `Solutions/13_Techniques--Pattern_Matching.md`'s `exercise_4.py` instead
  declares `type Notification = Email | Webhook`, silently dropping `Sms`
  and `Push`, and never defines a `cost()` function at all, so it only ever
  shows one error, for `render()`.
- **Solution does:** `exercise_4.py` (lines 132-155) has only `Email` and
  `Webhook` in the union, and only a `render()` function. It never adds a
  `case Webhook` to `cost()`, so the exercise's explicit second half ("add
  its `case` to ... `cost()`", "add both cases and confirm `ty` passes") is
  never carried out or shown.
- **Suggested fix:** Have `exercise_4.py` extend the chapter's actual
  `notifications_match.py` (keep `Sms` and `Push` in the union) and show the
  `cost()` function with its `Webhook` case added too, matching what the
  exercise asks for.

### 2. Exercise 4's solution shows a `ty` error message that does not match what `ty` actually reports

- **Severity:** wrong
- **Where:** `Solutions/13_Techniques--Pattern_Matching.md:157-166`
- **Exercise says:** "Run `ty` before adding its `case` to `render()` and
  `cost()`, and read the errors."
- **What actually happens:** Reproducing the "before" state (union has
  `Webhook` but `render()` has no `case Webhook`) and running `uv run ty
  check` (ty 0.0.75, the version pinned by this repo) gives:
  ```
  error[type-assertion-failure]: Argument does not have asserted type `Never`
    --> ex4_before_case.py:20:13
                             Inferred type of argument is `Webhook & ~Email`
  info: `Never` and `Webhook & ~Email` are not equivalent types
  Found 1 diagnostic
  ```
  This is the same error *shape* the chapter's own exercise 2 solution shows
  correctly (verified: exercise 2's quoted `ty` output for `Rectangle`
  matches exactly what `ty` reports when reproduced). But exercise 4's
  solution quotes a different, older-looking error entirely:
  ```
  error[invalid-argument-type]: Argument to function `assert_never` is incorrect
    |
    |             assert_never(note)
    |                          ^^^^ Expected `Never`, found `Webhook`
  ```
  Different diagnostic code (`invalid-argument-type` vs. the real
  `type-assertion-failure`) and different message text.
- **Solution does:** Quotes the stale/incorrect error text described above.
- **Suggested fix:** Regenerate the quoted error block from an actual `uv
  run ty check` on the exercise's own file, the same way exercise 2's block
  was produced.

### 3. Exercise 3's solution renames the pre-existing catch-all case without being asked to

- **Severity:** minor
- **Where:** `Chapters/13_Techniques--Pattern_Matching.md:454` (and
  `Solutions/13_Techniques--Pattern_Matching.md:106-107`)
- **Exercise says:** "Rewrite `mapping_patterns.handle()` to also accept a
  nested shape, such as `{"type": "click", "at": {"x": x, "y": y}}`, binding
  `x` and `y` from the inner dictionary." (Adding a case, nothing else.)
- **What actually happens:** Doing only what's asked (adding the nested
  `case` and leaving everything else alone) reproduces the chapter's stated
  output with the original catch-all intact: `case unknown: return
  f"Unrecognized event: {unknown}"` still prints `Unrecognized event:
  {'button': 1}` for an unmatched event, verified by running the edited file.
- **Solution does:** Renames the catch-all's bound name and message from
  `unknown` / `"Unrecognized event: {unknown}"` to `nonevent` /
  `"Not an event: {nonevent}"`, an edit the exercise never asked for. (This
  particular case isn't exercised in the solution's own printed output, so
  the rename isn't even demonstrated.)
- **Suggested fix:** Keep the original `unknown` / `"Unrecognized event:
  ..."` case unchanged, adding only the new nested-pattern case.

### 4. Exercise 6's solution never writes a function named `act()`

- **Severity:** drift
- **Where:** `Chapters/13_Techniques--Pattern_Matching.md:858-861` (and
  `Solutions/13_Techniques--Pattern_Matching.md:261-332`)
- **Exercise says:** "Give `value_patterns.py`'s `Signal` a third member,
  and write `act()` so that it compares against a module-level `FALLBACK:
  Final[Signal]`. Run it and confirm that the constant captures instead of
  comparing."
- **What actually happens:** The instruction is doable exactly as worded:
  adding a third `Signal` member and rewriting `act()` (keeping only `case
  Signal.GO` plus a bare `case FALLBACK:`) reproduces the capture bug when
  called with `Signal.STOP`, verified by running:
  ```
  print(act(Signal.STOP))
  #: FALLBACK is now Signal.STOP
  ```
- **Solution does:** `ch13_fallback_capture.py` never defines an `act()`.
  It reuses the chapter's own function name `broken()` for the buggy
  version (with `FALLBACK` swapping in for the chapter's `DEFAULT`), plus
  `dotted()` and `guarded()` for the two fixes. The code and its printed
  output are correct, but the exercise's explicitly named function `act()`
  never appears.
- **Suggested fix:** Either rename the solution's `broken()` to `act()` (or
  rename the exercise's requested function to `broken()`/some other name)
  so the two agree.
