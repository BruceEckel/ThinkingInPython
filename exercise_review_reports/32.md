## Findings

### 1. Solution 8's `weapon_outcome()` is not antisymmetric: three weapon pairs lose to each other

- **Severity:** wrong
- **Where:** `Solutions/32_Patterns--Multiple_Dispatching.md:511-541`
  (`exercise_8.py`), and the identical formula in `exercise_10.py`
  (`Solutions/...md:627+`)
- **Solution says:** "ranked around a cycle: each weapon beats the previous two
  in the ranking and loses to the next two, the same shape
  `paper_scissors_rock.py` uses for three items, extended to six"
  (`Solutions/...md:506`)
- **What actually happens:** With six weapons, `diff = (ia - ib) % 6` has five
  non-draw values, and the prose accounts for only four of them (1, 2 → win;
  4, 5 → lose). `diff == 3`, the antipodal pair, falls through into the `LOSE`
  branch in *both* directions:

  ```
  $ uv run python ex8check2.py
  pairs where both directions report the same result:
    Jargon vs SellImaginaryProduct: lose / lose  <-- both lose
    Play vs Edict: lose / lose  <-- both lose
    InventFeature vs Schedule: lose / lose  <-- both lose
  ```

  So `battle(a, b)` and `battle(b, a)` name opposite winners for the same two
  weapons: `battle` returns `b` on `LOSE`, so whoever is passed second wins.
  The three-item shape in `paper_scissors_rock.py` *is* antisymmetric
  (diff 1 → win, diff 2 → lose, nothing left over), so it does not "extend to
  six" the way the sentence claims. This is visible in the group table:
  `Dwarf vs Elf` is `['lose','lose','lose','lose']` while `Elf vs Dwarf` is
  `['win','win','lose','win']` — not the mirror image.
- **Suggested fix:** Judgment call between two options. (a) Make the ranking
  antisymmetric by making the antipodal pair a draw (`if diff == 3: return
  Outcome.DRAW`) — but then `meeting()` can stall on repeated draws and needs a
  tie-break. (b) Use an odd number of weapons (five, or six with each beating
  the previous *three*... which reintroduces the same problem), or key a real
  36-entry table by hand. Simplest correct version: rank so each weapon beats
  the previous `k` and loses to the next `k` with `2k + 1 == len(WEAPON_ORDER)`,
  i.e. keep six weapons only if the antipodal case is defined explicitly.

### 2. Solution 8 claims "no group can count on winning"; `Troll` wins every seed

- **Severity:** wrong
- **Where:** `Solutions/32_Patterns--Multiple_Dispatching.md:600-603`
- **Solution says:** "The weapon ranking is a genuine cycle: nothing dominates
  everything, so no group can count on winning. The outcome depends on the
  random weapon draws each round, exactly as it does in a real
  rock-paper-scissors tournament."
- **What actually happens:** `meeting()` is deterministic in its outcome.

  ```
  meeting(5) winners over 200 seeds:  Counter({'Troll': 200})
  meeting(20) winners over 50 seeds:  Counter({'Troll': 50})
  ```

  Two of the three cross-kind matchups never depend on the draw at all:
  `Dwarf vs Elf` loses on all four weapon combinations, and `Elf vs Troll`
  loses on all four. Combined with `meeting()`'s fixed pair order
  (`Dwarf`-`Elf` first), `Troll` is the survivor every time. The published
  `#: Troll` marker is not one sampled outcome, it is the only outcome.
- **Suggested fix:** Either fix the ranking (finding 1) so the matchups are
  genuinely mixed, or replace the paragraph with what the listing actually
  does. Note that the `#: Troll` marker will not detect a future regression
  here, since it cannot vary.

  (cyclically)."

### 4. Solution 6's fail-fast paragraph is false for the chapter's `Lizard`

- **Severity:** wrong
- **Where:** `Solutions/32_Patterns--Multiple_Dispatching.md:442-447`
- **Solution says:** "The tolerant version also loses the failure that made the
  exact version safe. A `Lizard` whose rows you forgot to write no longer
  raises `KeyError`. It silently inherits its parent's answers and plays as
  whatever it derives from."
- **What actually happens:** Exercise 1 adds `class Lizard(Item)`, a direct
  subclass of the base. Its MRO is `[Lizard, Item, object]`, and no row is
  keyed on `Item`, so the tolerant lookup still raises. Running the solution's
  own `TolerantItem.compete()` body against a row-less `Lizard(Item)`:

  ```
  $ uv run python ex6b.py
  KeyError ['Lizard', 'Rock']     # Lizard(Item), rows forgotten
  win                             # Origami(Paper), rows inherited
  ```

  Only a subclass of a *concrete* item type (`Origami(Paper)`) inherits
  answers. A new competitor added the way the chapter adds `Lizard` still
  fails fast.
- **Suggested fix:** Replace `Lizard` with a subclass of a concrete item, e.g.
  "a `WetPaper(Paper)` whose rows you forgot to write no longer raises a
  `KeyError`; it silently plays as `Paper`." That also connects to the last
  paragraph, which already uses `WetPaper` as its example.

### 5. Exercise 6 asks for one MRO walk and one answer; the solution does two of each

- **Severity:** drift
- **Where:** `Chapters/32_Patterns--Multiple_Dispatching.md:527-529` and
  `Solutions/32_Patterns--Multiple_Dispatching.md:425, 442`
- **Exercise says:** "make the table tolerate subclasses by walking
  `type(self).__mro__` for the first class that has a row, and say **which of
  the two** properties named after the table listing you have just given up."
- **What actually happens:** Walking only `type(self).__mro__` (what the
  exercise asks) gives up exactly one property, exact matching; the opponent is
  still matched exactly and a missing pair still raises. Verified:

  ```
  $ uv run python ex6.py
  win                             # Origami(Paper) vs Rock, left MRO walked
  KeyError ['Rock', 'Origami']    # right operand still exact
  ```

  The solution instead walks **both** MROs (nested loops over
  `type(self).__mro__` and `type(item).__mro__`), which is more than the
  exercise asked for, and its "Order now decides the answer" discussion exists
  only because of the second loop. It then answers the singular question with
  two properties ("the property the chapter names first", then "also loses the
  failure that made the exact version safe").
- **Suggested fix:** Either widen the exercise ("by walking the MROs of both
  operands") so the solution matches, or narrow the solution to the single left
  MRO the exercise names and drop the second-property paragraph (which finding
  4 shows is wrong as written anyway).
