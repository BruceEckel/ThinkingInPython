## Findings

### 1. Solutions exercise 2's committed output marker disagrees with the actual run

- **Severity:** minor
- **Where:** `Solutions/35_Patterns--Flyweight.md:132` (code at
  `build/solutions/35_Patterns--Flyweight/exercise_2.py`)
- **Exercise says:** "Use `tracemalloc` to compare `parse_map()` on a
  large map against a version whose `tile()` has no `@cache`. How does
  the ratio change as the map grows?"
- **What actually happens:** Running the solution from the repo root
  (`uv run python build/solutions/35_Patterns--Flyweight/exercise_2.py`)
  four times in a row gives:
  ```
  50 ratio uncached/cached: 9.8
  100 ratio uncached/cached: 9.9
  200 ratio uncached/cached: 11.1
  ```
  This is stable across repeated runs on this machine. The committed
  marker at line 132 reads `#: 50 ratio uncached/cached: 9.9`, i.e. 9.9
  where the actual, reproducible value is 9.8. Lines 133-134 (`9.9` at
  size 100, `11.1` at size 200) match. The prose's qualitative claim
  ("roughly 10x at a 50x50 map") is unaffected either way, only the
  printed digit is wrong.
- **Solution does:** N/A (this is the solution's own listing).
- **Suggested fix:** Update the marker at line 132 to `#: 50 ratio
  uncached/cached: 9.8`, the way any other stale `#:` marker is
  corrected. Because this measurement comes from `tracemalloc` rather
  than a registered wall-clock timing boolean, it is not in
  `tools/data/timing.txt` and so is not self-healing; worth confirming
  the value is stable on the machine that regenerates markers before
  committing a fix, since allocator behavior can differ across
  platforms.

### 2. Exercise 8's solution silently changes the sleep duration the exercise specifies

- **Severity:** minor / drift
- **Where:** `Chapters/35_Patterns--Flyweight.md:508` (exercise text)
  vs. `Solutions/35_Patterns--Flyweight.md:534` (solution code)
- **Exercise says:** "Make `tile()`'s body slow, with a
  `time.sleep(0.05)` before it builds the `Tile`, and call it from four
  threads with the same, previously unseen symbol."
- **What actually happens:** `exercise_8.py` in Solutions uses
  `time.sleep(0.1)` instead of the `0.05` the exercise specifies (with
  an added comment, "Widen the window between miss and store"). I
  patched a copy back to `0.05` and ran it five times in a row; it
  reproduced the same race result every time (`4 4` / `1` / `1`), so
  `0.05` is not needed for the demonstration to work reliably on this
  machine — the solution's value is not a fix for a flaky `0.05`, just
  a different, unannounced choice.
- **Solution does:** Uses `0.1` and gets the same `#: 4 4` / `#: 1` /
  `#: 1` result the exercise's stated `0.05` also produces.
- **Suggested fix:** Either change the solution to `time.sleep(0.05)`
  to match the exercise exactly, or add a short prose note explaining
  why a wider sleep was chosen (e.g. more margin against scheduler
  noise on some machines, consistent with the Windows-timer traps noted
  elsewhere in this repo). Either is a small edit; not blocking, since
  both values demonstrate the same race.
