## Findings

### 1. Exercise 9's stated method does not work; every natural payload is a `SyntaxError`

- **Severity:** wrong (the exercise can be done, but not by the route it
  describes, and it gives no hint that more is required)
- **Where:** `Chapters/17_Techniques--Metaprogramming.md:1840-1843`
- **Exercise says:** "Remove that check, call `Command.make_class()` with a name
  containing a newline and a second statement, and confirm that the injected
  statement runs."
- **What actually happens:** `make_class()` splices `class_name` in **twice**,
  and the second splice lands inside the `super().__init__("{class_name}")`
  string literal. A raw newline there is an unterminated string literal, so the
  `exec()` never runs anything. I copied `commander.py`, deleted the
  `KNOWN_COMMANDS` check, and tried the payloads a reader would reach for
  (`uv run python .../ex9_try.py`):

  ```
  A: 'Reset\nprint("INJECTED")'                              -> SyntaxError: unterminated string literal
  B: 'Reset(Command): pass\nprint("INJECTED")\nclass Ignored' -> SyntaxError: unterminated string literal
  C: 'X: pass  # ")\nprint("INJECTED")\nclass Fake'           -> SyntaxError: unterminated string literal
  D: 'X: pass; Y = """\nprint("INJECTED")\n#'                 -> INJECTED, then KeyError
  ```

  Only D, which ends its payload with a line that opens a triple-quoted string
  to swallow the second splice, executes the injected statement.
- **Solution does:** the solution reaches the same conclusion and uses the same
  trick (`Solutions/17_Techniques--Metaprogramming.md:391`, payload
  `'X(Command):\n    pass\nprint("injected code ran")\nY = """  #'`), and its
  prose says outright "The payload needs a little care, because `make_class()`
  splices `class_name` in twice." So the chapter's half is the one that is
  missing information, not the solution's.
- **Suggested fix:** add one clause to the exercise warning that the name is
  spliced in twice and that the second splice sits inside a string literal, so
  the payload has to close or swallow it. For example: "…with a name containing
  a newline and a second statement (note that `make_class()` splices the name in
  twice, the second time inside a string literal, so a bare newline is a
  `SyntaxError`), and confirm that the injected statement runs."

### 2. Solution 6 quotes a version of `metaclass_layout_conflict.py` that the chapter no longer has

- **Severity:** wrong (the solution states three things about the chapter's
  listing that reading the listing disproves)
- **Where:** `Solutions/17_Techniques--Metaprogramming.md:226-258`, against
  `Chapters/17_Techniques--Metaprogramming.md:1127-1135`
- **Solution says:** "Removing the `# type: ignore` from
  `metaclass_layout_conflict.py` leaves the class header bare:" followed by

  ```python
  with ignore(TypeError):
      class Singleton(type, dict[type, Any]):
          pass
  ```

  then a diagnostic quoted as `--> metaclass_layout_conflict.py:6:11`, then
  "Running the same file prints
  `TypeError('multiple bases have instance lay-out conflict')`."
- **What actually happens:** the chapter's listing uses `try:` / `except
  TypeError as e: print(e)`, not `with ignore(TypeError):`, and imports nothing
  from `exceptions`. Three consequences, all reproduced:

  1. The class header is on **line 5**, not 6. With the `# type: ignore`
     removed, `uv run ty check` reports
     `--> ...\ex6.py:5:11`, everything else in the diagnostic matching the
     solution's text.
  2. The program prints the bare message, not the `repr`:
     `uv run python ex6.py` → `multiple bases have instance lay-out conflict`.
     The `TypeError('...')` form the solution quotes is what
     `utils/exceptions.py`'s `ignore` prints (`print(f"{exc!r}")`), which the
     chapter's listing does not use.
  3. The last paragraph's "The `# type: ignore` is in the chapter's version
     because this listing exists to show the `TypeError`" is still true, but the
     quoted code above it is not the chapter's code.
- **Suggested fix:** replace the quoted snippet with the chapter's `try` /
  `except TypeError as e: print(e)` form, change `:6:11` to `:5:11`, and change
  "Running the same file prints `TypeError('multiple bases have instance lay-out
  conflict')`" to "Running the same file prints `multiple bases have instance
  lay-out conflict`."

### 3. Solution 9 contradicts itself about when the injected statement runs

- **Severity:** minor
- **Where:** `Solutions/17_Techniques--Metaprogramming.md:405` vs `:417`
- **Solution says:** at line 405, correctly, "`print("injected code ran")` is not
  part of any class body. It runs at module level inside `exec()`". At line 417,
  the same solution says "the injected `print()` runs while `exec()` is
  executing the class body."
- **What actually happens:** the injected statement runs at module level of the
  exec'd source, after the class body has finished. Reproduced with an
  instrumented payload:

  ```
  $ uv run python chk9.py
  class body running
  injected code ran; X exists: True
  ```

  In the solution's own payload the class body is `pass`, and `class
  X(Command): pass` is complete before `print("injected code ran")` is reached.
- **Suggested fix:** change line 417 to "…and the injected `print()` runs at
  module level inside `exec()`, after the class body has finished," or simply
  drop the trailing clause, since line 405 already makes the point.

### 4. Solutions 8 and 10 rebuild the named listing under new names instead of editing it

- **Severity:** minor (drift)
- **Where:** `Chapters/...:1837-1839` and `:1844-1847`;
  `Solutions/...:324-361` and `:430-452`
- **Exercise says:** ex. 8, "In `new_vs_init.py`, move the `bases += (Tag,)`
  line from `__new__()` into `__init__()`"; ex. 10, "Change
  `prepare_namespace.py`'s `NoDuplicates` so that … it keeps the *first*
  definition."
- **Solution does:** solution 8 writes a fresh file with the class renamed
  `Built` → `Demo`, deletes `Meta.__new__()` entirely (so `added_in_new` and the
  `display_object()` call are gone), and never shows `new_vs_init.py`'s own
  closing line changing from `has Tag base: True` to `False`. Solution 10
  renames `NoDuplicates` → `KeepFirst` and `Strict` → `First` and drops

- **What actually happens:** performing exercise 8 as written on the real
  listing gives exactly the answer the solution predicts — I edited a copy of

  False` — so nothing here is *wrong*, only differently presented from what the
  exercise asked for. Solution 10's version behaves identically to editing
  `NoDuplicates` in place, which I confirmed.
- **Suggested fix:** either keep the names the exercises name (`Built`,
  `NoDuplicates`, `Strict`), or add a sentence to each solution saying it shows
  the change in a reduced standalone file.

### 5. Exercise 10's confirmation is unobservable in the chapter's listing

- **Severity:** minor
- **Where:** `Chapters/17_Techniques--Metaprogramming.md:1846`, against the
  `prepare_namespace.py` listing at `:1240-1264`
- **Exercise says:** "Confirm that `Handlers().on_open()` then runs the first
  `on_open`."
- **What actually happens:** in `prepare_namespace.py`, both `on_open` bodies
  are `...`, so both return `None` and print nothing. After the `NoDuplicates`
  change, `Handlers().on_open()` succeeds silently and confirms nothing about
  *which* definition survived. Distinguishing them requires an edit the exercise
  never mentions.
- **Solution does:** silently gives the two methods `print("first on_open")` and

- **Suggested fix:** add the needed edit to the exercise, e.g. "…give the two
  `on_open` definitions distinguishable bodies and confirm that
  `Handlers().on_open()` then runs the first one."
