## Findings

### 1. Solution 5 names the wrong diagnostic for the downstream break

- **Severity:** wrong
- **Where:** `Solutions/47_Effects--Stateless_in_Practice.md:594-596`
- **Solution says:** "Fixing that then breaks every caller that matched
  exhaustively on the old set: `assert_never()` reports the new member as an
  unhandled branch in `report()`."
- **What actually happens:** after widening `research()`'s error parameter to
  include `TooLong`, the diagnostic `ty` produces in `report()` is an
  `invalid-yield` at the `yield from`, not an `assert_never` failure. Built the
  Solutions' own `report.py` against the widened `research_long.research`:

  ```
  $ uv run ty check --extra-search-path . report_b.py
  error[invalid-yield]: Yield expression type does not match annotation
    --> report_b.py:18:24
  18 |     found = yield from caught(research)()
     |                        ^^^^^^^^^^^^^^^^^^ expression of type
     |   `Need[Feed] | Need[Encyclopedia] | TooLong`,
     |   expected `Need[Feed] | Need[Encyclopedia]`
  ```

  `assert_never()` fires only after two *further* edits — widening
  `catch(Unavailable, NotInteresting, NoArticle)` to include `TooLong` and
  widening the `found:` annotation. Only then:

  ```
  error[type-assertion-failure]: Argument does not have asserted type `Never`
    --> report_c.py:31:13
  31 |             assert_never(found)
     |   Inferred type of argument is
     |   `TooLong & ~Unavailable & ~NotInteresting & ~NoArticle`
  ```

  The solution's first quoted diagnostic (the `invalid-yield` inside
  `research()` at the new `yield from within_limit(article)` line) reproduces
  exactly as printed, so only the second claim is wrong.
- **Suggested fix:** replace the colon clause with the diagnostic that actually
  comes next, e.g. "`report()` fails at its own `yield from` with the same
  `invalid-yield`, and once you widen `catch()` and the annotation to match,
  `assert_never()` then reports `TooLong` as an unhandled branch."

### 2. Solution 9's "a fifth attempt would raise a `StopIteration`" does not happen

- **Severity:** wrong
- **Where:** `Solutions/47_Effects--Stateless_in_Practice.md:915`
- **Solution says:** "A fifth attempt would raise a `StopIteration` from
  `read()`."
- **What actually happens:** the effect ends silently and `run()` returns `None`.
  Using the solution's own `reading()`/`recording()` handlers with the same
  four-balance script and a fifth price:

  ```
  $ uv run python work_ex9b.py
  NO EXCEPTION; run() returned None [40, 10]
  ```

  (Caught with a bare `except BaseException`, so nothing was swallowed by my
  test.) The exhausted iterator's `StopIteration` propagates into the generator
  machinery driving the Effect and terminates it, so `spree()`'s `return bought`
  never runs and the count is lost rather than reported.
- **Suggested fix:** either state what happens ("a fifth attempt exhausts the
  iterator, the Effect ends early, and `run()` returns `None` instead of a
  count — a silent truncation, which is the reason the final `next(balances,
  None) is None` assertion is worth writing") or drop the sentence. The
  surrounding argument does not depend on it.

### 3. Exercise 8's literal edit fails, and chapter 47 never gives the missing fact

- **Severity:** drift
- **Where:** `Chapters/47_Effects--Stateless_in_Practice.md:2192-2195` (and the
  body claim at line 1778)
- **Exercise says:** "Change `parallel.py` to use a `ProcessPoolExecutor`
  instead of a `ThreadPoolExecutor`, and confirm `squares()` stays unchanged."
- **What actually happens:** performing exactly that edit on `parallel.py`
  (swap the import and the constructor, change nothing else) dies on Windows in
  a cascade of `BrokenProcessPool` / `Process ... terminated abruptly with exit
  code 1` messages, dozens of lines long, because `parallel.py`'s driver code
  sits at module level and each spawned worker re-imports the module and builds
  another pool. Adding `if __name__ == "__main__":` around the module-level
  block fixes it, and `squares()` is then unchanged character for character:

  ```
  $ uv run python ex8b.py
  [0, 1, 4, 9, 16]
  under 150ms: False 0.27144559999999274
  ```

  Chapter 47 never mentions the guard. Its own sentence on the subject (line
  1778) is "Supplying a `ProcessPoolExecutor` instead moves the same work into
  processes, with no change to `squares()`", which is true about `squares()` and
  silent about the change the file does need. The fact lives in chapter 19
  (`Chapters/19_Techniques--Concurrency.md:838`), which is prior material, so a
  reader who remembers it recovers; a reader who does not gets a failure that
  looks like a bug in Stateless. The Solutions listing does carry the guard, with
  the comment `# Required: workers re-import this module`, so the chapter and the
  solution disagree about what the exercise costs.
- **Solution does:** section 8 has the guard and explains it in prose, and drops
  the timing print entirely.
- **Suggested fix:** either add half a sentence to the exercise ("the module-level
  block will need an `if __name__ == \"__main__\":` guard") or to line 1779. Note
  also that the timing boolean flips: five 50 ms tasks take about 0.27 s under a
  process pool, so `elapsed < 0.15` becomes `False`. The exercise does not ask
  about timing, so this is context, not a second defect.

### 4. Solution 12 quotes a `ValueError` message the library does not print

- **Severity:** minor
- **Where:** `Solutions/47_Effects--Stateless_in_Practice.md:1141-1145`
- **Solution says (in a ```text block):**
  "ValueError: Not enough annotated arguments to handler function 'scripted'.
  Expected 1, got 0. 'handle' uses type annotations to match handlers with
  abilities, so the argument to 'scripted' must be annotated."
- **What actually happens:** deleting the annotation from `scripted`'s parameter
  in the solution's own `exercise_12.py` gives:

  ```
  ValueError: Not enough annotated arguments to handler function
  '<function scripted_from.<locals>.scripted at 0x000001D68263D2D0>'.
  Expected 1, got 0. 'handle' uses type annotations to match handlers with
  abilities, so the argument to
  '<function scripted_from.<locals>.scripted at 0x000001D68263D2D0>'
  must be annotated.
  ```

  `handler.py:117` interpolates `f"{f}"`, so the message carries the full
  function repr in both slots, not a bare name. The difference is more than a
  stripped memory address: the qualified `scripted_from.<locals>.scripted` is
  what a reader would try to match against.
- **Suggested fix:** quote the message as printed (an elided address is fine), or
  introduce the block as a paraphrase rather than tool output. The rest of the
  section is correct: I confirmed `handle()` calls `get_type_hints()` and raises
  at decoration time, and that deleting `low: int` from the accessor changes
  nothing in the file but silences `error[invalid-argument-type]` at
  `roll("a", 6)` in a caller.
