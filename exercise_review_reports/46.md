### 4. Exercise 11's stated outcome does not hold for the ambiguity it just had the reader create

- **Severity:** drift
- **Where:** `Chapters/46_Effects--Stateless.md:1786-1792`;
  `Solutions/46_Effects--Stateless.md:742-828`
- **Exercise says:** "Add a third implementation and predict … which of the six
  orderings send Alice's greeting where. Then follow the section's advice: give
  the two recording implementations a method name the screen one does not have,
  declare each as its own `Protocol`, and show that the ambiguity is now a type
  error rather than a silent choice."
- **What actually happens:** the six-ordering half is correct and reproducible
  (first argument always wins; two orderings go to the screen, two to each
  recorder). The fix half only removes the screen-vs-recorder ambiguity. Two
  recorders that share the `record()` name, declared as two separate
  `Protocol`s, are structurally identical, so they still satisfy each other and
  still resolve by argument order with no diagnostic. Reproduced: two `record()`
  implementations supplied in each order, `ty` reports "All checks passed!", and
  the output flips with the order:

  ```text
  ['Hello, Alice!'] []
  ['Hello, Alice!'] ['Hello, Bob!']
  ```
- **Solution does:** drops the third implementation entirely — `exercise_11.py`
  declares only `Terminal` and `Capture` — and then contradicts the exercise's
  claim in prose: "Add a second recorder, an `Audit` that also defines
  `record()`, and `supply(capture, audit)` is ambiguous again by argument order,
  with no diagnostic" (`Solutions/…:817-822`).
- **Suggested fix:** judgment call. Either narrow the exercise's claim ("show
  that the screen/recorder ambiguity is now a type error, and say what happens to
  the two recorders") or drop the "third implementation" from the second half so
  the exercise and the solution's listing describe the same program.

### 5. Exercise 6's "Run it against `greet()`" fails on the `greet()` in the file the exercise names

- **Severity:** minor
- **Where:** `Chapters/46_Effects--Stateless.md:1746-1749`
- **Exercise says:** "`default_console.py` defaults by supplying an instance.
  Write the other kind of default, one that builds whatever the request names.
  … a function annotated `Need[Console]` and returning `ability.t()` hands back a
  default-constructed instance of the requested class. Run it against `greet()`
  and confirm the greeting prints."
- **What actually happens:** `default_console.py`'s `Console` is
  `@dataclass class Console: tag: str`, so `ability.t()` cannot construct it.
  Taking that file's `greet()` (the nearest antecedent):

  ```text
  TypeError: Console.__init__() missing 1 required positional argument: 'tag'
  ```

  With `greeter.py`'s zero-field `Console` the exercise works exactly as
  described; I confirmed the full exercise (handler answers `Need[Log]` at
  runtime, `ty` sees a leftover `Need[Log]` and demands a `# type: ignore`).
- **Solution does:** declares its own field-free `@dataclass class Console`, so
  it never meets the problem.
- **Suggested fix:** name the file, e.g. "Run it against `greeter.py`'s
  `greet()`", or say the default-constructed class must take no arguments.

### 6. Exercise 10 cannot trigger its `ValueError` from the chapter's own data

- **Severity:** minor
- **Where:** `Chapters/46_Effects--Stateless.md:1778-1785`
- **Exercise says:** "a helper that formats the score and raises a `ValueError`
  on a negative one … then run it on a name that triggers each failure and on one
  that succeeds"
- **What actually happens:** `announce()` gets its value from `scores.py`'s
  `SCORES = {"Alice": 42, "Bob": 7}`, which holds no negative score, so no name
  reaches the `ValueError` path. The reader must add data the exercise never
  mentions. Working the exercise required `SCORES["Dave"] = -1` before the three
  outcomes appeared (`Alice: 42`, `KeyError: 'Carol'`, `ValueError: negative
  score for Dave`).
- **Solution does:** silently redefines the scoreboard as
  `{"Alice": 42, "Bob": 7, "Cyd": -3}` in `exercise_10.py`.
- **Suggested fix:** add "adding a negative entry to `SCORES`" (or "with a
  scoreboard of your own that has a negative score") to the exercise.

### 7. Exercise 9's import of `stateless_coroutine.py` prints an unrelated line

- **Severity:** minor
- **Where:** `Chapters/46_Effects--Stateless.md:1771-1777`
- **Exercise says:** "Write `report_all()`, which calls
  `stateless_coroutine.py`'s `report()` for three URLs"
- **What actually happens:** `stateless_coroutine.py` runs
  `print(run(report("http://example.com")))` at module level with no
  `if __name__ == "__main__":` guard, so `from stateless_coroutine import report`
  emits a line before the reader's own program produces anything:

  ```text
  body = 'fetched http://example.com', len(body) = 26
  RuntimeError: asyncio.run() cannot be called from a running event loop
  body = 'fetched http://a.com', len(body) = 20
  …
  ```
- **Solution does:** redefines `fetch()` and `report()` locally in
  `exercise_9.py` (consistent with the Solutions preamble), so it never imports
  the chapter listing and never sees this.
- **Suggested fix:** either note that the reader will see the imported module's
  own output, or reword to "copy `stateless_coroutine.py`'s `report()`".
