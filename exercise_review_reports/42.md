## Findings

### 1. Exercise 3 asks for `Result[str, list[str]]`; the solution returns something else, and its reason for doing so is false under ty 0.0.75

- **Severity:** wrong
- **Where:** `Chapters/42_Functional--Error_Handling.md:724-726`,
  `Solutions/42_Functional--Error_Handling.md:182` (signature) and
  `:222-231` (the justification)
- **Exercise says:** "Rewrite `combined` so it collects all the failures
  instead of stopping at the first one, returning `Result[str, list[str]]`."
- **Solution does:** defines three new concrete classes (`IntResult`,
  `ErrorResult`, `MultiErrorResult`), drops `Ok`/`Err`/`Result`
  entirely, and declares `def combined(i: int, j: int) -> str |
  MultiErrorResult`. It justifies that with: "Reusing one generic
  `Ok[A]`/`Err[E]` pair for both asks a type checker to recover a type
  parameter from a plain `isinstance()` check, and Python's runtime type
  erasure makes that recovery impossible in general. `ty` reports that
  gap as an error."
- **What actually happens:** `ty` 0.0.75 (`uv run ty --version` →
  `ty 0.0.75 (a553dcc1a 2026-08-26)`) narrows exactly that pattern and
  reports no error. Written with the chapter's own `result.py` and the
  exercise's declared return type:

  ```python
  def combined(i: int, j: int) -> Result[str, list[str]]:
      a, b, c = func_a(i), func_b(j), func_c(i + j)
      errors = [r.error for r in (a, b, c)
                if isinstance(r, Err)]
      if errors:
          return Err(errors)
      assert isinstance(a, Ok)
      assert isinstance(b, Ok)
      assert isinstance(c, Ok)
      return Ok(add(a.answer, b.answer, c.answer))
  ```

  `uv run python ex3e.py` prints
  `(7, 5) Ok(answer='add(7 + 5 + 12): 24')`,
  `(1, 5) Err(error=['func_a(1)'])`,
  `(1, 2) Err(error=['func_a(1)', 'func_b(2)', 'func_c(3): division by zero'])`.
  `uv run ty check ex3e.py` → `All checks passed!`;
  `uv run ruff check --line-length 60 ex3e.py` → `All checks passed!`,
  and no line exceeds 60 columns. A `reveal_type` probe confirms the
  narrowing directly: `[r.error for r in (a, b, c) if isinstance(r,
  Err)]` reveals as `list[str]`, and `a.answer` after `isinstance(a,
  Ok)` reveals as `int`. The three `assert isinstance` lines are not
  even required; a comprehension form without them also passes.
- **Suggested fix:** rewrite solution 3 to use `Ok`/`Err` and return
  `Result[str, list[str]]` as the exercise asks, and delete the
  type-erasure paragraph (`:222-231`), which is no longer true. If the
  concrete-class version is kept for some other reason, the exercise's
  stated return type must change to match, and the `ty` claim still has
  to go.

### 2. Exercise 6's two-part question has an empty half under every reading, and the solution rewrites more than the exercise asks

- **Severity:** wrong
- **Where:** `Chapters/42_Functional--Error_Handling.md:733-735`,
  `Solutions/42_Functional--Error_Handling.md:389-432`
- **Exercise says:** "Rewrite `func_a()` to return `int | None` instead
  of `Result[int, str]` and adjust `composing.py` to match. Which of the
  three failures in the chain can the caller still tell apart, and which
  have collapsed into each other?"
- **What actually happens:** doing literally what the sentence says
  (convert `func_a()` only, leave `func_b()` and `func_c()` returning
  `Result`) collapses nothing. My `composed()` returns
  `Result[int, str] | None` and `uv run python ex6.py` prints:

  ```
  0 Ok(answer=0)
  1 None
  2 Err(error='func_b(2)')
  3 Err(error='func_c(3): division by zero')
  4 Ok(answer=4)
  ```

  (`uv run ty check ex6.py` → `All checks passed!`) All three failures
  stay distinguishable, so the "which have collapsed into each other"
  half has no answer. The only reading that produces a collapse is to
  make `composed()` itself return `int | None`, which forces
  `func_b()`'s and `func_c()`'s failures to `None` as well — and then
  *all three* collapse, so the "which can the caller still tell apart"
  half has no answer. Either way one half of the question is empty.
- **Solution does:** takes the second reading and goes further than the
  exercise's wording, rewriting `func_a()`, `func_b()`, *and*
  `func_c()` to `int | None`, then answering only one half: "All three
  failures have collapsed into each other."
- **Suggested fix:** make the exercise say what the solution does and
  ask the single question it answers, e.g. "Rewrite `func_a()`,
  `func_b()`, and `func_c()` to return `int | None` and adjust
  `composing.py` to match. What can the caller still tell about which of
  the three steps failed?" (An alternative that keeps the two-part
  question: convert `func_a()` and `func_b()` only, leaving `func_c()`
  on `Result` — then `func_a`'s and `func_b`'s failures really have
  collapsed and `func_c`'s is still distinguishable. That is a larger
  rewrite of both halves.)

### 3. Exercise 1 asks to confirm short-circuiting that the solution's arrangement cannot show

- **Severity:** minor
- **Where:** `Chapters/42_Functional--Error_Handling.md:717-719`,
  `Solutions/42_Functional--Error_Handling.md:57` and `:68-75`
- **Exercise says:** "extend the `bind()` chain in
  `composing_with_bind.py` to include it. Confirm an `Err` from
  `func_e()` still short-circuits."
- **What actually happens:** appending `func_e` (the natural reading of
  "extend the chain") makes it the last step, so an `Err` it produces
  has nothing left to skip. Short-circuiting *is* observable if
  `func_e` goes in the middle; `uv run python ex1.py` with
  `func_a(i).bind(func_b).bind(func_e).bind(func_c)` prints
  `4 Err(error='func_e(4)')`, with `func_c` never reached.
- **Solution does:** appends `func_e` at the end
  (`Solutions/...md:57`) and its prose concedes the point: "`func_e` is
  the last step, so that `Err` travels no further." It then confirms a
  different claim, that earlier failures short-circuit *before*
  `func_e`.
- **Suggested fix:** reword the exercise to what the solution actually
  demonstrates, e.g. "Confirm that a failure earlier in the chain
  short-circuits before `func_e()` runs" — or ask for `func_e()` in the
  middle of the chain, which makes the original sentence true.
