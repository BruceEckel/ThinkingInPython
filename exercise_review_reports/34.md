## Findings

### 1. Solution 5 silently rewrites `to_infix()` to drop all parentheses, so its printed output cannot be reproduced with the chapter's `infix.py`

- **Severity:** drift
- **Where:** `Chapters/34_Patterns--Composite_and_Interpreter.md:664` (exercise 5),
  `Solutions/34_Patterns--Composite_and_Interpreter.md:362-372` and `:415-418`
- **Exercise says:** "Write `derivative(e, name)` ... Run its results through
  `simplify()` and compare."
- **What actually happens:** The exercise sends the reader to the chapter's own
  `simplify()` and (implicitly) its own `to_infix()`. `exercise_5.py` carries a
  copy of `to_infix()` with the parentheses removed
  (`return f"{to_infix(left)} + {to_infix(right)}"` instead of the chapter's
  `f"({to_infix(left)} + {to_infix(right)})"`), and also drops the chapter's
  `case _: assert_never(e)`. Nothing in the exercise or the solution's prose
  mentions the change. Running the same `derivative()` against the chapter's
  unmodified `infix.py` and `simplify.py`:

  ```
  $ uv run python ex5chapter.py
  ((1 * x) + (x * 1))
  (x + x)
  ```

  The solution prints `1 * x + x * 1` / `x + x`. A reader who does the exercise
  as written gets output that does not match the solution's markers, in a
  chapter whose exercise 4 opens by stating that `to_infix()` parenthesizes
  every operation.
- **Solution does:** shows the paren-free rendering with no note that it changed
  `to_infix()`.
- **Suggested fix:** either restore the chapter's `to_infix()` in
  `exercise_5.py` and update the two markers to `((1 * x) + (x * 1))` /
  `(x + x)`, or add one sentence to solution 5 saying it uses a paren-free
  `to_infix()` for readability (exercise 4's version would also do).

### 2. Solution 6 rewrites `__add__()` and `__mul__()`, which exercise 6 does not ask for and the solution's prose never mentions

- **Severity:** drift
- **Where:** `Chapters/34_Patterns--Composite_and_Interpreter.md:668-672`,
  `Solutions/34_Patterns--Composite_and_Interpreter.md:447-465`
- **Exercise says:** "Rewrite `__radd__()` and `__rmul__()` to return
  `NotImplemented` for a non-`int` operand ... and confirm `"a" + x` now raises a
  `TypeError`."
- **What actually happens:** Rewriting only the two named methods is sufficient
  for the stated outcome. I copied `expr.py`, added
  `if not isinstance(other, int): return NotImplemented` to `__radd__()` and
  `__rmul__()` only, and got:

  ```
  $ uv run python check.py
  + TypeError: can only concatenate str (not "Var") to str
  * TypeError: can't multiply sequence by non-int of type 'Var'
  2*x+1 -> Add(left=Mul(left=Num(value=2), right=Var(name='x')), right=Num(value=1))
  ```
- **Solution does:** additionally guards `__add__()` and `__mul__()` with
  `if isinstance(other, Operators | int)`. The explanation paragraphs discuss
  only `__radd__()`. This is the chapter-10-exercise-5 shape: the exercise names
  two edits, the solution makes four.
- **Suggested fix:** smallest is to add a sentence to the solution noting that
  `__add__()`/`__mul__()` get the same guard because `x + "a"` is the mirror
  hole (`wrap()` passes a non-`int` straight through). Alternatively widen the
  exercise to name the four operator methods.

### 3. Exercise 3 asks for three updates; solution 3 supplies code for one and adds an operator the exercise did not name

- **Severity:** drift
- **Where:** `Chapters/34_Patterns--Composite_and_Interpreter.md:657-660`,
  `Solutions/34_Patterns--Composite_and_Interpreter.md:128-231`
- **Exercise says:** "Add `Neg` ... and `Div` ... along with `__neg__()` and
  `__truediv__()` operator methods. Update `evaluate()`, `to_infix()`, and
  `simplify()`."
- **What actually happens:** `exercise_3.py` implements `evaluate()` only. The
  `to_infix()` cases appear as two inline f-string fragments in prose and
  `simplify()`'s new cases are described in words with no code. The solution
  also defines `__rtruediv__()`, which the exercise does not name. Solution 5
  acknowledges the gap ("the same way exercise 3 leaves `to_infix()`'s and
  `simplify()`'s new cases to prose rather than code"), so this is deliberate,
  but the exercise asks for three updates and gets one.
- **Suggested fix:** either add the `Neg`/`Div` cases to `to_infix()` and
  `simplify()` in `exercise_3.py`, or soften the exercise to "Update
  `evaluate()`, and say what `to_infix()` and `simplify()` need."

### 4. Exercise 4 asks for "only the parentheses that precedence requires"; solution 4 deliberately emits some it does not

- **Severity:** minor
- **Where:** `Chapters/34_Patterns--Composite_and_Interpreter.md:661-663`,
  `Solutions/34_Patterns--Composite_and_Interpreter.md:307-317`
- **Exercise says:** "Rewrite it to emit only the parentheses that precedence
  requires".
- **What actually happens:** the `prec + 1` rule for the right operand adds
  parentheses at equal precedence. Reproduced against the solution's own
  `to_infix()`:

  ```
  $ uv run python probe4.py
  x + (x + 1)
  x * (x * 2)
  x + 1 + x
  ```

  Both of the exercise's own examples pass, and the solution states the
  deviation and justifies it, so this is a wording mismatch rather than a wrong
  solution.
- **Suggested fix:** relax the exercise's goal sentence to "emit only the
  parentheses that meaning requires" (which the solution does satisfy), leaving
  the two worked examples as the acceptance test.

## Notes

- **Solution 2's paraphrase of the `ty` message is slightly off.** It says "`ty`
  reports that `entry` (or `e`) could be a `Symlink` that no case handles." The
  real output names `entry` at both sites and never `e`; the message is
  `error[type-assertion-failure]: Argument does not have asserted type 'Never' /
  Inferred type of argument is 'Symlink & ~File & ~Directory'`. The substance
  (both operations get flagged) is correct.
- **Solution 7 escapes more than the three characters the exercise names.**
  Exercise 7 says "replaces `<`, `>`, and `&`"; the solution uses
  `html.escape()`, whose default `quote=True` also escapes `"` and `'`.
  Reproduced: a comment `a "quoted" & <b>` renders as
  `<p>a &quot;quoted&quot; &amp; &lt;b&gt;</p>`. Strictly safer and standard, so
  I did not raise it as a finding, but the two do not describe the same
  transformation.
- **In-process quirk, not a chapter defect.** Once a `RecursionError` has been
  caught in a process on this 3.15.0b3 build, a *deeper* subsequent recursion
  can succeed: in one process, depth 2000 raised while 3000 and 5000 then
  returned. Each depth raises reliably in a fresh process. `exercise_8.py` is
  unaffected (its only later `evaluate()` call is shallow), but a future listing
  that catches a `RecursionError` and then recurses again in the same process
  should not be trusted to fail twice.
