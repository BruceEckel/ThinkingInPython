## PEP 342 and its predecessors (PEP 288, PEP 325, PEP 340, PEP 343): why `send()`, `throw()`, and `close()` exist

### Takeaway
PEP 342 (Guido van Rossum and Phillip J. Eby, created 10 May 2005, Python 2.5) states two limitations of PEP 255 generators: a generator can send values out at a pause but cannot receive "values or exceptions" when it resumes, and it cannot pause inside `try/finally`, so "an aborted coroutine" cannot "clean up after itself".
`send()` and the yield expression answer the first limitation, and `throw()` answers it for exceptions.
`close()`, `GeneratorExit`, and `yield` inside `try/finally` answer the second.
The second half of that design came from the `with` statement work (PEP 340, then PEP 343), where `contextlib.contextmanager` needed a way to raise the block's exception inside the suspended generator.

**PEP 342 Motivation, complete and verbatim** ([PEP 342, Motivation](https://peps.python.org/pep-0342/#motivation)):

> Coroutines are a natural way of expressing many algorithms, such as simulations, games, asynchronous I/O, and other forms of event-driven programming or co-operative multitasking. Python's generator functions are almost coroutines -- but not quite -- in that they allow pausing execution to produce a value, but do not provide for values or exceptions to be passed in when execution resumes. They also do not allow execution to be paused within the `try` portion of `try/finally` blocks, and therefore make it difficult for an aborted coroutine to clean up after itself.
>
> Also, generators cannot yield control while other functions are executing, unless those functions are themselves expressed as generators, and the outer generator is written to yield in response to values yielded by the inner generator. This complicates the implementation of even relatively simple use cases like asynchronous communications, because calling any functions either requires the generator to *block* (i.e. be unable to yield control), or else a lot of boilerplate looping code must be added around every needed function call.
>
> However, if it were possible to pass values or exceptions *into* a generator at the point where it was suspended, a simple co-routine scheduler or *trampoline function* would let coroutines *call* each other without blocking -- a tremendous boon for asynchronous applications. Such applications could then write co-routines to do non-blocking socket I/O by yielding control to an I/O scheduler until data has been sent or becomes available. Meanwhile, code that performs the I/O would simply do something like this:
>
>     data = (yield nonblocking_read(my_socket, nbytes))
>
> in order to pause execution until the `nonblocking_read()` coroutine produced a value.
>
> In other words, with a few relatively minor enhancements to the language and to the implementation of the generator-iterator type, Python will be able to support performing asynchronous operations without needing to write the entire application as a series of callbacks, and without requiring the use of resource-intensive threads for programs that need hundreds or even thousands of co-operatively multitasking pseudothreads. Thus, these enhancements will give standard Python many of the benefits of the Stackless Python fork, without requiring any significant modification to the CPython core or its APIs. In addition, these enhancements should be readily implementable by any Python implementation (such as Jython) that already supports generators.

- The limitations the Motivation lists: (1) no values or exceptions passed in on resume; (2) no pause inside the `try` of `try/finally`, so no cleanup for an aborted coroutine; (3) a generator cannot yield control while a called function runs unless that function is also a generator and the caller re-yields its values (the problem PEP 380 later solved). ([PEP 342, Motivation](https://peps.python.org/pep-0342/#motivation))
- The use cases it names: "simulations, games, asynchronous I/O, and other forms of event-driven programming or co-operative multitasking"; "non-blocking socket I/O"; and the two alternatives it rejects, "the entire application as a series of callbacks" and "resource-intensive threads". ([PEP 342, Motivation](https://peps.python.org/pep-0342/#motivation))

**PEP 342 Specification Summary, verbatim (items 1 to 6)** ([PEP 342, Specification Summary](https://peps.python.org/pep-0342/#specification-summary)):
- "1. Redefine `yield` to be an expression, rather than a statement. The current yield statement would become a yield expression whose value is thrown away. A yield expression's value is `None` whenever the generator is resumed by a normal `next()` call."
- "2. Add a new `send()` method for generator-iterators, which resumes the generator and *sends* a value that becomes the result of the current yield-expression. The `send()` method returns the next value yielded by the generator, or raises `StopIteration` if the generator exits without yielding another value."
- "3. Add a new `throw()` method for generator-iterators, which raises an exception at the point where the generator was paused, and which returns the next value yielded by the generator, raising `StopIteration` if the generator exits without yielding another value. (If the generator does not catch the passed-in exception, or raises a different exception, then that exception propagates to the caller.)"
- "4. Add a `close()` method for generator-iterators, which raises `GeneratorExit` at the point where the generator was paused. If the generator then raises `StopIteration` (by exiting normally, or due to already being closed) or `GeneratorExit` (by not catching the exception), `close()` returns to its caller. If the generator yields a value, a `RuntimeError` is raised. If the generator raises any other exception, it is propagated to the caller. `close()` does nothing if the generator has already exited due to an exception or normal exit."
- "5. Add support to ensure that `close()` is called when a generator iterator is garbage-collected."
- "6. Allow `yield` to be used in `try/finally` blocks, since garbage collection or an explicit `close()` call would now allow the `finally` clause to execute."

**Why `yield` became an expression**
- PEP 342 gives no separate rationale section; the reason follows from the Motivation (a value must arrive "at the point where it was suspended"). Its explanation of the result, verbatim: "In effect, a yield-expression is like an inverted function call; the argument to yield is in fact returned (yielded) from the currently executing function, and the *return value* of yield is the argument passed in via `send()`." ([PEP 342, New syntax: Yield Expressions](https://peps.python.org/pep-0342/#new-syntax-yield-expressions))
- On a bare `yield`, verbatim: "Note that a yield-statement or yield-expression without an expression is now legal. This makes sense: when the information flow in the `next()` call is reversed, it should be possible to yield without passing an explicit value (`yield` is of course equivalent to `yield None`)." ([PEP 342](https://peps.python.org/pep-0342/#new-syntax-yield-expressions))
- On priming, verbatim: "Because generator-iterators begin execution at the top of the generator's function body, there is no yield expression to receive a value when the generator has just been created. Therefore, calling `send()` with a non-`None` argument is prohibited when the generator iterator has just started, and a `TypeError` is raised if this occurs (presumably due to a logic error of some kind). Thus, before you can communicate with a coroutine you must first call `next()` or `send(None)` to advance its execution to the first yield expression." ([PEP 342, New generator method: send(value)](https://peps.python.org/pep-0342/#new-generator-method-send-value))
- Ruby comparison, verbatim: "Note: the syntactic extensions to yield make its use very similar to that in Ruby. This is intentional." ([PEP 342](https://peps.python.org/pep-0342/#new-syntax-yield-expressions))
- "What's New in Python 2.5" (A.M. Kuchling) states the before-and-after, verbatim: "As introduced in Python 2.3, generators only produce output; once a generator's code was invoked to create an iterator, there was no way to pass any new information into the function when its execution is resumed. Sometimes the ability to pass in some information would be useful. Hackish solutions to this include making the generator's code look at a global variable and then changing the global variable's value, or passing in some mutable object that callers then modify." ([What's New in Python 2.5, PEP 342](https://docs.python.org/3/whatsnew/2.5.html#pep-342-new-generator-features))
- Same document, verbatim: "The cumulative effect of these changes is to turn generators from one-way producers of information into both producers and consumers. Generators also become coroutines, a more generalized form of subroutines. Subroutines are entered at one point and exited at another point (the top of the function, and a `return` statement), but coroutines can be entered, exited, and resumed at many different points (the `yield` statements). We'll have to figure out patterns for using coroutines effectively in Python." ([What's New in Python 2.5](https://docs.python.org/3/whatsnew/2.5.html#pep-342-new-generator-features))
- Release date, verbatim: "Python 2.5 was released on September 19, 2006." ([What's New in Python 2.5](https://docs.python.org/3/whatsnew/2.5.html))

**`throw()`: semantics and name**
- Verbatim: "In summary, `throw()` behaves like `next()` or `send()`, except it raises an exception at the suspension point. If the generator is already in the closed state, `throw()` just raises the exception it was passed without executing any of the generator's code." ([PEP 342, New generator method: throw()](https://peps.python.org/pep-0342/#new-generator-method-throw-type-value-none-traceback-none))
- Name, verbatim: "Unlike `raise` (which immediately raises an exception from the current execution point), `throw()` first resumes the generator, and only then raises the exception. The word *throw* is suggestive of putting the exception in another location, and is already associated with exceptions in other languages." ([PEP 342](https://peps.python.org/pep-0342/#new-generator-method-throw-type-value-none-traceback-none))

**`close()` and `GeneratorExit`**
- `close()` is defined as `throw(GeneratorExit)` plus a check, verbatim pseudo-code: `def close(self): try: self.throw(GeneratorExit) except (GeneratorExit, StopIteration): pass else: raise RuntimeError("generator ignored GeneratorExit")  # Other exceptions are not caught`. ([PEP 342, New generator method: close()](https://peps.python.org/pep-0342/#new-generator-method-close))
- Verbatim: "A new standard exception is defined, `GeneratorExit`, inheriting from `Exception`. A generator should handle this by re-raising it (or just not catching it) or by raising `StopIteration`." ([PEP 342](https://peps.python.org/pep-0342/#new-standard-exception-generatorexit)) (Note: the PEP text says `Exception`; `GeneratorExit` was later moved under `BaseException`, a change outside this note's sources: unverified here.)
- Why `RuntimeError` when a closed generator yields, Guido verbatim: "I originally chose `TypeError` because it represents gross misbehavior of the generator function, which should be fixed by changing the code. ... I'd rather not introduce a new exception class just for this purpose, since it's not an exception that I want people to catch: I want it to turn into a traceback which is seen by the programmer who then fixes the code." ([PEP 342, Open Issues](https://peps.python.org/pep-0342/#open-issues))
- Garbage collection, verbatim: "`g.__del__()` is a wrapper for `g.close()`. This will be called when the generator object is garbage-collected (in CPython, this is when its reference count goes to zero)." ([PEP 342, New generator method: __del__()](https://peps.python.org/pep-0342/#new-generator-method-del))
- Link to PEP 343, verbatim: "This allows other code to potentially use `close()` in a `try/finally` or `with` block (per PEP 343) to ensure that a given generator is properly finalized." ([PEP 342](https://peps.python.org/pep-0342/#new-generator-method-del))

**Why `close()`, `throw()`, and `try/finally` arrived together: the PEP 343 chain of reasoning**
- Guido proposed `throw()`, `GeneratorExit`, and `close()` as one package on python-dev, 18 May 2005, subject "Combining the best of PEP 288 and PEP 325: generator exceptions and cleanup". Verbatim: "I believe that in the discussion about PEP 343 vs. Nick's PEP 3XX ... the main difference is that Nick proposes a way to inject an exception into a generator; and I've said a few times that I like that idea. I'd like to propose to make that a separate PEP, which can combine elements of PEP 288 and PEP 325." And: "There's a new exception, GeneratorExit, which can be thrown to cause a generator to clean up. A generator should not yield a value in response to this exception." And: "That's it! With this, we can write the decorator from Nick's PEP 3XX and the generator examples in PEP 343 can be rewritten to have a try/finally clause around the yield statement." ([Guido van Rossum, python-dev, 2005-05-18](https://mail.python.org/pipermail/python-dev/2005-May/053885.html))
- In that same post, "PEP 342" still names a different proposal: "PEP 342 ("continue EXPR") already implies that". PEP 342 was merged with these ideas afterward. ([same post](https://mail.python.org/pipermail/python-dev/2005-May/053885.html))
- PEP 343 (Guido van Rossum and Alyssa Coghlan, created 13 May 2005, Python 2.5), Introduction, verbatim: "After a lot of discussion about PEP 340 and alternatives, I decided to withdraw PEP 340 and proposed a slight variant on PEP 310. After more discussion, I have added back a mechanism for raising an exception in a suspended generator using a `throw()` method, and a `close()` method which throws a new GeneratorExit exception; these additions were first proposed on python-dev in [2] and universally approved of." ([PEP 343, Introduction](https://peps.python.org/pep-0343/#introduction))
- PEP 343 Motivation and Summary, the step-by-step derivation, verbatim: "Additional discussion showed that people really liked being able to "see" the exception in the generator, even if it was only to log it; the generator is not allowed to yield another value, since the with-statement should not be usable as a loop (raising a different exception is marginally acceptable). To enable this, a new `throw()` method for generators is proposed, which takes one to three arguments representing an exception in the usual fashion (type, value, traceback) and raises it at the point where the generator is suspended. Once we have this, it is a small step to proposing another generator method, `close()`, which calls `throw()` with a special exception, `GeneratorExit`. This tells the generator to exit, and from there it's another small step to proposing that `close()` be called automatically when the generator is garbage-collected. Then, finally, we can allow a yield-statement inside a try-finally statement, since we can now guarantee that the finally-clause will (eventually) be executed." ([PEP 343, Motivation and Summary](https://peps.python.org/pep-0343/#motivation-and-summary))
- PEP 343 on why generators as templates survived PEP 340's rejection, verbatim: "I had one idea left from the PEP 340 euphoria that I wasn't ready to drop: using generators as "templates" for abstractions like acquiring and releasing a lock or opening and closing a file is a powerful idea, as can be seen by looking at the examples in that PEP." ([PEP 343](https://peps.python.org/pep-0343/#motivation-and-summary))
- PEP 343, verbatim: "With PEP 342 accepted, it is possible to write a decorator that makes it possible to use a generator that yields exactly once to control a with-statement." ([PEP 343, Generator Decorator](https://peps.python.org/pep-0343/#generator-decorator))
- PEP 343 on the `__exit__()` return value, verbatim: "The main use case for swallowing exceptions is to make it possible to write the `@contextmanager` decorator so that a try/except block in a decorated generator behaves exactly as if the body of the generator were expanded in-line at the place of the with-statement." ([PEP 343](https://peps.python.org/pep-0343/))
- "What's New in Python 2.5", verbatim: "This seems like a minor bit of language trivia, but using generators and `try...finally` is actually necessary in order to implement the `with` statement described by PEP 343." ([What's New in Python 2.5](https://docs.python.org/3/whatsnew/2.5.html#pep-342-new-generator-features))

**The trampoline example**
- The Motivation introduces the term, verbatim: "a simple co-routine scheduler or *trampoline function* would let coroutines *call* each other without blocking". ([PEP 342, Motivation](https://peps.python.org/pep-0342/#motivation))
- Example 3, the text the PEP gives for what the example shows, verbatim: "A simple co-routine scheduler or *trampoline* that lets coroutines *call* other coroutines by yielding the coroutine they wish to invoke. Any non-generator value yielded by a coroutine is returned to the coroutine that *called* the one yielding the value. Similarly, if a coroutine raises an exception, the exception is propagated to its *caller*. In effect, this example emulates simple tasklets as are used in Stackless Python, as long as you use a yield expression to invoke routines that would otherwise *block*. This is only a very simple example, and far more sophisticated schedulers are possible. (For example, the existing GTasklet framework for Python (http://www.gnome.org/~gjc/gtasklet/gtasklets.html) and the peak.events framework (http://peak.telecommunity.com/) already implement similar scheduling capabilities, but must currently use awkward workarounds for the inability to pass values or exceptions into generators.)" ([PEP 342, Examples](https://peps.python.org/pep-0342/#examples))
- The code is a class `Trampoline` with docstring `"""Manage communications between coroutines"""`, a `collections.deque` queue, and a `schedule(self, coroutine, stack=(), val=None, *exc)` method. Its `resume()` calls `coroutine.throw(value,*exc)` when an exception is pending, otherwise `coroutine.send(value)`. A yielded generator is treated as a call (comment: "Yielded to a specific coroutine, push the current one on the stack, and call the new one with no args"); any other yielded value is a return (comment: "Yielded a result, pop the stack and send the value to the caller"); an exception goes back to the caller (comment: `# send the error back to the "caller"`). ([PEP 342, Examples](https://peps.python.org/pep-0342/#examples))
- Example 4 runs many coroutines on one trampoline: an `echo_handler(sock)` that writes `data = yield nonblocking_read(sock)`, a `listen_on()` that calls `trampoline.add( handler(connected_socket) )` per connection, and the comment `# loop forever, accepting connections and servicing them` / `# "in parallel"` before `t.run()`. ([PEP 342, Examples](https://peps.python.org/pep-0342/#examples))
- Examples 1 and 2 are the consumer side: a `consumer` decorator that primes a generator "to its first yield point", and a `thumbnail_pager` that receives images through `(yield)` and, in `except GeneratorExit:`, flushes "any pending output" and closes the downstream consumer. The PEP: "Functions like this can be chained together to form efficient processing pipelines of *consumers* that each can have complex internal state". ([PEP 342, Examples](https://peps.python.org/pep-0342/#examples))
- PEP 342 dropped one feature from PEP 340, verbatim: "An earlier draft of this PEP proposed a new `continue EXPR` syntax for use in for-loops (carried over from PEP 340), that would pass the value of *EXPR* into the iterator being looped over. This feature has been withdrawn for the time being". ([PEP 342, Optional Extensions](https://peps.python.org/pep-0342/#optional-extensions))

### Inferences
- PEP 342's own words support the chapter's "driver" framing: its trampoline is a loop that answers each yielded value, treating a yielded generator as a call and any other value as a result to send back, and sending an exception back with `throw()`. The yield expression as an "inverted function call" is the PEP's phrase for the request-and-answer shape.
- The three methods have two different origins. `send()` (and the yield expression) comes from the coroutine and asynchronous I/O motive and from PEP 288's data-passing idea. `throw()`, `close()`, and `try/finally` around `yield` come from cleanup (PEP 325) and from the `with` statement, whose generator-based context manager had to deliver the block's exception at the `yield`. PEP 343 states the derivation as a chain: `throw()`, then `close()` as `throw(GeneratorExit)`, then `close()` on garbage collection, then `yield` inside `try/finally`.
- The PEP 342 Motivation's third limitation (a generator cannot yield while a called function runs, without boilerplate re-yield loops) is the problem PEP 380 solved four years later; the trampoline's explicit stack is the 2005 workaround for it.

### Gaps
- The python-dev thread in which "PEP 342" changed from "Enhanced Iterators" (`continue EXPR`) to "Coroutines via Enhanced Generators" was not read; the merge is documented here only by PEP 340's note and Guido's 2005-05-18 post.
- When `GeneratorExit` moved from `Exception` to `BaseException` was not checked against a primary source (unverified).

## Twisted's `deferredGenerator` and `inlineCallbacks`: cause or consequence of PEP 342?

### Takeaway
PEP 342 does not mention Twisted; it names GTasklet and peak.events as frameworks that "must currently use awkward workarounds".
Twisted's `deferredGenerator`/`waitForDeferred` is a workaround of that kind, written for generators that cannot receive values, and Twisted's own documentation says `inlineCallbacks` needs Python 2.5, so `inlineCallbacks` follows from PEP 342.

### Cited Findings
- Twisted 8.2.0 API docs for `deferredGenerator`, verbatim: "deferredGenerator and waitForDeferred help you write Deferred-using code that looks like a regular sequential function. If your code has a minimum requirement of Python 2.5, consider the use of inlineCallbacks instead, which can accomplish the same thing in a more concise manner." ([Twisted 8.2.0, twisted.internet.defer](https://twisted.org/documents/8.2.0/api/twisted.internet.defer.html))
- The workaround's shape, verbatim from the same page: `thing = waitForDeferred(makeSomeRequestResultingInDeferred())` / `yield thing` / `thing = thing.getResult()`, and "waitForDeferred returns something that you should immediately yield; when your generator is resumed, calling thing.getResult() will either give you the result of the Deferred if it was a success, or raise an exception if it was a failure. Calling getResult is absolutely mandatory. If you do not call it, your program will not work." Also: "Remember that 'return result' won't work; use 'yield result; return' in place of that." ([Twisted 8.2.0](https://twisted.org/documents/8.2.0/api/twisted.internet.defer.html))

### Inferences
- `deferredGenerator` shows what the missing `send()`/`throw()` cost: the generator yields a wrapper, and on resume it must fetch the result (or have the failure raised) by a separate `getResult()` call, and it cannot `return` a value. `inlineCallbacks` replaces each of those with `send()` (the result), `throw()` (the failure), and later a generator `return`.
- What the generator form fixed about callbacks, in Twisted's words, is that the code "looks like a regular sequential function".

### Gaps
- The Twisted release that introduced `deferredGenerator` (believed to be 2004 to 2005) and the one that introduced `inlineCallbacks` (believed to be Twisted 2.5, around early 2007) were not confirmed in a changelog: unverified.
- No statement by Twisted's authors that they lobbied for PEP 342 was found.

## PEP 380: why `yield from` and a generator's `return value` exist

### Takeaway
PEP 380 (Greg Ewing, created 13 February 2009, accepted June 2011, Python 3.3 released 29 September 2012) exists because code containing `yield` cannot be moved into a helper function the way other code can: the helper becomes a generator, and a re-yield loop forwards values but not `send()`, `throw()`, `close()`, or a result.
The generator `return value` exists so a subgenerator behaves like a function that returns a result, which is what "generators as threads" (and asyncio) need.

### Cited Findings
- Header: "Title: Syntax for Delegating to a Subgenerator", "Author: Gregory Ewing", "Status: Final", "Created: 13-Feb-2009", "Python-Version: 3.3", "Resolution: https://mail.python.org/pipermail/python-dev/2011-June/112010.html". ([PEP 380](https://peps.python.org/pep-0380/))
- Abstract, verbatim: "A syntax is proposed for a generator to delegate part of its operations to another generator. This allows a section of code containing 'yield' to be factored out and placed in another generator. Additionally, the subgenerator is allowed to return with a value, and the value is made available to the delegating generator. The new syntax also opens up some opportunities for optimisation when one generator re-yields values produced by another." ([PEP 380, Abstract](https://peps.python.org/pep-0380/#abstract))
- Motivation, complete and verbatim ([PEP 380, Motivation](https://peps.python.org/pep-0380/#motivation)):

> A Python generator is a form of coroutine, but has the limitation that it can only yield to its immediate caller. This means that a piece of code containing a `yield` cannot be factored out and put into a separate function in the same way as other code. Performing such a factoring causes the called function to itself become a generator, and it is necessary to explicitly iterate over this second generator and re-yield any values that it produces.
>
> If yielding of values is the only concern, this can be performed without much difficulty using a loop such as
>
>     for v in g:
>         yield v
>
> However, if the subgenerator is to interact properly with the caller in the case of calls to `send()`, `throw()` and `close()`, things become considerably more difficult. As will be seen later, the necessary code is very complicated, and it is tricky to handle all the corner cases correctly.
>
> A new syntax will be proposed to address this issue. In the simplest use cases, it will be equivalent to the above for-loop, but it will also handle the full range of generator behaviour, and allow generator code to be refactored in a simple and straightforward way.

- The forwarding rules, verbatim excerpts: "Any values that the iterator yields are passed directly to the caller." "Any values sent to the delegating generator using `send()` are passed directly to the iterator." "Exceptions other than GeneratorExit thrown into the delegating generator are passed to the `throw()` method of the iterator." "If a GeneratorExit exception is thrown into the delegating generator, or the `close()` method of the delegating generator is called, then the `close()` method of the iterator is called if it has one." "The value of the `yield from` expression is the first argument to the `StopIteration` exception raised by the iterator when it terminates." "`return expr` in a generator causes `StopIteration(expr)` to be raised upon exit from the generator." ([PEP 380, Proposal](https://peps.python.org/pep-0380/#proposal))
- The Formal Semantics expansion of `RESULT = yield from EXPR` is about 40 lines of Python with nested `try` blocks for `GeneratorExit`, `BaseException` (forwarded to `_i.throw`), and `StopIteration` (whose `.value` becomes the result). This is the "very complicated" code the Motivation refers to. ([PEP 380, Formal Semantics](https://peps.python.org/pep-0380/#formal-semantics))
- The Refactoring Principle, verbatim: "The rationale behind most of the semantics presented above stems from the desire to be able to refactor generator code. It should be possible to take a section of code containing one or more `yield` expressions, move it into a separate function (using the usual techniques to deal with references to variables in the surrounding scope, etc.), and call the new function using a `yield from` expression. The behaviour of the resulting compound generator should be, as far as reasonably practicable, the same as the original unfactored generator in all situations, including calls to `__next__()`, `send()`, `throw()` and `close()`." ([PEP 380, The Refactoring Principle](https://peps.python.org/pep-0380/#the-refactoring-principle))
- Accepted limits, verbatim: "A block of code that catches GeneratorExit without subsequently re-raising it cannot be factored out while retaining exactly the same behaviour." "Factored code may not behave the same way as unfactored code if a StopIteration exception is thrown into the delegating generator. With use cases for these being rare to non-existent, it was not considered worth the extra complexity required to support them." ([PEP 380](https://peps.python.org/pep-0380/#the-refactoring-principle))
- Generators as Threads, the reason for `return value`, verbatim: "A motivation for generators being able to return values concerns the use of generators to implement lightweight threads. When using generators in that way, it is reasonable to want to spread the computation performed by the lightweight thread over many functions. One would like to be able to call a subgenerator as though it were an ordinary function, passing it parameters and receiving a returned value." Then: "Using the proposed syntax, a statement such as `y = f(x)` where f is an ordinary function, can be transformed into a delegation call `y = yield from g(x)` where g is a generator. One can reason about the behaviour of the resulting code by thinking of g as an ordinary function that can be suspended using a `yield` statement." ([PEP 380, Generators as Threads](https://peps.python.org/pep-0380/#generators-as-threads))
- Same section, on exceptions and closing, verbatim: "Concerning `throw()` and `close()`, it is reasonable to expect that if an exception is thrown into the thread from outside, it should first be raised in the innermost generator where the thread is suspended, and propagate outwards from there; and that if the thread is terminated from outside by calling `close()`, the chain of active generators should be finalised from the innermost outwards." ([PEP 380](https://peps.python.org/pep-0380/#generators-as-threads))
- Same section, on routing values, verbatim: "The `yield from` expression allows the logic of the thread to be spread over as many functions as desired, with the production or consumption of items occurring in any subfunction, and the items are automatically routed to or from their ultimate source or destination." ([PEP 380](https://peps.python.org/pep-0380/#generators-as-threads))
- Why the value rides on `StopIteration`, verbatim: "Using a generalization of the StopIteration exception makes it easy for other kinds of iterators to participate in the protocol without having to grow an extra attribute or a close() method." "It simplifies the implementation, because the point at which the return value from the subgenerator becomes available is the same point at which the exception is raised." ([PEP 380, Use of StopIteration to return values](https://peps.python.org/pep-0380/#use-of-stopiteration-to-return-values))
- A rejected idea that clarifies `close()`'s role, verbatim: "This usage of close() and GeneratorExit would be incompatible with their current role as a bail-out and clean-up mechanism." And: "Signalling the end of values to a consumer is better addressed by other means, such as sending in a sentinel value or throwing in an exception agreed upon by the producer and consumer." ([PEP 380, Rejected Ideas](https://peps.python.org/pep-0380/#rejected-ideas))
- Optimisation, verbatim: "The overhead of passing `__next__()` calls and yielded values down and up the chain can cause what ought to be an O(n) operation to become, in the worst case, O(n**2)." ([PEP 380, Optimisations](https://peps.python.org/pep-0380/#optimisations))
- Syntax, verbatim: "The particular syntax proposed has been chosen as suggestive of its meaning, while not introducing any new keywords and clearly standing out as being different from a plain `yield`." ([PEP 380, Syntax](https://peps.python.org/pep-0380/#syntax))
- Acceptance. The PEP says "Guido officially accepted the PEP on 26th June, 2011" and links a message dated "Sat Jun 25 18:44:36 CEST 2011" (a 25/26 June discrepancy, likely time zones). That message gives no technical reasons; Guido, verbatim: "Let me cut this short. PEP 380 is pretty much approved. I know there are a few details worth quibbling over, but they are not going to jeopardize acceptance of the PEP. We are waiting for an implementation in Python 3.3." It answers Eby's argument that a library could do it, after Nick Coghlan wrote (quoted there) "Indeed, PEP 380 is *really* hard to do properly without language support." ([PEP 380, PEP Acceptance](https://peps.python.org/pep-0380/#pep-acceptance); [Guido van Rossum, python-dev, 2011-06-25, "EuroPython Language Summit report"](https://mail.python.org/pipermail/python-dev/2011-June/112010.html))
- "What's New in Python 3.3", verbatim: "PEP 380 adds the `yield from` expression, allowing a generator to delegate part of its operations to another generator. This allows a section of code containing `yield` to be factored out and placed in another generator. Additionally, the subgenerator is allowed to return with a value, and the value is made available to the delegating generator." And: "Python 3.3 was released on September 29, 2012." ([What's New in Python 3.3](https://docs.python.org/3/whatsnew/3.3.html))

**How asyncio (PEP 3156) depends on PEP 380**
- PEP 3156 Abstract, verbatim: "The proposal includes a pluggable event loop, transport and protocol abstractions similar to those in Twisted, and a higher-level scheduler based on `yield from` (PEP 380)." ([PEP 3156, Abstract](https://peps.python.org/pep-3156/#abstract))
- Header: "Author: Guido van Rossum", "Created: 12-Dec-2012", "Python-Version: 3.3", "Discussions-To: python-tulip@googlegroups.com". ([PEP 3156](https://peps.python.org/pep-3156/))
- Verbatim: "For users (like myself) who don't like using callbacks, a scheduler is provided for writing asynchronous I/O code as coroutines using the PEP 380 `yield from` or PEP 492 `await` expressions." ([PEP 3156](https://peps.python.org/pep-3156/))
- Coroutines section, verbatim: "A coroutine is a generator that follows certain conventions." "Coroutines use the `yield from` syntax introduced in PEP 380, instead of the original `yield` syntax." ([PEP 3156, Coroutines](https://peps.python.org/pep-3156/#coroutines))
- The four things a coroutine can do, verbatim: "`result = yield from future` -- suspends the coroutine until the future is done, then returns the future's result, or raises an exception, which will be propagated." "`result = yield from coroutine` -- wait for another coroutine to produce a result (or raise an exception, which will be propagated)." "`return expression` -- produce a result to the coroutine that is waiting for this one using `yield from`." "`raise exception` -- raise an exception in the coroutine that is waiting for this one using `yield from`." ([PEP 3156, Coroutines](https://peps.python.org/pep-3156/#coroutines))
- Verbatim: "Calling a coroutine does not start its code running -- it is just a generator, and the coroutine object returned by the call is really a generator object, which doesn't do anything until you iterate over it." ([PEP 3156](https://peps.python.org/pep-3156/#coroutines))
- Shipping, verbatim: "As of October 20th 2013, the `asyncio` package has been checked into the Python 3.4 repository and released with Python 3.4-alpha-4, with "provisional" API status." ([PEP 3156, Status](https://peps.python.org/pep-3156/#status))

### Inferences
- Each of asyncio's four coroutine operations uses a piece of PEP 380: `yield from` delegation for the call, the `StopIteration` value for `return`, `throw()` forwarding for the exception path, and the innermost-first propagation for both.
- PEP 380's "Generators as Threads" section is the clearest primary statement of the computer-science idea: a generator is "an ordinary function that can be suspended", and `yield from` restores the call stack that PEP 342's trampoline had to keep explicitly.

### Gaps
- Guido's python-ideas posts from October 2012 discuss the design (see the next section) but none that I read gives his reasons for accepting PEP 380 in 2011; the acceptance message itself gives none.

## PEP 3156, PEP 492, PEP 525, and PEP 479: separate native coroutines and the late fixes

### Takeaway
PEP 492 (Yury Selivanov, created 9 April 2015, Python 3.5 released 13 September 2015) keeps the generator machinery ("Coroutines are still based on generators internally") and adds a separate native type because generator-based coroutines were easy to confuse with generators, became or stopped being coroutines when a `yield` was added or removed, and could suspend only where `yield` was legal.
PEP 525 (Python 3.6) applies PEP 255's rationale to `async for`.
PEP 479 (Python 3.5 opt-in, default in 3.7) turns a `StopIteration` escaping a generator into `RuntimeError`, because a stray `StopIteration` silently ended iteration and broke the `yield from` refactoring abstraction.

### Cited Findings

**PEP 492**
- Header: "Title: Coroutines with async and await syntax", "Author: Yury Selivanov", "Created: 09-Apr-2015", "Python-Version: 3.5", "Status: Final". ([PEP 492](https://peps.python.org/pep-0492/))
- Abstract, verbatim: "This proposal aims to answer that need by making writing explicitly asynchronous, concurrent Python code easier and more Pythonic. It is proposed to make *coroutines* a proper standalone concept in Python, and introduce new supporting syntax. The ultimate goal is to help establish a common, easily approachable, mental model of asynchronous programming in Python and make it as close to synchronous programming as possible." ([PEP 492, Abstract](https://peps.python.org/pep-0492/#abstract))
- Abstract, on the event loop, verbatim: "While the PEP is not tied to any specific Event Loop implementation, it is relevant only to the kind of coroutine that uses `yield` as a signal to the scheduler, indicating that the coroutine will be waiting until an event (such as IO) is completed." ([PEP 492](https://peps.python.org/pep-0492/#abstract))
- Rationale and Goals, complete and verbatim ([PEP 492, Rationale and Goals](https://peps.python.org/pep-0492/#rationale-and-goals)):

> Current Python supports implementing coroutines via generators (PEP 342), further enhanced by the `yield from` syntax introduced in PEP 380. This approach has a number of shortcomings:
>
> * It is easy to confuse coroutines with regular generators, since they share the same syntax; this is especially true for new developers.
> * Whether or not a function is a coroutine is determined by a presence of `yield` or `yield from` statements in its *body*, which can lead to unobvious errors when such statements appear in or disappear from function body during refactoring.
> * Support for asynchronous calls is limited to expressions where `yield` is allowed syntactically, limiting the usefulness of syntactic features, such as `with` and `for` statements.
>
> This proposal makes coroutines a native Python language feature, and clearly separates them from generators. This removes generator/coroutine ambiguity, and makes it possible to reliably define coroutines without reliance on a specific library. This also enables linters and IDEs to improve static code analysis and refactoring.
>
> Native coroutines and the associated new syntax features make it possible to define context manager and iteration protocols in asynchronous terms. As shown later in this proposal, the new `async with` statement lets Python programs perform asynchronous calls when entering and exiting a runtime context, and the new `async for` statement makes it possible to perform asynchronous calls in iterators.

- Specification, verbatim: "This specification presumes knowledge of the implementation of coroutines in Python (PEP 342 and PEP 380). Motivation for the syntax changes proposed here comes from the asyncio framework (PEP 3156) and the "Cofunctions" proposal (PEP 3152, now rejected in favor of this specification)." ([PEP 492, Specification](https://peps.python.org/pep-0492/#specification))
- Relation to generators, verbatim: "Coroutines are based on generators internally, thus they share the implementation. Similarly to generator objects, *coroutines* have `throw()`, `send()` and `close()` methods. `StopIteration` and `GeneratorExit` play the same role for coroutines (although PEP 479 is enabled by default for coroutines)." ([PEP 492, Coroutine object methods](https://peps.python.org/pep-0492/#coroutine-object-methods))
- Verbatim: "Any `yield from` chain of calls ends with a `yield`. This is a fundamental mechanism of how *Futures* are implemented. Since, internally, coroutines are a special kind of generators, every `await` is suspended by a `yield` somewhere down the chain of `await` calls (please refer to PEP 3156 for a detailed explanation)." ([PEP 492, Await Expression](https://peps.python.org/pep-0492/))
- Separation, verbatim: "Great effort has been made to make sure that coroutines and generators are treated as distinct concepts: 1. *Native coroutine* objects do not implement `__iter__` and `__next__` methods. Therefore, they cannot be iterated over or passed to `iter()`, `list()`, `tuple()` and other built-ins. They also cannot be used in a `for..in` loop." ([PEP 492, Differences from generators](https://peps.python.org/pep-0492/))
- Visible suspension points, verbatim: "The vision behind existing generator-based coroutines and this proposal is to make it easy for users to see where the code might be suspended. Making existing "for" and "with" statements to recognize asynchronous iterators and context managers will inevitably create implicit suspend points, making it harder to reason about the code." ([PEP 492, Why not reuse existing "for" and "with" statements](https://peps.python.org/pep-0492/#why-not-reuse-existing-for-and-with-statements))
- "What's New in Python 3.5": "Python 3.5 was released on September 13, 2015." and "PEP 492 greatly improves support for asynchronous programming in Python by adding awaitable objects, coroutine functions, asynchronous iteration, and asynchronous context managers." ([What's New in Python 3.5](https://docs.python.org/3/whatsnew/3.5.html))

**PEP 525 (asynchronous generators)**
- Header: "Author: Yury Selivanov", "Created: 28-Jul-2016", "Python-Version: 3.6". ([PEP 525](https://peps.python.org/pep-0525/))
- Rationale, verbatim: "Regular generators (introduced in PEP 255) enabled an elegant way of writing complex *data producers* and have them behave like an iterator. However, currently there is no equivalent concept for the *asynchronous iteration protocol* (`async for`). This makes writing asynchronous data producers unnecessarily complex, as one must define a class that implements `__aiter__` and `__anext__` to be able to use it in an `async for` statement. Essentially, the goals and rationale for PEP 255, applied to the asynchronous execution case, hold true for this proposal as well." ([PEP 525, Rationale and Goals](https://peps.python.org/pep-0525/#rationale-and-goals))
- Verbatim: "in our testing of the reference implementation, asynchronous generators are **2x** faster than an equivalent implemented as an asynchronous iterator." ([PEP 525](https://peps.python.org/pep-0525/#rationale-and-goals))
- "Python 3.6 was released on December 23, 2016." ([What's New in Python 3.6](https://docs.python.org/3/whatsnew/3.6.html))

**PEP 479 (`StopIteration` inside generators)**
- Header: "Author: Chris Angelico, Guido van Rossum", "Created: 15-Nov-2014", "Python-Version: 3.5". Transition plan includes "Python 3.6: Non-silent deprecation warning." and "Python 3.7: Enable new semantics everywhere." ([PEP 479](https://peps.python.org/pep-0479/))
- Abstract, verbatim: "This PEP proposes a change to generators: when `StopIteration` is raised inside a generator, it is replaced with `RuntimeError`. (More precisely, this happens when the exception is about to bubble out of the generator's stack frame.)" ([PEP 479, Abstract](https://peps.python.org/pep-0479/#abstract))
- Rationale, verbatim: "The interaction of generators and `StopIteration` is currently somewhat surprising, and can conceal obscure bugs. An unexpected exception should not result in subtly altered behaviour, but should cause a noisy and easily-debugged traceback. Currently, `StopIteration` raised accidentally inside a generator function will be interpreted as the end of the iteration by the loop construct driving the generator." ([PEP 479, Rationale](https://peps.python.org/pep-0479/#rationale))
- Verbatim: "This is particularly pernicious in combination with the `yield from` construct of PEP 380, as it breaks the abstraction that a subgenerator may be factored out of a generator." And: "Similarly problematic behavior occurs when an `asyncio` coroutine raises `StopIteration`, causing it to terminate silently". And: "Finally, the proposal also clears up the confusion about how to terminate a generator: the proper way is `return`, not `raise StopIteration`." ([PEP 479, Rationale](https://peps.python.org/pep-0479/#rationale))

### Inferences
- PEP 492's first two shortcomings are both about the same fact: in a generator-based coroutine, the presence of `yield` is the only marker that a function is a coroutine. `async def` moves that marker to the definition line, and `await` keeps a visible marker at each suspension point.
- PEP 479 is the price of PEP 380's choice to carry the return value on `StopIteration`: once `return value` and "end of iteration" share one exception, an accidental `StopIteration` from a helper reads as a normal return.

### Gaps
- None for these PEPs' rationales; all were read in full in the relevant sections.

## Why Guido chose explicit `yield from` coroutines over callbacks and over implicit switching (greenlets, gevent, Stackless)

### Takeaway
The primary sources I could read show Guido rejecting callbacks for his own code ("For users (like myself) who don't like using callbacks") and contrasting the effort with greenlets in October 2012 ("There happen to be several problems with greenlets"), and PEP 492 states the design goal as "to make it easy for users to see where the code might be suspended".
The fullest statement of the visible-suspension-point argument in a source I read is Glyph Lefkowitz's "Unyielding" (2014), which says Guido gave the same kind of example.
I did not find, in a primary source I could read in full, Guido's own sentence saying that a visible `yield from` marks each suspension point.

### Cited Findings
- Guido, python-ideas, 15 Oct 2012, thread "The async API of the future: yield-from", replying to Matt Joiner, verbatim: "Here you're basically arguing for greenlets/gevent -- you're saying you just don't want to put up with the yields everywhere. And: "There happen to be several problems with greenlets (even Christian Tismer said so, and included Stackless in the problem). - Same post, verbatim: "A system that presents "implicit coroutines" – those which may transfer control to another concurrent task at any layer of the stack without any syntactic indication that this may happen – are simply the dubious optimization by itself." And: "green or lightweight threads are indeed threads, in that they present these same problems." ([Unyielding](https://blog.glyph.im/2014/02/unyielding.html))
- Same post, verbatim: "As it happens, this is the same variety of example Guido van Rossum gives when he describes why chose to use explicit coroutines instead of green threads for the upcoming standard library asyncio module". The link on that sentence points to PEP 3156, not to a talk or post. ([Unyielding](https://blog.glyph.im/2014/02/unyielding.html))

### Inferences
- The argument against implicit switching (greenlets, gevent, Stackless) is about local reasoning: with an explicit `yield from`/`await`, a reader sees in the text where another task can run; with greenlets, any call can switch. This matches PEP 492's stated "vision" and Glyph's account; the attribution of that wording to Guido himself rests on Glyph's report.
- The argument against callbacks, in PEP 342 (2005) and PEP 3156 (2012), is the same: code written as callbacks is split across functions, and the generator form keeps it "a regular sequential function" (Twisted's phrase).

### Gaps
- Unverified: Guido's own words that a visible `yield from` marks each task-switch point. A web search surfaced a python-tulip Google Groups message (subject "The difference between yield and yield-from", March 2013) whose search snippet reads "What you're suggesting here is what greenlets do, and hence that's how gevent works. But I don't like it", but the page as fetched did not contain that passage, so the quotation is unverified and should not be used without reading the original: [python-tulip thread](https://groups.google.com/g/python-tulip/c/bmphRrryuFk/m/aB45sEJUomYJ).
- Guido's PyCon 2013 keynote and his Tulip talks (2013) were not found as text or slides; no quotation from them is offered.

## How the best-known explanations state the idea (David Beazley, 2008, 2009, 2014)

### Takeaway
Beazley separates three uses of `yield`: producing data for iteration, consuming data sent in, and acting as a "trap" that hands control to a scheduler, the way a system call traps into an operating system.
His 2014 talk adds the `@contextmanager` view ("Think of "yield" as scissors") and builds an "inlined future" from it, and its historical slide summarizes the arc from iteration (2.3) to coroutines (2.5) to delegation (3.3).

## Verification of the chapter's five claims

### Takeaway
Claims 1 and 4 are confirmed.
Claims 2, 3, and 5 are broadly right but each needs a qualification: `close()` came from cleanup and the `with` statement rather than from simulations or I/O; PEP 342's trampoline is described as letting coroutines call one another (its second example runs many on it); and PEP 492 describes native coroutines as generator-based internally but deliberately a separate type, and says the PEP is not tied to one event loop.

### Cited Findings
1. "PEP 342, written in 2005, ... added the send channel to Python 2.5 in 2006." **Confirmed.** PEP 342: "Created: 10-May-2005", "Python-Version: 2.5", and the patch "was committed to CVS 01-02 August 2005" ([PEP 342](https://peps.python.org/pep-0342/)). "Python 2.5 was released on September 19, 2006." ([What's New in Python 2.5](https://docs.python.org/3/whatsnew/2.5.html))
2. "Simulations, games, and asynchronous I/O need to pass a value or an exception into a generator at its suspension point, so `send()`, `throw()`, and `close()` arrived together." **Partly confirmed; the causal link is too narrow for `close()`.** The use cases are PEP 342's: "Coroutines are a natural way of expressing many algorithms, such as simulations, games, asynchronous I/O, and other forms of event-driven programming or co-operative multitasking", and generators "do not provide for values or exceptions to be passed in when execution resumes" ([PEP 342, Motivation](https://peps.python.org/pep-0342/#motivation)). The three methods did arrive together, in PEP 342 and Python 2.5. But the same Motivation gives a separate reason, the one `close()` answers: generators "do not allow execution to be paused within the `try` portion of `try/finally` blocks, and therefore make it difficult for an aborted coroutine to clean up after itself" (same source). PEP 343 derives `throw()` and then `close()` from the `with` statement: "people really liked being able to "see" the exception in the generator ... To enable this, a new `throw()` method for generators is proposed ... Once we have this, it is a small step to proposing another generator method, `close()`" ([PEP 343](https://peps.python.org/pep-0343/#motivation-and-summary)). Also, the PEP says coroutines express these algorithms naturally; it does not say the applications "need" the feature.
3. "The PEP describes a scheduler that runs many generators as a 'trampoline'." **Confirmed with a nuance.** PEP 342 uses the word twice: "a simple co-routine scheduler or *trampoline function* would let coroutines *call* each other without blocking" ([Motivation](https://peps.python.org/pep-0342/#motivation)) and "A simple co-routine scheduler or *trampoline* that lets coroutines *call* other coroutines by yielding the coroutine they wish to invoke" ([Examples](https://peps.python.org/pep-0342/#examples)). The defining feature in the PEP is coroutines calling one another (yielding a generator is a call, yielding any other value is a return to the caller, exceptions propagate to the caller). Running many is shown by Example 4 (`trampoline.add( handler(connected_socket) )`, "servicing them "in parallel"") and by the `Trampoline` class's queue.
4. "`yield from` (PEP 380, Python 3.3, 2012)." **Confirmed.** "Python-Version: 3.3" ([PEP 380](https://peps.python.org/pep-0380/)); "Python 3.3 was released on September 29, 2012." ([What's New in Python 3.3](https://docs.python.org/3/whatsnew/3.3.html)). Note: PEP 380 was created in 2009 and accepted in June 2011.
5. "`async`/`await` (PEP 492, Python 3.5, 2015) is the same machinery with a syntax that marks a function as one the event loop resumes." **Partly confirmed.** Version and year: "Python-Version: 3.5" ([PEP 492](https://peps.python.org/pep-0492/)); "Python 3.5 was released on September 13, 2015." ([What's New in Python 3.5](https://docs.python.org/3/whatsnew/3.5.html)). Same machinery: "Coroutines are based on generators internally, thus they share the implementation. Similarly to generator objects, *coroutines* have `throw()`, `send()` and `close()` methods." ([PEP 492](https://peps.python.org/pep-0492/#coroutine-object-methods)). Qualifications: PEP 492 "clearly separates them from generators" and native coroutine objects "do not implement `__iter__` and `__next__`" ([PEP 492](https://peps.python.org/pep-0492/#rationale-and-goals)), so the syntax marks a distinct type, not only a role. And the PEP "is not tied to any specific Event Loop implementation" while being "relevant only to the kind of coroutine that uses `yield` as a signal to the scheduler" ([PEP 492, Abstract](https://peps.python.org/pep-0492/#abstract)), so "a scheduler" or "a driver" is more exact than "the event loop". The syntax also marks each suspension point (`await`), which PEP 492 names as the goal: "to make it easy for users to see where the code might be suspended."

### Inferences
- A rewording of claim 2 that the sources support: PEP 342 gives two reasons. A coroutine, the natural form for simulations, games, and asynchronous I/O, must receive a value or an exception where it paused (`send()`, `throw()`), and a coroutine abandoned midway must be able to clean up (`close()`, and `yield` allowed inside `try/finally`).
- A rewording of claim 5 that the sources support: `async`/`await` runs on the generator machinery (`send()`, `throw()`, `close()`), but `async def` makes a separate coroutine type that cannot be iterated, and `await` marks each point where a scheduler can suspend it.

### Gaps
- None; each claim was checked against the primary source.

## Context only: did other languages follow the same path from generator to async function?

### Takeaway
JavaScript followed Python's path in the same order and says so in its proposal: generators (ES2015), a generator-driving library (`co`), then async functions built on "Promises and Generators".
For C#, Kotlin, C++20, and Rust I gathered no primary sources in this pass, so the dates below are unverified.

### Cited Findings
- TC39 async functions proposal README, verbatim: "The introduction of Promises and Generators in ECMAScript presents an opportunity to dramatically improve the language-level model for writing asynchronous code in ECMAScript." And: "This proposal is implemented in a regenerator which can compile ES5 code containing `async` and `await` down to vanilla ES5". ([tc39/ecmascript-asyncawait README](https://github.com/tc39/ecmascript-asyncawait))
- `co` README, verbatim: "Generator based control flow goodness for nodejs and the browser, using promises, letting you write non-blocking code in a nice-ish way." And: "`co@4.0.0` has been released, which now relies on promises. It is a stepping stone towards the async/await proposal." ([tj/co README](https://github.com/tj/co))
- Glyph Lefkowitz groups C#'s `async`/`await` with Twisted's `@inlineCallbacks` and Tulip's `yield from` as "explicit coroutines". ([Unyielding](https://blog.glyph.im/2014/02/unyielding.html))
- PEP 492 cites prior art, as reported by a fetch of the rendered page (not checked against the source line): "async/await is not a new concept in programming languages", naming C#, Hack, Dart, and Scala among others. ([PEP 492](https://peps.python.org/pep-0492/))

### Inferences
- The JavaScript proposal's own first sentence matches the Python sequence: a generator that can be resumed with a value (and a promise/Future to wait for) comes first, a library driver proves the pattern, and dedicated syntax follows.

### Gaps
- Unverified, from general knowledge only: C# iterators (`yield return`) in C# 2.0 (2005) and `async`/`await` in C# 5.0 (2012); ES2015 generators and ES2017 async functions; Kotlin coroutines stable in Kotlin 1.3 (2018); C++20 coroutines; Rust `async`/`await` stable in 1.39 (2019), implemented on internal generators. No designer quotation explaining why the generator came first was collected for any of these languages.
