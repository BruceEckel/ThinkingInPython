# Python's decision: PEP 255 and the 1999-2001 debate (generators vs. coroutines vs. continuations vs. Stackless)

Method note: every python-dev quotation below was read from the pipermail HTML of the message itself (downloaded and converted to text), not from a search snippet.
PEP text was read from the PEP source in the python/peps repository.
Timestamps are as the archive prints them (the 1999 archive prints CEST; the 2001 archive prints the sender's local zone).
Archive message 095208 and 095210 (May 1999) carry identical text from Tim Peters, nine hours apart; the second looks like a re-send, so cite 095208.

## 1. What PEP 255 gives as its motivation

### Takeaway
PEP 255 frames generators as the answer to one problem: a producer that must keep state between the values it produces.
It walks through every alternative Python had in 2001 (callback, whole list, iterator object with hand-kept state, threads, Stackless) and rejects each for a stated reason, then names Sather/CLU iterators and Icon generators as languages that already solved it with "a kind of function that can return an intermediate result ... but maintaining the function's local state so that the function can be resumed again right where it left off."

### Cited Findings
- Header: "PEP: 255 / Title: Simple Generators / Author: Neil Schemenauer, Tim Peters, Magnus Lie Hetland / Status: Final / Type: Standards Track / Requires: 234 / Created: 18-May-2001 / Python-Version: 2.2 / Post-History: 14-Jun-2001, 23-Jun-2001" — [PEP 255 source](https://github.com/python/peps/blob/main/peps/pep-0255.rst); [PEP 255](https://peps.python.org/pep-0255/)
- The problem statement (first sentence of Motivation): "When a producer function has a hard enough job that it requires maintaining state between values produced, most programming languages offer no pleasant and efficient solution beyond adding a callback function to the producer's argument list, to be called with each value produced." — [PEP 255](https://peps.python.org/pep-0255/)
- The callback alternative, with `tokenize.py` and `tabnanny.py`: "For example, ``tokenize.py`` in the standard library takes this approach: the caller must pass a *tokeneater* function to ``tokenize()``, called whenever ``tokenize()`` finds the next token. This allows tokenize to be coded in a natural way, but programs calling tokenize are typically convoluted by the need to remember between callbacks which token(s) were seen last. The *tokeneater* function in ``tabnanny.py`` is a good example of that, maintaining a state machine in global variables, to remember across callbacks what it has already seen and what it hopes to see next. This was difficult to get working correctly, and is still difficult for people to understand. Unfortunately, that's typical of this approach." — [PEP 255](https://peps.python.org/pep-0255/)
  - Note the shape of the argument: the callback makes the *producer* natural and the *consumer* convoluted. Every later alternative is judged by which side it makes natural.
- Alternative 2, build the whole list: "An alternative would have been for tokenize to produce an entire parse of the Python program at once, in a large list. Then tokenize clients could be written in a natural way, using local variables and local control flow (such as loops and nested if statements) to keep track of their state. But this isn't practical: programs can be very large, so no a priori bound can be placed on the memory needed to materialize the whole parse; and some tokenize clients only want to see whether something specific appears early in the program (e.g., a future statement, or, as is done in IDLE, just the first indented statement), and then parsing the whole program first is a severe waste of time." — [PEP 255](https://peps.python.org/pep-0255/)
- Alternative 3, an iterator object with hand-kept state (PEP 234): "Another alternative would be to make tokenize an iterator, delivering the next token whenever its ``.next()`` method is invoked. This is pleasant for the caller in the same way a large list of results would be, but without the memory and "what if I want to get out early?" drawbacks. However, this shifts the burden on tokenize to remember *its* state between ``.next()`` invocations, and the reader need only glance at ``tokenize.tokenize_loop()`` to realize what a horrid chore that would be. Or picture a recursive algorithm for producing the nodes of a general tree structure: to cast that into an iterator framework requires removing the recursion manually and maintaining the state of the traversal by hand." — [PEP 255](https://peps.python.org/pep-0255/)
- Alternative 4, threads: "A fourth option is to run the producer and consumer in separate threads. This allows both to maintain their states in natural ways, and so is pleasant for both. Indeed, Demo/threads/Generator.py in the Python source distribution provides a usable synchronized-communication class for doing that in a general way. This doesn't work on platforms without threads, though, and is very slow on platforms that do (compared to what is achievable without threads)." — [PEP 255](https://peps.python.org/pep-0255/)
- Alternative 5, Stackless coroutines: "A final option is to use the Stackless (PEP 219) variant implementation of Python instead, which supports lightweight coroutines. This has much the same programmatic benefits as the thread option, but is much more efficient. However, Stackless is a controversial rethinking of the Python core, and it may not be possible for Jython to implement the same semantics. This PEP isn't the place to debate that, so suffice it to say here that generators provide a useful subset of Stackless functionality in a way that fits easily into the current CPython implementation, and is believed to be relatively straightforward for other Python implementations." — [PEP 255](https://peps.python.org/pep-0255/)
- The prior art and the "resumable" formulation: "That exhausts the current alternatives. Some other high-level languages provide pleasant solutions, notably iterators in Sather, which were inspired by iterators in CLU; and generators in Icon, a novel language where every expression *is a generator*. There are differences among these, but the basic idea is the same: provide a kind of function that can return an intermediate result ("the next value") to its caller, but maintaining the function's local state so that the function can be resumed again right where it left off." — [PEP 255](https://peps.python.org/pep-0255/)
  - The references are: "[2] "Iteration Abstraction in Sather" Murer, Omohundro, Stoutamire and Szyperski" and "[3] http://www.cs.arizona.edu/icon/". Ralph Griswold is not named anywhere in the PEP. — [PEP 255 source](https://github.com/python/peps/blob/main/peps/pep-0255.rst)
- The payoff, stated against the thread option: "From ``fib``'s point of view it's just delivering a sequence of results, as if via callback. But from its caller's point of view, the ``fib`` invocation is an iterable object that can be resumed at will. As in the thread approach, this allows both sides to be coded in the most natural ways; but unlike the thread approach, this can be done efficiently and on all platforms. Indeed, resuming a generator should be no more expensive than a function call." — [PEP 255](https://peps.python.org/pep-0255/)
- The closing link to PEP 234: "The same kind of approach applies to many producer/consumer functions. For example, ``tokenize.py`` could yield the next token instead of invoking a callback function with it as argument, and tokenize clients could iterate over the tokens in a natural way: a Python generator is a kind of Python iterator, but of an especially powerful kind." — [PEP 255](https://peps.python.org/pep-0255/)
- What "frozen" means (the implementation model in the spec): "If a ``yield`` statement is encountered, the state of the function is frozen, and the value of *expression_list* is returned to ``.next()``'s caller. By "frozen" we mean that all local state is retained, including the current bindings of local variables, the instruction pointer, and the internal evaluation stack: enough information is saved so that the next time ``.next()`` is invoked, the function can proceed exactly as if the ``yield`` statement were just another external call." — [PEP 255](https://peps.python.org/pep-0255/)
- The PEP's code examples are `fib()` and a binary `Tree` with a recursive and a non-recursive `inorder()` generator; `tokenize` is the motivating case in prose, not a code listing. — [PEP 255](https://peps.python.org/pep-0255/)

### Inferences
- The PEP's argument is a two-sided-naturalness argument: callbacks make the producer natural and the consumer a state machine; an iterator object makes the consumer natural and the producer a state machine; threads and coroutines make both natural but are slow, unportable, or controversial. A generator is the one option that makes both sides natural, cheaply, on every platform. This is the "WHY" the book's author is asking for, in the PEP's own terms.
- "Remove the recursion manually and maintain the state of the traversal by hand" names the specific cost: converting control-flow state (where am I in the loop or recursion) into data state (fields and flags).

### Gaps
- The PEP does not mention `os.path.walk()`, `xrange()`, or `xreadlines()`. See section 7.

## 2. python-dev 1999: Tim Peters on generators, coroutines, continuations

### Takeaway
The debate opened on 13 May 1999 when Sam Rushing asked for a "stackless" interpreter to get coroutines or continuations for Medusa, whose callback style he called continuation-passing style.
Tim Peters answered over the following weeks with a consistent position: generators ("semi-coroutines", "half a coroutine", "resumable function") are what Python needs, they are easy because they always return to their caller so only one frame must be kept, and full coroutines and continuations are much harder because the C stack gets in the way.

### Cited Findings
- Thread opener, Sam Rushing, "[Python-Dev] 'stackless' python?", Thu May 13 08:34:19 CEST 1999: "has there been discussion of separating the Python and C invocation stacks, (i.e., removing recursive calls to the intepreter) to facilitate coroutines or first-class continuations? One of the biggest barriers to getting others to use asyncore/medusa is the need to program in continuation-passing-style (callbacks, callbacks to callbacks, state machines, etc...). ... And even when you do 'get' it, there are limits to how inside-out your thinking can go. 8^) If Python had coroutines/continuations, it would be possible to hide asyncore-style select()/poll() machinery 'behind the scenes'." — [python-dev 1999-May/095192](https://mail.python.org/pipermail/python-dev/1999-May/095192.html)
- Sam Rushing, same thread, Fri May 14 04:00:09 CEST 1999, on his async server: "This code in CPS is a horrible, complicated mess, it takes something like 8 callback methods, variables and exceptions have to be passed around in 'continuation' objects. It's hairy because there are three levels of callback state. Ugh." — [python-dev 1999-May/095199](https://mail.python.org/pipermail/python-dev/1999-May/095199.html)
- Tim Peters, "[Python-Dev] 'stackless' python?", Sat May 15 09:51:00 CEST 1999, introducing "semi coroutines" and the porting argument: "The Icon language needs a bit of platform-specific context-switching assembly code to support its full coroutine features, although its bread-and-butter generators ("semi coroutines") don't need anything special. The result is that Icon ports sometimes limp for a year before they support full coroutines, waiting for someone wizardly enough to write the necessary code. ... Not attractive. Generators are, though <wink>." — [python-dev 1999-May/095207](https://mail.python.org/pipermail/python-dev/1999-May/095207.html)
- Tim Peters, same thread, Sat May 15 09:51:03 CEST 1999, on why generators are easy and continuations are not: "The problem is that when C calls Python, any notion of continuation has to include C's state too, else resuming the continuation won't return into C correctly. ... The thing that makes generators so much easier is that they always return directly to their caller, at the point of call; so no C frame can get stuck in the middle even under today's implementation; it just requires not deleting the generator's frame object, and adding an opcode to *resume* the frame's execution the next time the generator is called." In the same message: "Icon iterators/generators could be implemented today if anyone bothered (Majewski essentially implemented them back around '93 already, but seemed to lose interest when he realized it couldn't be extended to full continuations, because of C/Python stack intertwingling)." — [python-dev 1999-May/095208](https://mail.python.org/pipermail/python-dev/1999-May/095208.html) (re-sent as [095210](https://mail.python.org/pipermail/python-dev/1999-May/095210.html))
- Tim Peters, Tue May 18 06:45:57 CEST 1999: "Python already has well-developed exception and thread facilities, so it's hard to make a case for continuations as a catch-all implementation mechanism. That may be the rub here: while any number of things *can* be implementated via continuations, I think very few *need* to be implemented that way, and full-blown continuations aren't easy to implement efficiently & portably. The Icon language was particularly concerned with backtracking searches, and came up with generators as another clearer/cheaper implementation technique." — [python-dev 1999-May/095227](https://mail.python.org/pipermail/python-dev/1999-May/095227.html)
- Tim Peters, "[Python-Dev] A "real" continuation example", Thu May 20 01:56:33 CEST 1999, solving the tree-fringe problem (generate a nested list's leaves one at a time) in Icon, Python, and Scheme: "The Python solution is the least satisfactory, using an explicit stack to simulate recursion by hand; if you didn't know the routine's purpose in advance, you'd have a hard time guessing it. The Icon solution is very short and simple ... It uses the subset of Icon ("generators") that doesn't require any C-stack trickery." — [python-dev 1999-May/095254](https://mail.python.org/pipermail/python-dev/1999-May/095254.html)
- **"half a coroutine"**: Tim Peters, "[Python-Dev] Coroutines", Sat May 22 06:22:50 CEST 1999, after showing a `fringe()`/`printinorder()` example built on his thread-based coroutine classes: "Generators are really "half a coroutine", so this doesn't show the full power (other examples in the post do). co.detach is a special way to deal with this asymmetry." In the same message: "In a nutshell, coroutines don't have a "caller/callee" relationship, they have "we're all equal partners" relationship, where any coroutine is free to resume any other one where it left off. It's no coincidence that making coroutines easy to use was pioneered by simulation languages!" — [python-dev 1999-May/095276](https://mail.python.org/pipermail/python-dev/1999-May/095276.html)
- Tim Peters, "[Python-Dev] Re: Coroutines", Sat May 22 06:22:55 CEST 1999 (five seconds later): "Generators ("semi-coroutines") are wonderful tools and easy to implement without major changes to the PVM. Python needs something like that. OTOH, generators are pretty much limited to that. + Coroutines are more general but much harder to implement, because each coroutine needs its own stack (a generator only has one stack *frame*-- its own --to worry about), and C-calling-Python can get into the act. As Sam said, they're probably no easier to implement than call/cc (but trivial to implement given call/cc)." — [python-dev 1999-May/095277](https://mail.python.org/pipermail/python-dev/1999-May/095277.html)
- Tim Peters, "[Python-Dev] Coroutines", Sat May 22 21:35:58 CEST 1999, on the earlier history: Steven Majewski "went most of the way, up until hitting the C<->Python stack intertwingling barrier, and then dropped it. - Tim Peters, "Fake threads (was [Python-Dev] ActiveState & fork & Perl)", Thu, 1 Jul 1999 00:30:30 -0400: "What I personally want for my own work is no more than Icon's generators, formally "semi coroutines", and easily implemented in the interpreter (although not the language) as it exists today. Coroutines, fake threads and continuations are much stronger than generators, and I expect you can fake any of the first three given either of the others." — [python-dev 1999-July/000450](https://mail.python.org/pipermail/python-dev/1999-July/000450.html)
- **Tim Peters's "biased short course"**, "Fake threads", Mon, 5 Jul 1999 02:55:02 -0400, in reply to Gordon McMillan's question about how the three "involve the idea of "resumable"". The key passages:
  - NOW: "When Python makes a call, it allocates a frame object. ... When a subroutine returns, it decrefs the frame and then the frame typically goes away".
  - GENERATORS: "Generators add two new abstract operations, "suspend" and "resume". When a generator suspends, it's exactly like a return today except we simply decline to decref the frame. That's it! The locals, and where we are in the computation, aren't thrown away. A "resume" then consists of *re*starting the frame at its next bytecode instruction, with the retained frame's locals and eval stack just as they were."
  - "They're asymmetric: "suspend" is something only a generator can do, and "resume" something only its caller can do".
  - The motivation in one sentence: "Because a generator remembers where it is and what its locals are, its state and "what to do next" don't have to be encoded in global data structures then decoded from scratch upon entry. That is, whenever you build a little (or large!) state machine to figure out "what to do next" from a collection of persistent flags and state vrbls, chances are good there's a simple algorithm dying to break free of that clutter <wink>."
  - COROUTINES: "Coroutines add only one new abstract operation, "transfer". They're fully symmetric so can get away with only one." ... "Why these are so much harder to implement than generators: "transfer" *names* who next gets control, while generators always return to their (unnamed) caller. So a generator simply "pops the stack" when it suspends, while coroutine flow need not be (and typically isn't) stack-like. In Python this is currently a coroutine-killer, because the C stack gets intertwined."
  - "Knuth seems to have this restricted flavor of coroutine in mind when he describes generator behavior as "semi-coroutine"."
  - CONTINUATIONS: "Continuations aren't more elaborate than coroutines, they're simpler. Indeed, they're simpler than generators, and even simpler than "a regular call"! ... they're a different *basis* for *all* call-like behavior."
  - On Guido: "Guido tends to like his implementations to mirror his surface semantics, though, and if he has ten constructs they're likely to be implemented ten ways." — [python-dev 1999-July/000467](https://mail.python.org/pipermail/python-dev/1999-July/000467.html)
- Gordon McMillan's question that prompted it, Sun, 4 Jul 1999: "All these beasts (continuations, coroutines, generators) involve the idea of "resumable", but: A generator's state is wholly self-contained / A coroutines's state is not necessarily self-contained but it is stable / Continuations may have volatile state." — [python-dev 1999-July/000463](https://mail.python.org/pipermail/python-dev/1999-July/000463.html)
- **"resumable function" and the "simplest possible version"**: Tim Peters, "[Python-Dev] Generator details", Thu, 8 Jul 1999 02:45:51 -0400, answering Guido's question whether the one-frame restriction is necessary: "It can simplify the implementation, and (not coincidentally <wink>) the user's mental model of how they work." Then: "Only that I've been pushing generators for almost a decade, and have always pushed the simplest possible version that's sufficient for my needs. However, every time I've made a micron's progress in selling this notion, it's been hijacked by someone else pushing continuations. So I keep pushing the simplest possible version of generators ("resumable function"), in the hopes that someday somebody will remember they don't need to turn Python inside out to get just that much <wink>." — [python-dev 1999-July/000485](https://mail.python.org/pipermail/python-dev/1999-July/000485.html)

### Inferences
- Tim's consistent technical criterion is direction of return: a generator returns to its unnamed caller, so suspension is "pop the stack, keep the frame", and nothing about the C stack changes. A coroutine names its target, so control flow stops being stack-like, and in CPython any C frame between two Python frames gets trapped. This criterion, not taste, is why the restricted form was implementable in 1999 and the general form was not.

### Gaps
- The archive shows "half a coroutine" in quotation marks in Tim's own text, which suggests he was quoting a stock phrase; I found no earlier source for it.
- I did not search comp.lang.python for 1999 posts; the python-dev record was sufficient for every phrase asked about.

## 3. Stackless, PEP 219/220, Medusa, Neil Schemenauer's patch, and Guido's reasons

### Takeaway
Stackless Python (Christian Tismer, 1999-2000) removed C-stack recursion so that continuations, coroutines, and microthreads became possible; Gordon McMillan wrote PEP 219 (changes to the core, Deferred) and PEP 220 (the facilities, Rejected) in August 2000.
Guido's recorded objections were portability (no stack-layout tricks, Jython must stay pure Java), complexity ("continuations are too complicated for most programmers"), and friendliness to C extensions that call back into Python.
Neil Schemenauer's patch in March 2001 came directly out of a PEP 219 thread in which Tim noted that a frame object is "96.3% of what's needed for generators".

Another thread in this list is porting Python to microplatforms like PalmOS. Typically the scheme Hackers are not afraid to delve deep into the machine, but I refuse to do that -- I think it's too risky." - Neil Schemenauer, "[Python-Dev] Simple generator implementation", Fri, 16 Mar 2001 05:54:48 -0800: "After searching through many megabytes of python-dev archives (grepmail is my friend), I finally found the posts Tim was referring me to (Subject: Generator details, Date: July 1999). - Samuele Pedroni (Jython developer), "[Python-Dev] Icon-style generators vs. jython", Sun, 18 Mar 2001: "In jython we have frames, and function are encapsulated in objects so the whole should be doable (with some effort) ... Freezing more than a frame is not directly possible in jython, frames are pushed and popped on java stack and function calls pass through java calling mechanism. (I imagine you need a separate thread for doing that)." — [python-dev 2001-March/013663](https://mail.python.org/pipermail/python-dev/2001-March/013663.html)
- Guido van Rossum, "[Python-Dev] gen-branch: CVS branch for Neil's generator patch", Fri, 15 Jun 2001: "I've checked in Neil's latest generator patch into a branch of the CVS tree." — [python-dev 2001-June/015440](https://mail.python.org/pipermail/python-dev/2001-June/015440.html)
- PEP 255's own credit: "This was derived from an earlier patch by Neil Schemenauer [4]" with "[4] http://python.ca/nas/python/generator.diff". The PEP names no SourceForge patch number. — [PEP 255](https://peps.python.org/pep-0255/)
- Retrospective (commentary, 2004): Guido van Rossum, "[Python-Dev] Stackless Python", Tue Jun 1 2004: "I think the bar should be raised pretty high for Stackless, given the various objections that have been raised against it (x86-only code, no Jython support, arbitrary exceptions, murky semantics, to name a few)" (quoted from his own earlier message); "C-only hacks are not welcome"; "(Jython must remain 100% pure Java.)"; and, asked why Python keeps state on the C stack: "IMO mostly because Python wants to be friendly to extensions written in C or C++, including those that frequently call back into Python." By "arbitrary exceptions" he meant "exceptions to the general rules. Like, you can't depend on tasklet switching when you use one of these extensions, or one of these built-ins". — [python-dev 2004-June/045089](https://mail.python.org/pipermail/python-dev/2004-June/045089.html)

### Inferences
- The causal chain is visible in the archive: Rushing's Medusa callbacks (May 1999) start the stackless discussion; Tim keeps steering toward the one-frame generator; continuations "hijack" it for two years (Tim's word, 1999 and 2000); PEP 219 stalls on the C-calls-Python problem; a Jython question in a PEP 219 thread (March 2001) makes Tim restate the frame-object argument; Neil implements it within hours, using Guido's and Tim's July 1999 "Generator details" design.
- Jython appears on both sides of the decision: PEP 255 cites it against Stackless, and Pedroni's message confirms that one frame is feasible in Jython while "Freezing more than a frame is not directly possible". This is the strongest primary evidence for "suspend only your own frame" as a portability requirement, not only a CPython convenience.

### Gaps
- I found no single 2001 message in which Guido states, in his own words, why generators were accepted and Stackless rejected. His reasons are assembled from 1999 posts (portability, complexity), the PEP's Stackless paragraph (co-written by Tim), and a 2004 retrospective.
- I did not read the full Tismer paper; the quotations from it above come from a search summary of the abstract and are marked as such. They need a direct read before use in the book.
- I did not check Sam Rushing's later (July 1999) "continuations for the curious" messages.

## 4. Verification of the chapter's six claims

### Takeaway
Claims 1, 2, 4, and 5 are confirmed, with small precision notes on 2 and 5.
Claim 3 is wrong in its wording: the PEP does not name Ralph Griswold, and it does not call the three languages "models".
Claim 6 is a fair paraphrase; Tim Peters's 1999 and 2001 wording supports it closely.

### Cited Findings
1. "PEP 255 added generators to Python 2.2 in 2001." **Confirmed.** "Created: 18-May-2001 / Python-Version: 2.2" — [PEP 255](https://peps.python.org/pep-0255/). "What's New in Python 2.2" has the section "PEP 255: Simple Generators" and says "In Python 2.3 this statement [`from __future__ import generators`] will become unnecessary." — [What's New 2.2 source](https://github.com/python/cpython/blob/main/Doc/whatsnew/2.2.rst). (Python 2.2's release date, December 2001, was not checked against a primary source in this research.)
2. "The PEP's example [is] the standard library's `tokenize()`." **Confirmed, with a precision note.** `tokenize.py`'s `tokenize()` with its *tokeneater* callback is the PEP's motivating example in prose, used for four of the five alternatives ("the caller must pass a *tokeneater* function to ``tokenize()``"). The PEP's code listings are `fib()` and a binary-tree `inorder()`, not tokenize. — [PEP 255](https://peps.python.org/pep-0255/)
3. "The PEP names Ralph Griswold's Icon language, with CLU and Sather, as the models." **Wrong as worded.** The exact PEP text: "Some other high-level languages provide pleasant solutions, notably iterators in Sather [2], which were inspired by iterators in CLU; and generators in Icon [3], a novel language where every expression *is a generator*. There are differences among these, but the basic idea is the same". Griswold is not named (the reference is the Icon home page URL), CLU appears only as Sather's inspiration, and the PEP calls them "pleasant solutions" with "the basic idea" in common, not models. A faithful rewording: "The PEP points to Sather's iterators (inspired by CLU's) and Icon's generators as languages that already had the idea." — [PEP 255](https://peps.python.org/pep-0255/)
4. "The PEP calls Stackless 'a controversial rethinking of the Python core.'" **Confirmed, exact wording.** "However, Stackless is a controversial rethinking of the Python core, and it may not be possible for Jython to implement the same semantics." — [PEP 255](https://peps.python.org/pep-0255/)
5. "In May 1999, two years before the PEP, Tim Peters called generators 'half a coroutine' on python-dev." **Confirmed.** Message: Tim Peters, subject "[Python-Dev] Coroutines", archive timestamp Sat May 22 06:22:50 CEST 1999 (that is, late on 21 May 1999 in US time), sentence: "Generators are really "half a coroutine", so this doesn't show the full power (other examples in the post do)." The PEP was created 18 May 2001, so "two years before" is exact to within a week. — [python-dev 1999-May/095276](https://mail.python.org/pipermail/python-dev/1999-May/095276.html). In the next message, five seconds later, he calls them "semi-coroutines". — [095277](https://mail.python.org/pipermail/python-dev/1999-May/095277.html)
6. That PEP 255's authors "wanted the useful part of a coroutine without the whole mechanism". **Supported (paraphrase, not a quotation).** The PEP: "generators provide a useful subset of Stackless functionality in a way that fits easily into the current CPython implementation" — [PEP 255](https://peps.python.org/pep-0255/). Tim Peters, 8 July 1999: "I keep pushing the simplest possible version of generators ("resumable function"), in the hopes that someday somebody will remember they don't need to turn Python inside out to get just that much" — [1999-July/000485](https://mail.python.org/pipermail/python-dev/1999-July/000485.html). Tim Peters, 31 Jan 2001: "once you go beyond "simple" (Icon) generators, a whole world of other stuff gets pulled in" — [2001-January/012402](https://mail.python.org/pipermail/python-dev/2001-January/012402.html). Tim Peters, 1 July 1999: "no more than Icon's generators, formally "semi coroutines"" — [1999-July/000450](https://mail.python.org/pipermail/python-dev/1999-July/000450.html).

### Inferences
- For claim 6, "useful subset of Stackless functionality" is the closest PEP wording, and it compares generators with Stackless (which offered coroutines), so the chapter can quote it directly instead of paraphrasing.

### Gaps
- None for the six claims, beyond the unchecked 2.2 release date.

## 5. Generators and the iterator protocol (PEP 234); What's New 2.2; retrospectives

### Takeaway
Iterators came first (Guido checked in an implementation in April 2001) and PEP 255 declares "Requires: 234"; a generator-iterator "conforms to the iterator protocol", so a generator is a cheap way to write an iterator without hand-kept state.
Tim had argued in January 2001 that the real precondition for generators was a generalized iteration protocol.
Kuchling's "What's New" presents generators as "resumable functions" and Icon as the source.

### Cited Findings
- PEP 255 spec: "Instead a generator-iterator object is returned; this conforms to the iterator protocol, so in particular can be used in for-loops in a natural way." — [PEP 255](https://peps.python.org/pep-0255/)
- Tim Peters, "[Python-Dev] Iterators, generators and 2.2", Sat, 21 Apr 2001 (cross-posted from python-list): "This is getting confused. Iterators != generators" ... "last night Guido checked an initial implementation into the 2.2 CVS tree." ... "There is no support here for generators or coroutines or microthreads, except in the sense that breaking the iteration==__getitem__ connection makes it easier to think about *how* generators may be implemented, and having an explicit iterator object "should" make it possible to go beyond Icon's notion of generators (which can only be driven implicitly by control context). Neil Schemenauer is currently thinking hard about that "in his spare time", but there's no guarantee anything will come of it in 2.2." — [python-dev 2001-April/014412](https://mail.python.org/pipermail/python-dev/2001-April/014412.html)
- Tim Peters, 17 Mar 2001, on teaching: "in earlier correspondence, the generator idea didn't seem to "click" until I called them "resumable functions" (as I often did in the past, but fell out of the habit). People new to the concept often pick that up quicker, or even, as in this case, remember that they once rolled such a thing by hand out of prior necessity." His forwarded correspondent wrote that generators "are what is needed for an efficient implementation of XSLT." — [python-dev 2001-March/013664](https://mail.python.org/pipermail/python-dev/2001-March/013664.html)
- Tim Peters, 27 Jun 2001, to a poster who called generators coroutines with "peer-to-peer synchronized messaging": "They're formally semi-coroutines; it's not symmetric." ... "Way too highfalutin' a view. Think of a generator as a resumable function, and you're not missing anything -- not even an implementation subtlety. They *are* resumable functions. A "yield" is just a "return", but with the twist that the function can resume executing after the "yield" again." — [python-dev 2001-June/015607](https://mail.python.org/pipermail/python-dev/2001-June/015607.html)
- A. M. Kuchling, "What's New in Python 2.2", "PEP 255: Simple Generators": "But, what if the local variables weren't thrown away on exiting a function? What if you could later resume the function where it left off? This is what generators provide; they can be thought of as resumable functions." ... "You could achieve the effect of generators manually by writing your own class and storing all the local variables of the generator as instance variables. ... However, for a moderately complicated generator, writing a corresponding class would be much messier." ... "The idea of generators comes from other programming languages, especially Icon ... where the idea of generators is central." ... "One novel feature of Python's interface as compared to Icon's is that a generator's state is represented as a concrete object (the iterator) that can be passed around to other functions or stored in a data structure." The section credits the implementation "mostly by Neil Schemenauer and Tim Peters". — [What's New in Python 2.2](https://docs.python.org/3/whatsnew/2.2.html); [source](https://github.com/python/cpython/blob/main/Doc/whatsnew/2.2.rst)

### Inferences
- Kuchling's last point and Tim's April 2001 point agree: Icon generators were tied to control context, and Python's novelty was to make the suspended function a first-class iterator object. That is what lets a caller interleave two traversals (the tree-fringe problem that recurs from 1994 through 2001).

### Gaps
- I did not find a Guido "History of Python" blog post on PEP 255 or a Guido interview about the 2001 decision; the search returned none. The only Guido retrospective located is the 2004 python-dev message in section 3.
- PEP 234's text does not mention generators (a grep of its source found no hit).

## 6. Why a generator suspends only its own frame (implementation)

### Takeaway
A CPython frame is a heap object; a return normally drops the last reference to it.
A generator keeps that reference, so suspending is a return that keeps the frame, and resuming re-enters it at the next bytecode.
Because the generator always returns to its caller, no C frame is ever caught between suspended Python frames; the general case (suspending several frames, or transferring to a named coroutine) would capture C stack, which needed Stackless-style surgery, was unportable, and was not possible in Jython.

### Cited Findings
- Tim Peters, 15 May 1999: generators "always return directly to their caller, at the point of call; so no C frame can get stuck in the middle even under today's implementation; it just requires not deleting the generator's frame object, and adding an opcode to *resume* the frame's execution" — [1999-May/095208](https://mail.python.org/pipermail/python-dev/1999-May/095208.html)
- Tim Peters, 22 May 1999: "each coroutine needs its own stack (a generator only has one stack *frame*-- its own --to worry about), and C-calling-Python can get into the act." — [1999-May/095277](https://mail.python.org/pipermail/python-dev/1999-May/095277.html)
- Tim Peters, 5 Jul 1999: "When a generator suspends, it's exactly like a return today except we simply decline to decref the frame." ... "if coroutine A merely calls (in the regular sense) function F, and F tries to transfer to coroutine B, the info needed to resume A includes the chunk of the C stack between A and F." — [1999-July/000467](https://mail.python.org/pipermail/python-dev/1999-July/000467.html)
- Tim Peters, 8 Jul 1999, on recursive generators under the one-frame rule: the tree traversal "would be written like this instead: `if node.left: suspend inorder(node.left)` ... Now there may be many instances of the "inorder" generator active (as many as the tree is deep), but each one returns directly to its caller". With full coroutines "your original version can be made to work, delivering its results directly to the ultimate consumer instead of (in effect) crawling up the stack each time there's a result." — [1999-July/000485](https://mail.python.org/pipermail/python-dev/1999-July/000485.html)
  - This is the recursive-generator cost that PEP 380's `yield from` later addressed (out of scope here; noted for the other researchers).
- Samuele Pedroni, 18 Mar 2001: "Freezing more than a frame is not directly possible in jython, frames are pushed and popped on java stack" — [2001-March/013663](https://mail.python.org/pipermail/python-dev/2001-March/013663.html)
- PEP 255 Q&A on the keyword: "It's also believed that efficient implementation in Jython requires that the compiler be able to determine potential suspension points at compile-time, and a new keyword makes that easy." — [PEP 255](https://peps.python.org/pep-0255/)
- PEP 219: "stack switching is an arcane and non-portable process, not supported by C." — [PEP 219](https://peps.python.org/pep-0219/)

### Inferences
- The one-frame rule and the `yield` keyword serve the same requirement: suspension points are known at compile time and lie in one frame, so any implementation that has frame objects (CPython, Jython) can support them without touching its host stack.

### Gaps
- None material.

## 7. Design choices debated, and concrete pain points named

### Takeaway
The PEP records four design decisions with reasons: reuse `def` (Guido's pronouncement), a `yield` keyword phased in through `from __future__ import generators`, no `yield` in the `try` of a `try`/`finally`, and a bare `return` (no value) to end.
The pain points participants named are `tokenize.py`/`tabnanny.py` callbacks, Medusa/asyncore callback servers, tree traversal and tree-fringe comparison, and lazy collections for `for`; `xrange()` came up only after the fact; `os.path.walk()` did not appear in anything I read.

### Cited Findings
- `def` stays (BDFL Pronouncement). Con (against a new keyword): "In practice (how you think about them), generators *are* functions, but with the twist that they're resumable." Pro: "generator-functions are actually factory functions that produce generator-iterators as if by magic." Guido: "``def`` it stays. No argument on either side is totally convincing, so I have consulted my language designer's intuition. It tells me that the syntax proposed in the PEP is exactly right - not too hot, not too cold. But, like the Oracle at Delphi in Greek mythology, it doesn't tell me why". — [PEP 255](https://peps.python.org/pep-0255/)
- `yield` as a keyword: "Control flow is much better expressed via keyword in Python, and yield is a control construct." Alternatives such as "return 3 and continue" were rejected: "I don't want to have to *deduce* that a yield is occurring from making sense of a previously senseless sequence of keywords or operators." — [PEP 255](https://peps.python.org/pep-0255/)
- `__future__`: "``yield`` is a new keyword, so a ``future`` statement (PEP 236) is needed to phase this in: in the initial release, a module desiring to use generators must include the line: from __future__ import generators". — [PEP 255](https://peps.python.org/pep-0255/)
- No `yield` in `try`/`finally`: "The difficulty is that there's no guarantee the generator will ever be resumed, hence no guarantee that the finally block will ever get executed; that's too much a violation of finally's purpose to bear." Consequence: "generators should allocate critical resources with great care." — [PEP 255](https://peps.python.org/pep-0255/)
- `return` with no value: "``return`` means "I'm done" in any kind of function, and that's easy to explain and to use." Why no `return expr`: "Perhaps we will someday. In Icon, ``return expr`` means both "I'm done", and "but I have one final useful value to return too, and this is it". At the start, and in the absence of compelling uses for ``return expr``, it's simply cleaner to use ``yield`` exclusively for delivering values." — [PEP 255](https://peps.python.org/pep-0255/)
- In the pronouncement thread, Guido already floated what PEP 342 later did for `finally`: "Another idea might be to somehow continue the frame with an exception at this point -- but I don't have a clue what exception would be appropriate (StopIteration isn't because it goes in the other direction)" (as quoted by Toby Dickenson, 21 Jun 2001). — [python-dev 2001-June/015501](https://mail.python.org/pipermail/python-dev/2001-June/015501.html)
- Pain point, async servers (Medusa): Rushing's CPS complaint, quoted in section 2 — [1999-May/095192](https://mail.python.org/pipermail/python-dev/1999-May/095192.html), [095199](https://mail.python.org/pipermail/python-dev/1999-May/095199.html). Guido answered "Agreed" to "This code in CPS is a horrible, complicated mess" and, of the closure-based version, "I agree that it is still ugly." — [095200](https://mail.python.org/pipermail/python-dev/1999-May/095200.html), [095206](https://mail.python.org/pipermail/python-dev/1999-May/095206.html)
- Pain point, lazy collections: generators are "exactly what you need to implement "for thing in object:" when object represents a collection that's tricky to materialize." — [1999-May/095277](https://mail.python.org/pipermail/python-dev/1999-May/095277.html)
- Pain point, tree traversal: "don't-try-to-traverse-a-tree-without-it-ly y'rs - tim" (sign-off, 15 May 1999) — [095208](https://mail.python.org/pipermail/python-dev/1999-May/095208.html); the tree-fringe solutions — [095254](https://mail.python.org/pipermail/python-dev/1999-May/095254.html); "recursive generators are particularly useful in both traversals and enumeration of combinatorial objects (permutations, subsets, and so on)" — [1999-July/000485](https://mail.python.org/pipermail/python-dev/1999-July/000485.html)
- `xrange()`: Skip Montanaro, 25 Jun 2001: "With generators in the language, should xrange be deprecated?" Guido: "No, but maybe xrange() should be changed to return an iterator", with a `yield`-based sketch. — [2001-June/015564](https://mail.python.org/pipermail/python-dev/2001-June/015564.html), [015568](https://mail.python.org/pipermail/python-dev/2001-June/015568.html)

### Inferences
- The `try`/`finally` ban and the bare `return` are both consequences of the "half a coroutine" choice: a generator could only send values out, so the caller had no way to tell an abandoned generator to clean up, and no channel back for a final value. Both restrictions were lifted later (PEP 342, PEP 380), which fits the later-PEP researchers' scope.

- `os.path.walk()` callbacks: I found no 1999-2001 python-dev message in the threads I read that names `os.path.walk()` as a motivation; treat any such claim as unverified.
- `xreadlines()`: a January 2001 python-dev thread is titled "[Patch #102915] xreadlines : readlines :: xrange : range" (Tim Peters, Guido, Neil Schemenauer participating), but I did not read it closely enough to quote a generator motivation from it. — [2001-January thread index](https://mail.python.org/pipermail/python-dev/2001-January/thread.html)
