## Ruby: blocks and `yield`, CLU, external enumerators, Fibers, `Enumerator::Lazy`

### Takeaway
Ruby's `yield` is CLU-style internal iteration (a method calls the caller's block), and Matz pointed at CLU as early as January 1996. Generator-style external iteration arrived with Ruby 1.9 (Fiber plus `Enumerator#next`, 2007-2009), and lazy pipelines with `Enumerator::Lazy` in Ruby 2.0 (2013). No verbatim "I took it from CLU" statement by Matz was found, only a 1996 mailing-list mention and a secondhand 2019 talk report.

### Cited Findings
- Matz, ruby-list:102, "TUTORIAL(iterater)", 1996-01-30: an iterator is a user-defined control structure, defined like a method that calls `yield`, and `yield` passes control to the block given to the iterator. On the idea not being unique to Ruby he writes "例えば一部で人気のあるCLUっていう言語にもある．" (literally: "For example, there is also one in a language called CLU, which is popular in some circles."). ([ruby-list:102](https://blade.ruby-lang.org/ruby-list/102))
- Secondhand report of a Matz talk (Cookpad gathering, Bristol, 2019): "Matz feels that blocks are the greatest invention of Ruby" and "He got the idea from a 1970s language called CLU" ... "from MIT, which called them "iterators" and only allowed them on certain loop constructs." This is the blogger's paraphrase, not a transcript. ([AppFolio Engineering, 2019](https://engineering.appfolio.com/appfolio-engineering/2019/7/3/rubys-roots-and-matzs-leadership))
- Matz interview with Bill Venners, 2003-12-22: "Basically, blocks are designed for loop abstraction."; "the methods called with blocks were referred to as iterators, because they were designed to iterate."; the role of blocks "was later enhanced from loop abstraction to anything."; on closures, "Lisp provided real closures, and I wanted to follow that." The interview names Lisp and does not name CLU. ([Artima, "Blocks and Closures in Ruby"](https://www.artima.com/articles/blocks-and-closures-in-ruby))
- Ruby 1.9.1 NEWS lists "Fiber: coroutines/micro-threads", "Enumerator.new { ... }", "Enumerator#with_object", "Enumerable#{map,collect} called without a block returns an enumerator.", "Even more builtin and bundled libraries have been made to return an enumerator when called without a block.", and under deprecations "generator library: use Enumerator." ([NEWS for Ruby 1.9.1](https://docs.ruby-lang.org/en/3.0/NEWS-1_9_1.html))
- Secondary source (Akinori Musha's "Evolution of Enumerator" slides, found through search): in August 2007 Enumerator became usable as an external iterator by using Ruby 1.9's Fiber to implement `next` and `rewind`; Ruby 1.9.0 shipped December 2007, 1.9.1 January 2009; `Enumerable#lazy` and `Enumerator::Lazy` were adopted in 2.0, February 2013. ([knu, "Evolution of Enumerator"](https://speakerdeck.com/knu/evolution-of-enumerator))
- Ruby 2.0.0 NEWS: added "a new class, Enumerator::Lazy for lazy enumeration", "Enumerable#lazy", and "Enumerator#size for lazy size evaluation". ([NEWS for Ruby 2.0.0](https://docs.ruby-lang.org/en/2.0.0/NEWS.html))
- Current Enumerator docs: `next` "returns the next value and increments the position."; `peek` "returns the next value but does not increment the position."; `rewind` "sets the position to zero."; `feed` "sets the value that is next to be returned."; at the end `next` "Raises StopIteration: iteration reached an end"; a conversion example reads `$!.result` from the `StopIteration`. External iteration "differs **significantly** from internal iteration.", "Using Fiber adds some overhead compared to internal enumeration.", and "The stacktrace will only include the stack from the Enumerator, not above." `Enumerator.new(size = nil) {|yielder| ... }` with `y << 42` is the generator-style constructor. ([class Enumerator](https://docs.ruby-lang.org/en/master/Enumerator.html))
- Rust RFC 3513's prior-art survey describes Ruby this way: "In Ruby, `yield` can be used with the Enumerator class to implement an iterator." and "Ruby also uses `yield` for a general coroutine mechanism with the Fiber class." ([Rust RFC 3513](https://rust-lang.github.io/rfcs/3513-gen-blocks.html))
- The Lua authors' 2004 paper explains what CLU iterators were, which is the model Ruby's block iterators follow: "The iterator abstraction was originally proposed and implemented by the designers of CLU [Liskov et al., 1977]. Because a CLU iterator preserves state between succesive calls, they described it as a coroutine. However, CLU iterators are not first-class objects, and are limited to a for loop construct that can invoke exactly one iterator." ([de Moura, Rodriguez, Ierusalimschy, "Coroutines in Lua", J.UCS 10(7), 2004](https://www.lua.org/doc/jucs04.pdf))

### Inferences
- Ruby had the CLU form (internal iteration, the producer drives) from its first releases in the mid-1990s, and gained the Python form (external, consumer-driven, resumable) only when Fibers made it possible to suspend a block-driven `each` in mid-flight. `Enumerator` is therefore a generator built on a stackful coroutine, the reverse of Python's path (generators first, coroutines grown out of them).
- Feature mapping: `Enumerator#feed` is a restricted two-way channel (it sets the value the pending `yield` returns); `StopIteration#result` carries the return value of the underlying `each`; `Fiber#resume(value)` and `Fiber.yield(value)` give full two-way transfer. There is no delegation keyword; `Enumerator::Lazy`, `Enumerator::Chain`, and nested `each` calls cover that ground.

### Gaps
- No primary source was found in which Matz says in so many words that `yield` or blocks were taken from CLU. The 1996 post only says CLU has iterators too. The claim is commonly attributed to "The Ruby Programming Language" (Flanagan and Matsumoto, 2008) and to Matz's talks; neither was checked.
- UNVERIFIED release dates: Ruby 1.9.0 on 2007-12-25, 1.9.1 on 2009-01-30, 2.0.0 on 2013-02-24. Only the month-level dates above come from a (secondary) source.
- UNVERIFIED: `Fiber#raise` (exception injection into a suspended fiber) arrived in Ruby 2.7 (December 2019); `Enumerator::Yielder#yield` and `#<<` date from 1.9; `Enumerator.produce` from 2.7; `Enumerator::Chain` from 2.6. Ruby has no explicit `close` for an enumerator; an abandoned fiber is collected, and `ensure` clauses in it are not guaranteed to run promptly.
- Ruby has no language-level async generator. Not researched further.

## Lua: asymmetric stackful coroutines in Lua 5.0 (2003)

### Takeaway
Lua 5.0 (released 11 April 2003) added full asymmetric, stackful, first-class coroutines, with generators as one application of them. The designers credit Scheme continuations as inspiration, Thatcher Ulrich's 2001 patch and Grim Fandango's cooperative multitasking as the route, and they explicitly call Python's generators "a restricted form of coroutines".

### Cited Findings
- Lua 5.0 was released on 11 April 2003; its main new features were "collaborative multithreading via Lua coroutines", full lexical scoping, and metatables. ([Lua version history](https://lua.org/versions.html))
- "The Evolution of Lua" (HOPL III, 2007), section 6.7: "For a long time we searched for some kind of first-class continuations for Lua. This search was motivated by the existence of first-class continuations in Scheme (always a source of inspiration to us) and by demands from game programmers for some mechanism for "soft" multithreading". ([Ierusalimschy, de Figueiredo, Celes, HOPL III](https://www.lua.org/doc/hopl.pdf))
- Same section: in December 2001 Thatcher Ulrich announced a Lua 4.0 patch making Lua-to-Lua calls non-recursive, with a `sleep()` call and a `lua_resume` API. "In other words, he proposed an asymmetric coroutine mechanism, based on two primitives: yield (which he called sleep) and resume. His patch followed the high-level description given in the mailing list by Bret Mogilefsky on the changes made to Lua 2.5 and 3.1 to add cooperative multitasking in Grim Fandango." ([HOPL III](https://www.lua.org/doc/hopl.pdf))
- Same section, on why asymmetric: "an asymmetric coroutine mechanism based on yield and resume manipulates partial continuations: yield captures the continuation up to the corresponding resume [19]. With asymmetric coroutines, the current continuation can include C parts, as long as they are outside the partial continuation being captured. In other words, the only restriction is that we cannot yield across a C call." ([HOPL III](https://www.lua.org/doc/hopl.pdf))
- Same section: "Unlike most implementations of asymmetrical coroutines, in Lua coroutines are what we call stackfull [19]. With them, we can implement symmetrical coroutines and even the call/1cc operator" and "We hope that the introduction of coroutines in Lua 5.0 marks a revival of coroutines as powerful control structures [18]." ([HOPL III](https://www.lua.org/doc/hopl.pdf))
- The HOPL paper's one CLU credit is for a different feature: "From CLU we took multiple assignment". ([HOPL III](https://www.lua.org/doc/hopl.pdf))
- "Coroutines in Lua" (submitted 16/2/04, appeared 28/7/04), on Python: "Python [Schemenauer et al., 2001] has recently incorporated a restricted form of coroutines that permits the development of simple iterators, or generators, but are not powerful enough to implement interesting features that can be written with true coroutines, including user-level multitasking. A similar mechanism is being proposed for Perl [Conway, 2000]. A different approach was followed by the designers of Lua, who decided on a full implementation of coroutines." ([de Moura, Rodriguez, Ierusalimschy, J.UCS 2004](https://www.lua.org/doc/jucs04.pdf))
- Same paper, section 4: "In Python [Schemenauer et al., 2001] a function that contains an yield statement is called a generator function. When called, a generator function returns a first-class object that can be resumed at any point in a program. However, a Python generator can be suspended only when its control stack is at the same level that it was at creation time; in other words, only the main body of a generator can yield." ([J.UCS 2004](https://www.lua.org/doc/jucs04.pdf))
- Same paper: "Python generators and similar constructs complicate the structure of recursive or more sophisticated generators. If items are produced within nested calls or auxiliary functions, it is necessary to create an hierarchy of auxiliary generators that "yield" in succession until the generator's original call point is reached. Moreover, this type of construct is far less expressive than true coroutines; for instance, it does not support the implementation of user-level multithreading." ([J.UCS 2004](https://www.lua.org/doc/jucs04.pdf))
- Same paper, on Sather and Icon: "Sather iterators [Murer et al., 1996], inspired by CLU iterators, are also confined to a single call point within a loop construct."; Icon "provides co-expressions, first-class objects that wrap an expression and an environment for its evaluation, so that the expression can be explicitly resumed at any place. Co-expressions are, actually, an implementation of asymmetric coroutines." ([J.UCS 2004](https://www.lua.org/doc/jucs04.pdf))
- Same paper, on Stackless Python: "The direct implementation of all these constructs clearly indicates that the language designer does not recognize the power of coroutines as a single unifying concept." ([J.UCS 2004](https://www.lua.org/doc/jucs04.pdf))
- Same paper, design reasons: "Since expressive power is not an issue, preserving two of the main characteristics of the Lua, simplicity and portability, constitutes the main reason for implementing asymmetric facilities." Also: "Lua coroutines are first-class values; they can be stored in variables, passed as arguments and returned as results." and "Lua provides a very convenient facility to allow a coroutine and its caller to exchange data. As we will see later, this facility is very useful for the implementation of generators". ([J.UCS 2004](https://www.lua.org/doc/jucs04.pdf))
- Same paper, conclusion: "Asymmetrical coroutines have equivalent power, are arguably easier to implement and fits nicely in procedural languages." ([J.UCS 2004](https://www.lua.org/doc/jucs04.pdf))
- Explicit close arrived in Lua 5.4: Roberto Ierusalimschy on lua-l, June 2020, says the goal of to-be-closed variables inside coroutines plus `coroutine.close` is to allow orderly kills of threads/coroutines. ([lua-l, 2020-06](https://lua-users.org/lists/lua-l/2020-06/msg00223.html); [Lua 5.4 Reference Manual](https://www.lua.org/manual/5.4/manual.html))
- Russ Cox (2023) on the same contrast: "Python provides generators that look a lot like Lua's coroutines, but they are not coroutines" and "Generators provide less power than coroutines, because only the top-most frame in the coroutine is allowed to yield." ([Cox, "Coroutines for Go"](https://research.swtch.com/coro))

### Inferences
- The 2004 paper's complaint about "an hierarchy of auxiliary generators that 'yield' in succession" is the problem Python later answered with `yield from` (PEP 380, 2009). Lua never needed delegation syntax, because any function called from the coroutine body can yield.
- The paper was written against PEP 255 generators (2001), before PEP 342 (2005) added `send()`. Lua's `resume`/`yield` passed values both ways from 5.0 in 2003, two years ahead of Python.
- Lua's lineage is Scheme continuations and Simula/BCPL-style coroutines, not CLU iterators. It is the clearest case in this survey of the "coroutines first, generators as a library pattern" branch.

### Gaps
- UNVERIFIED: Lua 5.4.0 release date (recalled as 29 June 2020; only the 2020 manual copyright and the June 2020 list post were seen).
- UNVERIFIED: Lua has no direct exception-injection operation on a suspended coroutine (no `throw`); errors inside a coroutine surface as a `false, message` result from `coroutine.resume`. `coroutine.wrap` (5.0) gives the generator-function form. `coroutine.isyieldable` (5.3) and yield across pcall/metamethods (5.2, 2011) were not checked.
- Lua has no generator expressions and no async generators as language features. Not researched further.

## PHP: Generators RFC (5.5), Generator Delegation and Return Expressions (7.0)

### Takeaway
PHP is the best-documented case of direct borrowing from Python: Nikita Popov's 2012 RFC links PEPs 255, 289, 342, 380, and 3152 and shipped `send()` and `throw()` from day one, and the two 2015 RFCs by Daniel Lowrey cite Python 3.3's `yield from` and return values and JavaScript ES6's `yield*` as precedent.

### Cited Findings
- "PHP RFC: Generators": author Nikita Popov, created 2012-06-05, status Implemented, vote 24 yes to 1 no, with vote entries dated 2012-08-25 to 2012-08-31. ([wiki.php.net/rfc/generators](https://wiki.php.net/rfc/generators))
- Language citations in that RFC: "There is an existing generator implementation in HipHop PHP, which uses automatic-detection."; "All existing generator implementations in other language (that I know of) also use automatic detection."; "This includes Python, JavaScript 1.7 and C#."; "The only exception to this is the generator support as defined by ECMAScript Harmony,"; "Python also has parentheses requirements for expression-use of `yield`."; "The languages that currently implement generators don't have support for yielding keys (only values)." ([wiki.php.net/rfc/generators](https://wiki.php.net/rfc/generators))
- Its reference list links "Implementation in Python", "Implementation in JavaScript", "Implementation in C#", "Generators in ECMAScript Harmony", "Implementation in SpiderMonkey (not conforming with Harmony)", and PEPs 255, 289, 342, 380, and 3152. Ruby and Lua are not mentioned. ([wiki.php.net/rfc/generators](https://wiki.php.net/rfc/generators))
- A deliberate departure from Python: "A nice side-effect of this behavior is that coroutines do not have to be primed with a `next()` call before they can be used." The parenthetical says priming "is required in Python" and that Python coroutines "usually use some kind of decorator that automatically primes the coroutine." ([wiki.php.net/rfc/generators](https://wiki.php.net/rfc/generators))
- Methods specified: `rewind()`, `valid()`, `current()`, `key()`, `next()`, `mixed send(mixed $value)`, `mixed throw(Exception $exception)`. "The return value of the `yield` expression is whatever was sent to the generator using `send()`." "The `throw()` method will return the next yielded value (if the exception is caught and no other exception is thrown)." ([wiki.php.net/rfc/generators](https://wiki.php.net/rfc/generators))
- Coroutine framing: "Generators can also be used the other way around, i.e. instead of producing values they can also consume them." "When used in this way they are often referred to as enhanced generators, reverse generators or coroutines." ([wiki.php.net/rfc/generators](https://wiki.php.net/rfc/generators))
- Return and close in the 5.5 design: "Using `return` with a value inside a generator: `E_COMPILE_ERROR`". There is no `close()` method; a generator closes on return, on an uncaught exception, or when the last reference goes, in which case "the generator will be closed as part of the garbage collection process." "If the generator contains (relevant) `finally` blocks those will be run.", and on forced closure "it is not allowed to use `yield` in the `finally` clause." Cloning support was "removed in PHP 5.5 Beta 3." ([wiki.php.net/rfc/generators](https://wiki.php.net/rfc/generators))
- "PHP RFC: Generator Delegation": author Daniel Lowrey, contributor Bob Weinand, version 0.2.0 dated 2015-03-01, vote 25 yes to 0 no (through 2015-03-29), status "Implemented in 7.0". ([wiki.php.net/rfc/generator-delegation](https://wiki.php.net/rfc/generator-delegation))
- Its citations: "Other popular dynamic languages currently support variants of the proposed syntax ..."; "Python 3.3 generators support the `yield from` syntax:"; "Javascript ES6 generators support the `yield*` syntax:"; references "New in Python 3.3: yield from" (PEP 380) and "JavaScript yield* Syntax". HHVM/Hack is not mentioned. ([wiki.php.net/rfc/generator-delegation](https://wiki.php.net/rfc/generator-delegation))
- Semantics: `yield from <expr>` accepts a generator, any `Traversable`, or an array; keys pass through unchanged (duplicates possible); values sent to the outer generator go to the subgenerator's `send()`; exceptions are forwarded with `throw()`; the subgenerator's return value becomes the value of the `yield from` expression (`null` for arrays and non-generator traversables). ([wiki.php.net/rfc/generator-delegation](https://wiki.php.net/rfc/generator-delegation))
- "PHP RFC: Generator Return Expressions": author Daniel Lowrey, contributor Nikita Popov, version 0.1 dated 2015-02-18, voting 2015-03-09 to 2015-03-16, 33 yes to 0 no, implemented in PHP 7.0. ([wiki.php.net/rfc/generator-return-expressions](https://wiki.php.net/rfc/generator-return-expressions))
- Its citations: "Other popular dynamic languages currently support generator return expressions ..."; section "Generator Returns in Python": "Python 3.3 added the ability to return expressions in sub-generators and have these results returned to the parent generator."; section "Generator Returns in Javascript": "Javascript ES6 generators yield objects with a `value` property enumerating the yielded value" and "a boolean `done` property to indicate when iteration has completed:". ([wiki.php.net/rfc/generator-return-expressions](https://wiki.php.net/rfc/generator-return-expressions))
- `Generator::getReturn()` returns the `return` value after completion (`null` with no `return`), and throws an exception if the generator is still running or ended by throwing. ([wiki.php.net/rfc/generator-return-expressions](https://wiki.php.net/rfc/generator-return-expressions))

### Inferences
- PHP took Python's three-step history (PEP 255, PEP 342, PEP 380) in two steps: `yield` plus `send()`/`throw()` together in 5.5, then return values and `yield from` together in 7.0. PHP never had the plain-iterator-only stage.
- Two PHP divergences from Python are stated in the RFCs: no priming call before the first `send()`, and yielded keys (`yield $k => $v`). PHP exposes the return value through a method (`getReturn()`) where Python carries it on `StopIteration`.
- PHP has no generator expression. The 2012 RFC links PEP 289 but proposes no such syntax.

### Gaps
- UNVERIFIED release dates: PHP 5.5.0 on 2013-06-20, PHP 7.0.0 on 2015-12-03. The generators RFC page itself does not name the version.
- PHP has no native async generators (the ecosystem builds async on generators or Fibers, PHP 8.1, 2021). Not researched; UNVERIFIED.
- Whether `send()`/`throw()` forwarding edge cases in `yield from` match PEP 380 exactly was not compared.

## F#: sequence expressions, `yield!`, computation expressions, async workflows

### Takeaway
F# `seq { ... }` with `yield` and `yield!` is a comprehension notation, generalized in 2007 into computation expressions whose first use was `async { ... }` (announced 10 October 2007). Syme credits Haskell (monads, `do` notation, list comprehensions, "Comprehensive Comprehensions"), the OCaml community, Scala's `react`, and C# 2.0 iterators' "implicit inversion of control-flow", and claims the reverse influence on C# 5.0 async/await.

### Cited Findings
- Syme, "The Early History of F#" (HOPL IV, 2020), section 9.7: "In April 2007, I spent a six-week sabbatical at EPFL with Martin Odersky in Lausanne. ... Partly through this visit another important idea was seeded and eventually added to the core F# design: computation expressions and their application to asynchronous programming. This would still be influencing C# years later, in C# 5.0 (async/await) and 8.0 (async sequences), and in turn influence many other languages." ([HOPL IV paper](https://fsharp.org/history/hopl-final/hopl-fsharp.pdf))
- Same section: "At EPFL in 2007, I noticed that Philipp Haller had added a react { ... } construct for message processing in Scala [Haller and Odersky 2009], and realized that some kind of primitive construct to deal with asynchronous programming was going to be needed in F#. C# had added "iterators" in C# 2.0 (again initiated by MSR) and this also featured an implicit inversion of control-flow which was of interest in the context of async programming." ([HOPL IV paper](https://fsharp.org/history/hopl-final/hopl-fsharp.pdf))
- Same section: "Ideas around async programming had also been floating around the OCaml community and its mailing lists, especially through the async implementation used in the system MLDonkey by Fabrice le Fessant, begun in 2001 ... Haskell had added monadic syntax. At that time, however, no strict functional language had a suitable extensible syntax allowing the re-interpretation of all control constructs in asynchronous form". ([HOPL IV paper](https://fsharp.org/history/hopl-final/hopl-fsharp.pdf))
- Same section: "On returning from EPFL, I discussed these problems with Margetson around May 2007, who emphasized the importance of monads in implementing async programming. This led me to finally experiment with adding a monadic syntax to F# and apply it to asynchronous programming, leading to the addition of async { ... } to F# in 2007 [Syme et al. 2011]. On October 10, 2007 we announced these features in the blog post Introducing F# Asynchronous Workflows [Syme 2007b]." ([HOPL IV paper](https://fsharp.org/history/hopl-final/hopl-fsharp.pdf))
- Section 9.8: "F# computation expression notation began with "async", however other important background included Haskell list comprehension syntax [Haskell Contributors 2019], Haskell "do notation" [Haskell Contributors 2020a] and Haskell's experimental "arrow" syntax [Paterson 2020]. In Haskell these are separate syntactic mechanisms. Other background includes C# LINQ expressions [Microsoft 2019]". ([HOPL IV paper](https://fsharp.org/history/hopl-final/hopl-fsharp.pdf))
- Section 9.8 on Wadler and Peyton Jones's "Comprehensive Comprehensions" (2007): "This paper (and my own 1:1 discussions with Peyton Jones at Microsoft Research during 2004-2010) had a significant influence on the development of F# CEs and the range of expression they needed to cover." ([HOPL IV paper](https://fsharp.org/history/hopl-final/hopl-fsharp.pdf))
- Section 9.8, the desugaring table: `yield` "requires Yield method"; `yield!` "requires YieldFrom method". For comprehension-style builders, "The MonadPlus return corresponds to yield syntax and de-sugars to the Yield method" and sequential composition "de-sugars to the Combine method". "The minimum needed to warrant the name "comprehension" is For and Yield." The `seq` builder is described as "the "seq" computation expression, for (on-demand) sequence comprehensions." ([HOPL IV paper](https://fsharp.org/history/hopl-final/hopl-fsharp.pdf))
- Section 9.8 on design ethos: "To achieve ease-of-transition, F# emphasises notational similarity between regular code, list comprehensions and asynchronous code. In contrast, the design of C# LINQ notation, Haskell list comprehensions and Haskell do-notation all emphasise notational difference". ([HOPL IV paper](https://fsharp.org/history/hopl-final/hopl-fsharp.pdf))
- Syme's archived blog post on computation expressions says they generalize the sequence expressions added in F# 1.9.1, and maps `yield expr` to `Seq.singleton`. (Seen through a search summary, not read in full.) ([Syme, "Some Details on F# Computation Expressions"](https://learn.microsoft.com/en-us/archive/blogs/dsyme/some-details-on-f-computation-expressions))
- A forum reply signed by Don Syme advises using `yield`/`yield!` instead of `->` and `->>` in sequence expressions of any real size, which shows `->>` as the earlier spelling of `yield!`. (Search summary; forum post, undated in the result.) ([fpish.net topic 57733](https://fpish.net/topic/None/57733))
- Petricek and Syme (2014) state that computation expressions have been available in F# since 2007. (Search summary.) ([Petricek and Syme, "The F# Computation Expression Zoo"](https://tomasp.net/academic/papers/computation-zoo/syntax-matters.pdf))
- Rust RFC 3513's survey: "In F#, generators can be expressed with sequence expressions using `yield`." ([Rust RFC 3513](https://rust-lang.github.io/rfcs/3513-gen-blocks.html))

### Inferences
- F# had a delegation form (`yield!`, earlier `->>`) in its sequence expressions by 2007, about two years before PEP 380 was written (2009) and five before Python 3.3 shipped it (2012). The route was different: `yield!` is the comprehension's "splice a whole sequence here" (`YieldFrom`, in effect `Seq.collect`/append), not a channel-forwarding protocol, because `seq` has no `send`, no `throw`, and no return value to forward.
- The HOPL account makes F# the hinge between two families: Haskell's monadic and comprehension notations on one side, and the C# 5.0 `async`/`await` design (and through it Python, JavaScript, Dart, Kotlin, Rust, Swift) on the other. Syme names C# 2.0 iterators as one input, so the influence between C# and F# ran in both directions.
- A `seq { }` block is lazy and restartable (an `IEnumerable`), so it also plays the role of a generator expression. `try/finally` and `use` inside it give deterministic cleanup through `IDisposable` on the enumerator.

### Gaps
- The exact release and date that introduced `seq { ... }`, `yield`, and `yield!` were not confirmed in a primary source. UNVERIFIED recall: F# 1.9.1 shipped in the first half of 2007, and earlier 1.1.x releases (2006) had `{ for x in xs -> e }` sequence comprehensions with `->` and `->>`. The HOPL paper does not date `yield!`.
- Async sequences in F#: `AsyncSeq` is a library (Petricek, around 2011), and `taskSeq` targets .NET `IAsyncEnumerable`. UNVERIFIED, not researched.
- No statement by Syme crediting Python was found; the HOPL paper's credits for this feature are Haskell, OCaml, Scala, and C#.

## Dart: `sync*`, `async*`, `yield`, `yield*` (Dart 1.9, March 2015)

### Takeaway
Dart 1.9 (March 2015) shipped four function kinds at once: plain, `async`, `sync*` (returns `Iterable`), and `async*` (returns `Stream`), with `yield` and the delegating `yield*`. The announcement credits no other language, and the design paper that would hold the credits (Meijer, Millikin, Bracha, 2015) could not be fetched.

### Cited Findings

## Kotlin: `sequence { yield(); yieldAll() }` on general coroutines

### Takeaway
Kotlin put one general mechanism in the language (suspending functions, experimental in 1.1, stable in 1.3 on 29 October 2018) and made generators a library function over it, restricted so that a sequence body can only suspend through `yield`/`yieldAll`. The design document cites C# and Python for `yield`, C# and JS for async/await, Go for channels, and Haskell for lazy lists.

### Cited Findings
- KEEP "Coroutines for Kotlin": authors Andrey Breslav and Roman Elizarov; contributors Vladimir Reshetnikov, Stanislav Erokhin, Ilya Ryzhenkov, Denis Zharkov; status "Stable since Kotlin 1.3 (Revision 3.3), experimental in Kotlin 1.1-1.2". ([KEEP coroutines.md](https://github.com/Kotlin/KEEP/blob/master/proposals/coroutines.md))
- Its language citations (fragments, as fetched): generators are "lazily computed sequences (handled by `yield` in C#, Python" ... "and many other languages"; asynchronous computations are "(handled by async/await in C# and other languages)"; futures work "like `async` and `await` in C#, JS and other languages"; a use case is "Channel-based concurrency (aka goroutines and channels);"; "Go-style type-safe channels can be implemented in Kotlin as a library."; lazy sequences behave "exactly like [Haskell's infinite lists]"; terminology refers to "first-class delimited continuations in functional languages like Scheme or continuation monad in Haskell"; "JS, Python and many other languages do not have threads". Dart, F#, Lua, and Scala are not mentioned. ([KEEP coroutines.md](https://github.com/Kotlin/KEEP/blob/master/proposals/coroutines.md))
- On sequences: "Another typical use case for coroutines would be lazily computed sequences"; "Note that this approach also allows to express `yieldAll(sequence)` as a library function"; generators "work _synchronously_." and "form _restricted suspension scope_."; "`sequence{}` and `yield()`, as shown above, are not ready for an arbitrary suspending function"; the `@RestrictsSuspension` annotation "enforces certain restrictions on suspending functions that can be used in the" scope. ([KEEP coroutines.md](https://github.com/Kotlin/KEEP/blob/master/proposals/coroutines.md))
- Kotlin 1.1 "What's new": "The key new feature in Kotlin 1.1 is coroutines, bringing the support of `async`/`await`, `yield`, and similar programming patterns."; "The key feature of Kotlin's design is that the implementation of coroutine execution is part of the libraries, not the language, so you aren't bound to any specific programming paradigm or concurrency library."; "The standard library uses coroutines to support lazily generated sequences with `yield` and `yieldAll` functions." The 1.1 example uses `buildSequence { ... yield(i * i) ... yieldAll(26..28) }`. ([What's new in Kotlin 1.1](https://kotlinlang.org/docs/whatsnew11.html))
- Kotlin 1.3 was released 29 October 2018 with coroutines stable ("Coroutines are now stable") and kotlinx.coroutines 1.0. ([JetBrains blog, Kotlin 1.3](https://blog.jetbrains.com/kotlin/2018/10/kotlin-1-3/); [What's new in Kotlin 1.3](https://kotlinlang.org/docs/whatsnew13.html))
- Rust RFC 3513's survey: "In Kotlin, a lazy Sequence can be built using `sequence` expressions and `yield`." ([Rust RFC 3513](https://rust-lang.github.io/rfcs/3513-gen-blocks.html))

### Inferences
- Kotlin inverts the Python and C# order of construction. Python grew coroutines out of generators (PEP 342, PEP 380, PEP 492). Kotlin specified continuation-passing suspend functions once and derived generators (`sequence`), async/await (`async`/`await()`), and Go-style channels as libraries. The KEEP's "use cases" list reads as a catalogue of what other languages had built as separate features.
- `yieldAll` is delegation as an ordinary library function, which the KEEP points out ("allows to express `yieldAll(sequence)` as a library function"). It needs no keyword because nested suspension is general.
- The asynchronous generator in Kotlin is the `flow { emit(x) }` builder in kotlinx.coroutines, again a library.

### Gaps
- Kotlin 1.1 release date: the fetched docs page reported "Released: 15 February 2016", which is Kotlin 1.0's date and looks like a fetch or page error. The JetBrains announcement URL (`blog.jetbrains.com/kotlin/2017/03/kotlin-1-1/`) returned HTTP 403; its path implies March 2017. UNVERIFIED recall: 1 March 2017.
- UNVERIFIED: `buildSequence`/`buildIterator` were renamed `sequence`/`iterator` in 1.3; `Flow` became stable in kotlinx.coroutines 1.3.0 (2019). Kotlin sequences are one-way (no send, no throw into the body, no return value); an abandoned sequence continuation is simply collected, so `finally` in the body is not guaranteed to run.
- No Elizarov or Breslav statement beyond the KEEP was read (talks such as "Kotlin Coroutines Reloaded" or Elizarov's Medium posts were not fetched).

## Rust: unstable coroutines, the `Coroutine` rename, `gen` blocks (RFC 3513)

### Takeaway
As of the tracking issue's state in August 2026, Rust still has no stable generator syntax: stackless coroutines have been nightly-only since RFC 2033 (2017) and exist to implement `async`/`await`; the `Generator` trait was renamed `Coroutine` in October 2023; `gen` blocks (RFC 3513) are implemented on nightly, with `gen` reserved as a keyword in the 2024 edition, and unstabilized. RFC 3513 has the most thorough prior-art section of any document in this survey.

### Cited Findings
- RFC 2033 "experimental coroutines": start date 2017-06-15, tracking issue rust-lang/rust#43122. It is "explicitly an experimental RFC and is not intended to be a reference for stability." Motivation is async I/O: "Syntax like async/await is essentially the defacto standard nowadays when working with async I/O," "especially in languages like C#, JS, and Python." It also mentions C++: ""Resumable expressions" is a proposal in C++ which attempts to deal with some of the "viral" concerns of async/await," and notes "As a reference point @Zoxc has implemented generators in a fork of rustc,". Its strawman uses a `Coroutine` trait with `resume` and a status enum with `Yield` and `Return` variants. ([Rust RFC 2033](https://rust-lang.github.io/rfcs/2033-experimental-coroutines.html))
- Inside Rust blog, oli-obk, 2023-10-23, "Generators are dead, long live coroutines, generators are back": "We have renamed the unstable `Generator` trait to `Coroutine` and adjusted all terminology accordingly." (PR #116958). "Our `Generator` trait was effectively a coroutine already." The rename is "directly motivated for _reintroducing_ generators, this time with simpler (`async`/`await` style) syntax for creating `Iterator`s." The `gen` block MVP is PR #116447 and "has very weird diagnostics and may panic on you if you poke it too much." ([Inside Rust, 2023-10-23](https://blog.rust-lang.org/inside-rust/2023/10/23/coroutines/))
- RFC 3513 "gen blocks": start date 2023-10-10, tracking issue rust-lang/rust#117078. `gen { ... }` produces an `Iterator`; the body must evaluate to unit or `!`; there are no resume arguments; holding a borrow of a local across a `yield` is an error (listed as a severe limitation and open question); `async gen` and a `yield from` are left to future work. `gen` is a reserved keyword in the 2024 edition (`r#gen` for old identifiers, `k#gen` from 2021). ([Rust RFC 3513](https://rust-lang.github.io/rfcs/3513-gen-blocks.html))
- RFC 3513 prior art, on origins: "The idea of generators that yield their values goes back at least as far as the Alphard language from circa 1975"; "This was later refined into the idea of iterators in the CLU language"; "The CLU language opened an iterator context with the `iter` keyword and produced values with `yield` statements."; "In Icon (introduced circa 1977), generators are woven deeply into the language". ([Rust RFC 3513](https://rust-lang.github.io/rfcs/3513-gen-blocks.html))
- RFC 3513 prior art, on current languages: "In Python, any function that contains a `yield` statement returns a generator."; "In JavaScript, `yield` can be used within `function*` generator functions." "These generator functions are general coroutines."; "In C#, within an iterator, the yield statement is used to either yield the next value or to stop iteration."; "In D, `yield` is used when constructing a Generator." "As in Ruby, generators in D are built on top of a more general Fiber class that also uses `yield`."; "In Racket, generators can be built using generator and `yield`."; "In Haskell (and in similar languages such as Idris, Clean, etc.), all functions are lazy unless specially annotated." "Consequently, Haskell does not need a special `yield` operator."; "The Koka language, by contrast, does not lean on laziness." "Unlike Scheme, these powerful control flow constructs are _typed_ and are called effect handlers." Under future possibilities: "Python has the ability to `yield from` an iterator." ([Rust RFC 3513](https://rust-lang.github.io/rfcs/3513-gen-blocks.html))
- Tracking issue #117078 (read 2026-11-11): open, labeled B-RFC-approved, project status "Accepted RFC" since 2025-03-04, no stabilization PR linked. History: gen blocks PR #116447 merged 2023-10-29; "async-gen" PR #118420 merged 2023-12-08; `gen fn` PR #118457 listed; `FusedIterator` PR #122829 on 2024-04-18. Unresolved questions include whether `gen {}` should implement `Iterator` or `IntoIterator`, self-referential gen blocks, the keyword choice, and two soundness issues (#159443, #161026). On 2025-01-14 yoshuawuyts argued that returning `Iterator` leaks the body's locals into auto-traits. Last recorded change: retitled 2026-08-08. ([rust-lang/rust#117078](https://github.com/rust-lang/rust/issues/117078))
- The 2024 edition shipped with Rust 1.85 in February 2025, and the edition guide says the `gen` reservation is meant to make stabilizing gen blocks easier later. ([Rust Edition Guide, gen keyword](https://doc.rust-lang.org/nightly/edition-guide/rust-2024/gen-keyword.html))
- `gen_blocks` is still listed as an unstable feature. ([Rust Unstable Book, gen_blocks](https://doc.rust-lang.org/unstable-book/language-features/gen-blocks.html))

### Inferences
- Rust is the one language here where async/await (stable in 1.39, November 2019, UNVERIFIED date) preceded generators by more than seven years and counting, although both compile through the same coroutine transform. The obstacle RFC 3513 names is Rust-specific: a generator that borrows its own locals across a `yield` is self-referential, and `Iterator::next` takes `&mut self`, not a pinned reference.
- The unstable `Coroutine` trait is the full-featured form: resume arguments (two-way send) and distinct yield and return types. `gen` blocks deliberately drop both, making them closer to C# iterators than to Python generators.
- Cleanup follows from ownership: dropping a suspended generator runs the destructors of its live locals, so no `close()` method exists or is needed. There is no exception injection, since Rust has no exceptions.

### Gaps
- The `async-stream` crate (the `stream!` macro, tokio project) and `genawaiter` were named in the brief and not researched. UNVERIFIED: `async-stream` gives `yield` inside a macro on stable Rust and predates gen blocks.
- UNVERIFIED: the `Coroutine` trait's present signature (`resume(self: Pin<&mut Self>, arg: R) -> CoroutineState<Y, Return>`), and the date resume arguments landed (2020).
- No source newer than the tracking issue (August 2026 retitle) was found. A stabilization between then and 2026-11-11 is unlikely and was not excluded by a release-notes check.

## C++: C++20 coroutines (`co_yield`) and C++23 `std::generator`

### Takeaway
C++ coroutines came from Microsoft: Gustafsson, Brewer, and Sutter's "Resumable Functions" (N3858, January 2014) and Nishanov and Radigan's v2 (N4134, October 2014), which became the Coroutines TS and C++20. N3858 names C# and Python as the languages with generator functions, and N4134 cites PEP 289 for generator expressions. C++20 shipped only the mechanism; the library generator arrived in C++23 as `std::generator` (P2502), with built-in recursive delegation through `co_yield ranges::elements_of(...)`.

### Cited Findings
- N3858 "Resumable Functions", 2014-01-19, Niklas Gustafsson, Deon Brewis, Herb Sutter (all Microsoft), supersedes N3722: "What we desire is the ability to produce each value of the sequence when it's needed but no sooner, i.e. lazily. Generator functions, a concept available in languages like C# and Python, address this need elegantly and efficiently. Writing general lazy sequence generator is surprisingly hard without language support and surprisingly simple with it. With a couple of minor modifications to the resumable functions definition, they could be available in C++, too." ([WG21 N3858](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2014/n3858.pdf))
- N4134 "Resumable Functions v.2", 2014-10-10, Gor Nishanov and Jim Radigan (Microsoft), supersedes N3977. Under "Resumable lambdas as generator expressions": "Resumable lambdas can be used as generator expressions [PythonGeneratorExpressions]." with the pair `squares = (x*x for x in S) // python` and `auto squares = [&]{ for(x:S) yield x*x;} ; // C++`. A later heading reads "C++ does not need generator expressions... it already has them!" and the text says "Python's generator expression can be trivially written in C++". The reference list includes "[PythonGenExprs] http://legacy.python.org/dev/peps/pep-0289/" and "[GoLang]". ([WG21 N4134](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2014/n4134.pdf))
- N4134 already shows `generator<int> fib(int n)`, a `recursive_generator<int>` ("Recursive application of generators allows to mitigate stackless coroutine inability to suspend from" nested calls, with `yield range(a, mid);`), and an `async_generator<int> Ticks()`. It states its abstractions expose "high-level semantics, such as generators, goroutines, tasks and more." At this stage the keywords were `await` and `yield`. ([WG21 N4134](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2014/n4134.pdf))
- Nishanov's later paper P1362R0 (2018) notes the Coroutines TS was earlier known as "resumable function v2 [N4134]" and discusses merging the TS into C++20. (Search summary.) ([P1362R0](https://isocpp.org/files/papers/p1362r0.pdf))
- P2502R2 "std::generator: Synchronous Coroutine Generator for Ranges", Casey Carter, 2022-06-03: "We propose a standard library type std::generator which implements a coroutine generator that models std::ranges::input_range." Acknowledgement: "I'd like to thank Lewis Baker and Corentin Jabot, whose P2168 [3] I looted shamelessly for this proposal." ([WG21 P2502R2](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2022/p2502r2.pdf))
- P2502R2 motivation: "C++ 20 had very minimalist library support for coroutines. Synchronous generators are an important use case for coroutines, one that cannot be supported without the machinery presented in this paper. Writing an efficient recursive generator is non-trivial; the standard should provide one." ([WG21 P2502R2](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2022/p2502r2.pdf))
- P2502R2 on delegation: "A "recursive generator" is a coroutine that supports the ability to directly co_yield a generator of the same type as a way of emitting the elements of that generator as elements of the current generator." The form is `co_yield std::ranges::elements_of(visit(*tree.left));`. "The recursive form can be implemented efficiently with symmetric transfer." The non-recursive form (a `for` loop re-yielding each element) "incurs O(depth) resumptions/suspensions per element". `elements_of` also accepts an arbitrary range. ([WG21 P2502R2](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2022/p2502r2.pdf))
- P2502R2 prior implementations: "generator has been provided as part of cppcoro and folly. However, cppcoro offers a separate recursive_generator type, which is different than the proposed design." "Folly uses a single generator type, which can be recursive but doesn't implement symmetric transfer." "ranges-v3 also implements a generator type, which is never recursive". The paper names no other programming language as an influence. ([WG21 P2502R2](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2022/p2502r2.pdf))
- cppreference: `std::generator` is "(since C++23)", header `<generator>`; "The class template `std::generator` presents a view of the elements yielded by the evaluation of a coroutine."; "`std::generator` models view and input_range."; feature macro `__cpp_lib_generator` = `202207L`, "synchronous coroutine generator for ranges"; "When the `co_yield` statement is of the form `co_yield ranges::elements_of(rng)`, each element of the range `rng` is successively produced as an element of the sequence." The promise type has `return_void` only: no input channel and no return value. ([cppreference, std::generator](https://en.cppreference.com/w/cpp/coroutine/generator))

### Inferences
- The Python citation in the C++ record is specific and narrow: PEP 289 generator expressions, plus "languages like C# and Python" for generator functions. The `await` half of the design descends from C# 5.0 through Microsoft's own teams (the N3858 authors); that descent is well known and was not found stated in the two papers read.
- `elements_of` is C++'s `yield from`, added 10 years after PEP 380 and for a different stated reason: efficiency (symmetric transfer makes nested yields O(1) per element instead of O(depth)), and disambiguation (a generator of generators must be able to yield a generator as a value). It forwards values only; `std::generator` has no send, throw, or return to forward.
- The core language mechanism is more general than the library type: `co_yield expr` is itself an expression whose value comes from the promise's `yield_value` awaiter, and `co_return v` can deliver a result, so a user-written coroutine type can implement two-way send and return values. `std::generator` chooses not to.
- Destroying a `std::generator` destroys the suspended coroutine frame and runs destructors of its locals (RAII), which is the explicit-finalization story; an exception thrown inside the body propagates out of the consumer's iterator increment.

### Gaps
- UNVERIFIED dates: Coroutines TS published 2017; merged into the C++20 working draft at the Cologne meeting, July 2019 (keywords `co_await`, `co_yield`, `co_return`); C++20 published December 2020; P2502 adopted for C++23 in July 2022 (consistent with the `202207L` macro, which was verified). MSVC shipped an experimental `/await` implementation in Visual Studio 2015.
- No statement by Gor Nishanov crediting C# `await`, or explaining the `co_` prefix, was read this session.
- C++ has no standard async generator as of C++23/26 (UNVERIFIED for C++26); `std::execution` (P2300) and third-party `async_generator` types (cppcoro) cover that ground.

- Earlier constructs cited by in-scope sources: Alphard generators (circa 1975), CLU iterators with `yield`, and Icon generators (circa 1977) per ([Rust RFC 3513](https://rust-lang.github.io/rfcs/3513-gen-blocks.html)); Sather iterators "inspired by CLU iterators" and Icon co-expressions per ([J.UCS 2004](https://www.lua.org/doc/jucs04.pdf)).

### Inferences
- Go is the notable holdout by design. The 2024 feature is CLU's model (the iterator calls a `yield` function, the loop body is the callee), stated as such in the Go blog. The pull form is derived through a coroutine (`iter.Pull` with an explicit `stop`), the reverse of Python, where pull is native and push is absent.
- Swift is the one modern language with async sequences and no synchronous generator. `AsyncStream` is a push-style bridge (a continuation's `yield`), not a suspended function body.
- Three in-scope primary sources independently trace `yield` to CLU: the Lua paper (2004), Cox for Go (2023), and Rust RFC 3513 (2023). Cox goes furthest ("almost exactly copied from CLU") about Python.

### Gaps
- Java: not researched beyond Cox's remark. UNVERIFIED: Java has no generator syntax; virtual threads (Project Loom) were finalized by JEP 444 in JDK 21 (September 2023); the underlying `Continuation` class is internal (`jdk.internal.vm`), so generators over Loom are unofficial; lazy `Stream` (Java 8, 2014) with `Stream.iterate`/`generate` is the standard substitute.
- Scala: not researched. UNVERIFIED: no native generators; lazy `Stream`/`LazyList` and `Iterator` cover the use; the delimited-continuations compiler plugin (`shift`/`reset`, Scala 2.8, 2010) allowed generator libraries and was later dropped; Scala 3 direct-style work (project Gears/Caprese) is experimental. Note that Scala's `for ... yield` is a comprehension, not a generator.
- Haskell: `conduit` and `pipes` (named in the brief) were not researched. UNVERIFIED: both are streaming libraries from around 2011-2012 that make `yield`/`await` explicit monadic operations with deterministic resource cleanup, which lazy lists cannot give.
- R: not researched. UNVERIFIED: base R has no generators; the `coro` package (Lionel Henry, CRAN around 2020-2021) provides `generator()` with `yield()` and async functions, and credits Python and JavaScript in its documentation.
- Raku: the history of `gather`/`take` (its origin in the Perl 6 Synopses, and Damian Conway's Perl 5 `Perl6::Gather` module, 2005) was not sourced. Whether `gather` is lazy by default depends on context per a Stack Overflow answer seen only in summary.
- Hack: the HHVM version and date that introduced async generators (recalled as 2014-2015) were not found. If 2014, Hack predates Dart 1.9 for async generators.
- Julia: the version where Channel-based generators (`Channel() do c ... end`) became the documented idiom (0.6, 2017) is from the commit and forum thread, not release notes.
- Other candidates for "notable firsts" that were not researched: Sather `iter` (1990s), Icon/Unicon, Scheme `call/cc` generators, OCaml 5 effect handlers (2022), Zig's removed async frames, Nim `iterator`, Elixir `Stream`, Clojure lazy seqs and `core.async`.

## Feature matrix: send, throw, close, return value, delegation, lazy comprehensions, async generators

### Takeaway
Outside Python and JavaScript, only PHP reproduces the full PEP 342/380 set (two-way `send`, `throw`, return value, `yield from`), and it copied it by citation. Lua and Ruby get two-way transfer from general coroutines; F#, Dart, Kotlin, C++ `std::generator`, and Rust `gen` blocks are one-way iterators with a delegation form; Dart, Kotlin, Hack, Swift, and (on nightly) Rust have async generators.

### Inferences
- Timeline of delegation forms, from the dated sources above: Lua 5.0 (April 2003, no syntax needed); F# `yield!` (by 2007); [Python PEP 380 written 2009, shipped in 3.3, 2012, per the PHP RFC's "Python 3.3" citations]; Dart `yield*` (March 2015); PHP `yield from` (voted March 2015, in 7.0); Kotlin `yieldAll` (1.1 experimental, stable October 2018); C++ `elements_of` (paper June 2022, C++23); Rust (still future work in RFC 3513).
- Two-way send outside Python and JavaScript appears only where a general coroutine sits underneath (Lua, Ruby Fibers, Rust's unstable `Coroutine`, custom C++ promise types) or where Python was copied by citation (PHP, and Hack after it). Every design that calls itself a generator or sequence builder after 2005 (F#, Dart, Kotlin, C++23, Rust `gen`) left send out.
- Exception injection (`throw`) is the rarest feature: PHP (5.5) is the only verified case in this set.
- Stated influence lines, each backed by a quote above: Python (PEPs 255/289/342/380/3152) to PHP; Python 3.3 and ES6 to PHP 7; C# and Python to C++ (N3858), PEP 289 to C++ (N4134); C#, Python, JS, Go, Haskell to Kotlin (KEEP); C#, JS, Python to Rust async (RFC 2033) and a 15-language survey for Rust `gen` (RFC 3513); Haskell, OCaml, Scala, C# 2.0 iterators to F#, and F# to C# 5.0 (Syme); Scheme, and Ulrich's patch, to Lua; CLU to Ruby (weakly sourced) and to Go (stated).
