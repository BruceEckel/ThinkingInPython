## 1. PEP 234 and PEP 255 (Python 2.2): Icon, CLU, Sather, Stackless; why `yield`, why `def`, why no `return expr`; PEP 219/220

### Takeaway
PEP 255 names three language precedents in one sentence (Sather iterators, "inspired by iterators in CLU", and Icon generators) and positions itself as "a useful subset of Stackless functionality" that fits CPython and Jython. The design choices (`yield` keyword, `def` reused, bare `return` only) are argued in the PEP's Q&A and a BDFL pronouncement, with Icon cited as the language where `return expr` does carry a final value.

### Cited Findings
- PEP 234 "Iterators": authors Ka-Ping Yee and Guido van Rossum, created 30-Jan-2001, header `Python-Version: 2.1`, Post-History 30-Apr-2001. It defines `StopIteration`: "A new exception is defined, `StopIteration`, which can be used to signal the end of an iteration." The PEP text names no other language as a source (it mentions only C, as implementation language). [PEP 234](https://peps.python.org/pep-0234/)
- What's New in Python 2.2 lists PEP 234 as new in 2.2: "Written by Ka-Ping Yee and GvR; implemented by the Python Labs crew, mostly by GvR and Tim Peters." Python 2.2 was "originally released on December 21, 2001". [What's New in Python 2.2](https://docs.python.org/3/whatsnew/2.2.html)
- PEP 234 on the exception design: "It has been questioned whether an exception to signal the end of the iteration isn't too expensive." and on naming: "it might have been better to go for `__next__()` and have a new built-in, `next(it)`" (the choice Python 3 later made). [PEP 234](https://peps.python.org/pep-0234/)
- PEP 255 "Simple Generators": authors Neil Schemenauer, Tim Peters, Magnus Lie Hetland; created 18-May-2001; `Python-Version: 2.2`; Post-History 14-Jun-2001, 23-Jun-2001; `Requires: 234`. (PEP source) [PEP 255](https://peps.python.org/pep-0255/)
- The crediting sentence, exact: "Some other high-level languages provide pleasant solutions, notably iterators in Sather [2]_, which were inspired by iterators in CLU; and generators in Icon [3]_, a novel language where every expression *is a generator*." It continues: "There are differences among these, but the basic idea is the same:  provide a kind of function that can return an intermediate result ("the next value") to its caller, but maintaining the function's local state so that the function can be resumed again right where it left off." (PEP source) [PEP 255](https://peps.python.org/pep-0255/)
- PEP 255's references are: [1] stackless.com, [2] "Iteration Abstraction in Sather," Murer, Omohundro, Stoutamire and Szyperski, [3] the Icon site at cs.arizona.edu. CLU gets no reference of its own; it appears only through Sather. [PEP 255](https://peps.python.org/pep-0255/)
- On Stackless, exact: "A final option is to use the Stackless [1]_ (:pep:`219`) variant implementation of Python instead, which supports lightweight coroutines." "However, Stackless is a controversial rethinking of the Python core, and it may not be possible for Jython to implement the same semantics." "generators provide a useful subset of Stackless functionality in a way that fits easily into the current CPython implementation". (PEP source) [PEP 255](https://peps.python.org/pep-0255/)
- The other alternatives PEP 255 lists before the language precedents: a callback argument (`tokenize.py`'s *tokeneater*), materializing a whole list, a hand-written PEP 234 iterator, and producer and consumer in separate threads (`Demo/threads/Generator.py`). (PEP source) [PEP 255](https://peps.python.org/pep-0255/)
- Why a keyword: "Control flow is much better expressed via keyword in Python, and yield is a control construct.  It's also believed that efficient implementation in Jython requires that the compiler be able to determine potential suspension points at compile-time, and a new keyword makes that easy." Rollout was through `from __future__ import generators` in 2.2. (PEP source) [PEP 255](https://peps.python.org/pep-0255/)
- Rejected spellings listed in the PEP: `return 3 and continue`, `return and continue 3`, `return generating 3`, `continue return 3`, `return >> , 3`, `from generator return 3`, `return >> 3`, `return << 3`, `>> 3`, `<< 3`, `* 3`. The answer: "nicer to make ``yield`` very clear -- I don't want to have to *deduce* that a yield is occurring". (PEP source) [PEP 255](https://peps.python.org/pep-0255/)
- Why reuse `def` (BDFL pronouncement on a proposed `gen` or `generator` keyword): "``def`` it stays.  No argument on either side is totally convincing, so I have consulted my language designer's intuition." The Con argument recorded: "generators *are* functions, but with the twist that they're resumable." The Pro argument recorded: generator functions are "factory functions that produce generator-iterators as if by magic". (PEP source) [PEP 255](https://peps.python.org/pep-0255/)
- Why no value on `return`, exact: "Perhaps we will someday.  In Icon, ``return expr`` means both "I'm done", and "but I have one final useful value to return too, and this is it".  At the start, and in the absence of compelling uses for ``return expr``, it's simply cleaner to use ``yield`` exclusively for delivering values." (PEP source) [PEP 255](https://peps.python.org/pep-0255/)
- Why `return` at all: "``return`` means "I'm done" in any kind of function, and that's easy to explain and to use." (PEP source) [PEP 255](https://peps.python.org/pep-0255/)
- Original restriction: "``yield`` is not allowed in the ``try`` clause of a ``try/finally`` construct.  A consequence is that generators should allocate critical resources with great care." The fetch summary gives the reason as "there's no guarantee the generator will ever be resumed." [PEP 255](https://peps.python.org/pep-0255/)
- What's New in Python 2.2 (A.M. Kuchling) credits Icon more strongly than the PEP does: "The idea of generators comes from other programming languages, especially Icon ... where the idea of generators is central." and "Python doesn't go nearly as far as Icon in adopting generators as a central concept." It also states a difference: "One novel feature of Python's interface as compared to Icon's is that a generator's state is represented as a concrete object (the iterator) that can be passed around to other functions or stored in a data structure." It does not mention CLU, Sather, or Stackless. Credit line: "Written by Neil Schemenauer, Tim Peters, Magnus Lie Hetland. Implemented mostly by Neil Schemenauer and Tim Peters". [What's New in Python 2.2](https://docs.python.org/3/whatsnew/2.2.html)
- PEP 219 "Stackless Python": Gordon McMillan, created 14-Aug-2000, status Deferred, header `Python-Version: 2.1`. "This PEP discusses changes required to core Python in order to efficiently support generators, microthreads and coroutines." "While these PEPs are based on Christian Tismer's Stackless [1] implementation, they do not regard Stackless as a reference implementation." "Stackless (with an extension module) implements continuations, and from continuations one can implement coroutines, microthreads (as has been done by Will Ware [2]) and generators." [PEP 219](https://peps.python.org/pep-0219/)
- PEP 219 on demand for continuations: "But in more than a year, no one has found any other productive use of continuations, so there seems to be no demand for their support." And on generators: "(Generators can be done on a single stack, but they can also be regarded as a very simple case of coroutines.)" [PEP 219](https://peps.python.org/pep-0219/)
- PEP 219 records earlier pure-Python work: "Tim Peters has done pure Python implementations of generators [3] and coroutines [4] using threads", with [3] being `Demo/threads/Generator.py`, the same file PEP 255 cites. [PEP 219](https://peps.python.org/pep-0219/)
- PEP 220 "Coroutines, Generators, Continuations": Gordon McMillan, created 14-Aug-2000, status Rejected, type Informational. It is an abstract only: "A low-level continuations module exists.  With it, coroutines and generators and "green" threads can be written.  A higher level module that makes coroutines and generators easy to create is desirable (and being worked on)." (PEP source) [PEP 220](https://peps.python.org/pep-0220/)

### Inferences
- PEP 255 credits a design idea (resumable function with preserved locals), not a syntax. Sather and Icon are the two cited by reference; CLU is cited second-hand as Sather's inspiration.
- The "simple" in the title is defined against Stackless: generators need only one frame kept alive, which PEP 219 itself notes "can be done on a single stack".
- The Icon `return expr` remark in 2001 anticipates PEP 380's generator return value (2009), which was justified on different grounds (refactoring and lightweight threads).
- Jython's implementability is a stated design constraint twice (keyword choice, and the case against Stackless).

### Gaps
- I did not read the June 2001 python-dev / python-iterators threads themselves (the lists are at lists.sourceforge.net/lists/listinfo/python-iterators per PEP 234), so who first proposed `yield` as the word, and whether it was taken from CLU/Sather/Icon vocabulary, is not confirmed in a primary source. From memory: CLU and Sather use `yield`, Icon uses `suspend`; that is not stated in PEP 255.
- PEP 234's header says `Python-Version: 2.1` although iterators shipped in 2.2 per What's New 2.2. I report both without resolving it.
- PEP 220 has no body beyond the abstract and no recorded rejection rationale or date.
- Guido van Rossum's "The History of Python" blog was not consulted; no claim here rests on it.

## 2. PEP 289 generator expressions (Python 2.4)

### Takeaway
PEP 289 credits no other language. It presents generator expressions as a "generalization of list comprehensions", and the Haskell credit exists only one step back, in What's New in Python 2.0's note on list comprehensions.

### Cited Findings
- PEP 289: author Raymond Hettinger, created 30-Jan-2002, `Python-Version: 2.4`, Post-History 22-Oct-2003. Abstract: "This PEP introduces generator expressions as a high performance, memory efficient generalization of list comprehensions" and generators. "This PEP is ACCEPTED for Py2.4." (PEP source) [PEP 289](https://peps.python.org/pep-0289/)
- The PEP text contains no mention of Haskell or any other language (checked by search of the PEP source for "haskell", "SETL", "other lang"). [PEP 289](https://peps.python.org/pep-0289/)
- Acknowledgements, exact: "Raymond Hettinger first proposed the idea of "generator comprehensions" in January 2002." "Peter Norvig resurrected the discussion in his proposal for Accumulation Displays." "Alex Martelli provided critical measurements that proved the performance benefits of generator expressions." "Phillip Eby suggested "iterator expressions" as the name." "Subsequently, Tim Peters suggested the name "generator expressions"." "Jiwon Seo single-handedly implemented various versions of the proposal including the final version loaded into CVS." "Guido van Rossum made the key design decisions after comments from Armin Rigo and newsgroup discussions." [PEP 289](https://peps.python.org/pep-0289/)
- Binding decision: "the first (outermost) for-expression should be evaluated immediately", the rest when the generator runs; and "Python takes a late binding approach to lambda expressions and has no precedent for automatic, early binding." The PEP's reference [1] is the python-dev April 2004 thread on early versus late binding. [PEP 289](https://peps.python.org/pep-0289/); [python-dev April 2004](https://mail.python.org/pipermail/python-dev/2004-April/044555.html)
- What's New in Python 2.4: "Proposed by Raymond Hettinger and implemented by Jiwon Seo with early efforts steered by Hye-Shik Chang." [What's New in Python 2.4](https://docs.python.org/3/whatsnew/2.4.html)
- PEP 202 "List Comprehensions": Barry Warsaw, created 13-Jul-2000, `Python-Version: 2.0`. The PEP text itself names no source language. (PEP source) [PEP 202](https://peps.python.org/pep-0202/)
- The Haskell credit, exact: "The idea of list comprehensions originally comes from the functional programming language Haskell (https://www.haskell.org). Greg Ewing argued most effectively for adding them to Python and wrote the initial list comprehension patch, which was then discussed for a seemingly endless time on the python-dev mailing list and kept up-to-date by Skip Montanaro." [What's New in Python 2.0](https://docs.python.org/3/whatsnew/2.0.html)

### Inferences
- The lineage Python documents is Haskell list comprehension (via What's New 2.0) to Python list comprehension (2.0) to generator expression (2.4). PEP 289 treats the lazy form as a Python-internal combination of two existing Python features.
- Greg Ewing wrote the first list-comprehension patch (2000) and later PEP 380 (2009), so one person is on both ends of this history.

### Gaps
- The task brief says PEP 289 was rejected and later revived. The current PEP text shows only "ACCEPTED"; the Acknowledgements imply a dormant period between January 2002 and Norvig's "Accumulation Displays" proposal (Post-History 22-Oct-2003), but I found no primary text recording a rejection. From memory, an earlier revision carried a rejection notice; unconfirmed.
- No Python primary source I read names an earlier language with lazy comprehensions as precedent for generator expressions (Haskell's lists are lazy, but no Python source makes that argument).
- The Python 2.4.0 release date (30 November 2004, from memory) was not confirmed; What's New 2.4 gives only the 2.4.1 date, "March 30, 2005".

## 3. PEP 288, PEP 325, PEP 340, PEP 343, and PEP 342 (Python 2.5): `send()`, `throw()`, `close()`, `GeneratorExit`, yield expression

### Takeaway
PEP 342 states its own sources: it is "basically a combination of ideas from" PEP 288 (Hettinger: `throw()` and the yield expression) and PEP 325 (Pedroni: `close()` and finalization), assembled during the PEP 340/343 `with`-statement work in spring 2005. The only other language it names is Ruby ("This is intentional"), and the only other system is Stackless Python; it does not mention Icon, Lua, or Sather.

### Cited Findings
- PEP 288 "Generators Attributes and Exceptions": Raymond Hettinger, created 21-Mar-2002, header `Python-Version: 2.5`, status Withdrawn (not Rejected). "This PEP proposes to enhance generators by providing mechanisms for raising exceptions and sharing data with running generators." Status note: "This PEP is withdrawn.  The exception raising mechanism was extended and subsumed into :pep:`343`.  The attribute passing capability never built a following, did not have a clear implementation, and did not have a clean way for the running generator to access its own namespace." (PEP source) [PEP 288](https://peps.python.org/pep-0288/)
- PEP 288's motivation ties exceptions to cleanup: "generator exception passing helps mitigate the try/finally prohibition for generators.  The need is especially acute for generators needing to flush buffers or close resources upon termination." (PEP source) [PEP 288](https://peps.python.org/pep-0288/)
- PEP 325 "Resource-Release Support for Generators": Samuele Pedroni, created 25-Aug-2003, header `Python-Version: 2.4`, status Rejected. "This PEP proposes that the built-in generator type implement a close method and destruction semantics, such that the restriction on yield placement can be lifted". Pronouncement: "Rejected in favor of :pep:`342` which includes substantially all of the requested behavior in a more refined form." (PEP source) [PEP 325](https://peps.python.org/pep-0325/)
- PEP 325 compares generators with Smalltalk-style blocks: "they match in power and offer some advantages over the approach using iterator methods taking a (smalltalkish) block." (PEP source) [PEP 325](https://peps.python.org/pep-0325/)
- PEP 340 "Anonymous Block Statements": Guido van Rossum, created 27-Apr-2005, Rejected. "This PEP competes with several other PEPs: :pep:`288` (Generators Attributes and Exceptions; only the second part), :pep:`310` (Reliable Acquisition/Release Pairs), and :pep:`325`". "I am rejecting this PEP in favor of :pep:`343`." It contrasts generator-based blocks with thunks and notes Ruby: "You can't use a yield-based block for that (except in Ruby, which uses yield syntax with a thunk-based implementation)." (PEP source) [PEP 340](https://peps.python.org/pep-0340/)
- PEP 342 "Coroutines via Enhanced Generators": Guido van Rossum and Phillip J. Eby, created 10-May-2005, `Python-Version: 2.5`. (PEP source) [PEP 342](https://peps.python.org/pep-0342/)
- The crediting passage, exact: "It is basically a combination of ideas from these two PEPs ... :pep:`288`, Generators Attributes and Exceptions.  The current PEP covers its second half, generator exceptions (in fact the ``throw()`` method name was taken from :pep:`288`).  :pep:`342` replaces generator attributes, however, with a concept from an earlier revision of :pep:`288`, the *yield expression*." and ":pep:`325`, Resource-Release Support for Generators.  :pep:`342` ties up a few loose ends in the :pep:`325` spec, to make it suitable for actual implementation." (PEP source) [PEP 342](https://peps.python.org/pep-0342/)
- Acknowledgements, exact: "Raymond Hettinger (:pep:`288`) and Samuele Pedroni (:pep:`325`) first formally proposed the ideas of communicating values or exceptions into generators, and the ability to close generators." Then "See also the Acknowledgements section of PEP 340." The References section reads "TBD." [PEP 342](https://peps.python.org/pep-0342/)
- Motivation, exact: "Python's generator functions are almost coroutines -- but not quite -- in that they allow pausing execution to produce a value, but do not provide for values or exceptions to be passed in when execution resumes." And: "a simple co-routine scheduler or *trampoline function* would let coroutines *call* each other without blocking". (PEP source) [PEP 342](https://peps.python.org/pep-0342/)
- Stackless credit, exact: "these enhancements will give standard Python many of the benefits of the Stackless Python fork, without requiring any significant modification to the CPython core or its APIs.  In addition, these enhancements should be readily implementable by any Python implementation (such as Jython) that already supports generators." (PEP source) [PEP 342](https://peps.python.org/pep-0342/)
- Ruby note, exact: "Note: the syntactic extensions to yield make its use very similar to that in Ruby.  This is intentional.  Do note that in Python the block passes a value to the generator using ``send(EXPR)`` rather than ``return EXPR``, and the underlying mechanism whereby control is passed between the generator and the block is completely different.  Blocks in Python are not compiled into thunks; rather, ``yield`` suspends execution of the generator's frame." It ends with an unresolved editorial aside: "(XXX - this stuff about blocks seems out of place now, perhaps Guido can edit to clarify.)" (PEP source) [PEP 342](https://peps.python.org/pep-0342/)
- The six changes in the Specification Summary: (1) "Redefine ``yield`` to be an expression, rather than a statement." (2) `send()`, which "*sends* a value that becomes the result of the current yield-expression". (3) `throw()`, "which raises an exception at the point where the generator was paused". (4) `close()`, "which raises ``GeneratorExit`` at the point where the generator was paused"; "If the generator yields a value, a ``RuntimeError`` is raised." (5) `close()` on garbage collection. (6) "Allow ``yield`` to be used in ``try/finally`` blocks". (PEP source) [PEP 342](https://peps.python.org/pep-0342/)
- PEP 342 on the yield expression: "In effect, a yield-expression is like an inverted function call". `GeneratorExit` was specified as "inheriting from Exception" in the PEP. (PEP source) [PEP 342](https://peps.python.org/pep-0342/)
- Rejected or withdrawn within PEP 342: "An earlier draft of this PEP proposed a new ``continue EXPR`` syntax for use in for-loops (carried over from :pep:`340`) ... This feature has been withdrawn for the time being". Also: "Oren Tirosh has proposed renaming the send() method to feed(), for compatibility with the consumer interface", and for `throw()`: "Alternative method names were considered: resolve(), signal(), genraise(), raiseinto(), and flush()." [PEP 342](https://peps.python.org/pep-0342/)
- Existing users named as motivation: GTasklet and `peak.events` "already implement similar scheduling capabilities, but must currently use awkward workarounds"; example 3 is "A simple co-routine scheduler or trampoline", and one example "emulates simple tasklets as are used in Stackless Python". [PEP 342](https://peps.python.org/pep-0342/)
- How PEP 343 drove it: PEP 343 says "After a lot of discussion about :pep:`340` and alternatives, I decided to withdraw :pep:`340`", "Inspired by a counter-proposal to :pep:`340` by Phillip Eby I tried" a generator-decorator form, and "With :pep:`342` accepted, it is possible to write a decorator" (`contextmanager`, first called `with_template`). "The generator based examples rely on :pep:`342`." Its reference [2] is titled "Guido suggests some generator changes that ended up in PEP 342". PEP 343 "was first accepted by Guido at his EuroPython keynote, 27 June 2005." (PEP source) [PEP 343](https://peps.python.org/pep-0343/)
- The two PEPs were co-designed down to the exception type: PEP 342 open issue 1 says "the ``with_template`` decorator class in :pep:`343` uses ``RuntimeError`` for similar offenses ... So now I believe they should both raise ``RuntimeError``", the same wording as Guido's post of 2 June 2005, "PEP 343 rewrite complete". [PEP 342](https://peps.python.org/pep-0342/); [python-dev 2005-June/054064](https://mail.python.org/pipermail/python-dev/2005-June/054064.html)
- What's New in Python 2.5: "PEP written by Guido van Rossum and Phillip J. Eby; implemented by Phillip J. Eby." "Earlier versions of these features were proposed in PEP 288 by Raymond Hettinger and PEP 325 by Samuele Pedroni." "Generators also become *coroutines*, a more generalized form of subroutines." And the PEP 343 link: "using generators and `try...finally` is actually necessary in order to implement the `with` statement described by PEP 343." PEP 343 itself: "PEP written by Guido van Rossum and Nick Coghlan; implemented by Mike Bland, Guido van Rossum, and Neal Norwitz." [What's New in Python 2.5](https://docs.python.org/3/whatsnew/2.5.html)

### Inferences
- Each PEP 342 method has a named Python-internal origin: `throw()` (name and idea) from PEP 288, the yield expression from "an earlier revision of PEP 288", `close()` and finalize-on-collection from PEP 325, `send()` named in PEP 342 itself (with `feed()` rejected), `GeneratorExit` new in PEP 342.
- There is a small inconsistency between the PEPs: PEP 288's status note says its exception mechanism was "subsumed into PEP 343", while PEP 342 says it took `throw()` from PEP 288. PEP 342 is where `throw()` is specified.
- `close()` and `throw()` exist mainly to make `@contextmanager` and `yield` inside `try/finally` sound; `send()` and the coroutine framing are Eby's trampoline use case. The `with` statement is the proximate cause of the 2005 timing.
- The Ruby resemblance is a leftover from PEP 340's block-statement design, as the PEP's own XXX note admits; it is a credit for the look of `yield` as an expression in a block protocol, not for coroutines.

### Gaps
- PEP 342 does not mention Icon co-expressions, Lua coroutines, or Sather; I found no primary Python source from 2005 crediting them. The python-dev threads of May-June 2005 were not read beyond the one post above.
- PEP 342's acceptance date is not in the PEP (Post-History is blank). Python 2.5's release date (19 September 2006, from memory) was not confirmed in a fetched source.
- The "earlier revision of PEP 288" containing the yield expression was not located.
- `GeneratorExit` was later moved to inherit from `BaseException` (Python 2.6, from memory); not confirmed here.
- What's New 2.5 "See also" cites a coroutine explanation "from a Perl point of view, written by Dan Sugalski"; I did not read it.

## 4. PEP 380 `yield from` (Python 3.3), generator `return value`, `StopIteration.value`, and PEP 3152

### Takeaway
Greg Ewing's motivation was refactoring: a generator "can only yield to its immediate caller", so code with a `yield` cannot be factored out once `send()`, `throw()`, and `close()` must be forwarded. Neither PEP 380, its first python-ideas draft, nor Guido's acceptance message cites another language; the only precedents named are earlier Python proposals using `yield *`.

### Cited Findings
- PEP 380 "Syntax for Delegating to a Subgenerator": Gregory Ewing, created 13-Feb-2009, `Python-Version: 3.3`. "Guido officially accepted the PEP on 26th June, 2011." [PEP 380](https://peps.python.org/pep-0380/)
- The first public draft is Ewing's python-ideas post of 13 Feb 2009, subject "Proto-PEP on a 'yield from' statement". It already contains the motivation sentence "A Python generator is a form of coroutine, but has the limitation that it can only yield to its immediate caller.", the generator return value ("generators will be allowed to execute a return statement with a value"), and the `yield *` remark. It names no other language. [python-ideas 2009-February/002883](https://mail.python.org/pipermail/python-ideas/2009-February/002883.html)
- The draft went through numbered revisions on python-ideas in February 2009 ("Revised^4", "Revised**6") and on python-dev in March 2009 ("Revised**8 PEP on Yield-From"). [python-ideas Revised^4](https://www.python.org/pipermail/python-ideas/2009-February/003033.html); [python-dev Revised**8](https://www.python.org/pipermail/python-dev/2009-March/087678.html)
- Motivation, exact: "This means that a piece of code containing a `yield` cannot be factored out and put into a separate function" in the way other code can. The PEP has a section named "The Refactoring Principle". [PEP 380](https://peps.python.org/pep-0380/)
- On the return value: "A motivation for generators being able to return values concerns the use of generators to implement lightweight threads." "The `yield from` expression allows the logic of the thread to be spread over as many functions as desired". Mechanism: "`return expr` in a generator causes `StopIteration(expr)` to be raised upon exit from the generator." and "the `StopIteration` exception will be given a `value` attribute that holds its first argument". [PEP 380](https://peps.python.org/pep-0380/)
- Alternative Proposals, exact: "Proposals along similar lines have been made before, some using the syntax `yield *` instead of `yield from`. While `yield *` is more concise, it could be argued that it looks too similar to an ordinary `yield` and the difference might be overlooked when reading code." "To the author's knowledge, previous proposals have focused only on yielding values, and thereby suffered from the criticism that the two-line for-loop they replace is not sufficiently tiresome to write to justify a new syntax. By dealing with the full generator protocol, this proposal provides considerably more benefit." [PEP 380](https://peps.python.org/pep-0380/)
- Criticisms recorded in the PEP: the value of `yield from` is derived differently from `yield`'s, which "suggests that some other syntax not containing the word `yield` might be more appropriate, but no acceptable alternative has so far been proposed. Rejected alternatives include `call`, `delegate` and `gcall`."; using an exception for the return value "has been criticised as an "abuse of exceptions""; "It has been suggested that a different exception, such as GeneratorReturn, should be used instead of StopIteration". [PEP 380](https://peps.python.org/pep-0380/)
- Rejected ideas: a way to skip the initial `__next__()` call (primed generators): "Outside the scope of the proposal."; `close()` returning the `StopIteration` value: "This usage of close() and GeneratorExit would be incompatible with their current role as a bail-out and clean-up mechanism."; raising an exception when a return value is ignored: "Ignoring a return value is not considered an error anywhere else in Python." [PEP 380](https://peps.python.org/pep-0380/)
- March 2009 python-dev debate (thread "PEP 380 (yield from a subgenerator) comments"): P.J. Eby objected to the return value and pointed at frameworks that spell it "yield Return(value)". Ewing replied "the need for such an unusual construct when using these frameworks is a wart, not a feature", "suspendable functions should have the same rights and privileges as ordinary ones", and "I'd be disappointed to lose that part of the proposal." [python-dev 2009-March/087583](https://mail.python.org/pipermail/python-dev/2009-March/087583.html)
- Other objections found in the February 2009 python-ideas threads (search-result summaries, not read in full): Bruce Frederiksen objected to reusing `return` for the final value; Antoine Pitrou argued the return mechanism alone would do. [python-ideas thread](https://mail.python.org/archives/list/python-ideas@python.org/thread/QYKLE5SBGTV2ZEA3LD3GL7GOXMUL57DL)
- Acceptance: Guido van Rossum, python-dev, Sat 25 Jun 2011, thread "EuroPython Language Summit report": "Let me cut this short. PEP 380 is pretty much approved." "We are waiting for an implementation in Python 3.3." [python-dev 2011-June/112010](https://mail.python.org/pipermail/python-dev/2011-June/112010.html)
- Shipping: "Python 3.3 was released on September 29, 2012." "PEP written by Greg Ewing; implementation by Greg Ewing, integrated into 3.3 by Renaud Blanch, Ryan Kelly and Nick Coghlan". "For simple iterators, `yield from iterable` is essentially just a shortened form of `for item in iterable: yield item`", but "unlike an ordinary loop, `yield from` allows subgenerators to receive sent and thrown values directly from the calling scope, and return a final value to the outer generator". [What's New in Python 3.3](https://docs.python.org/3/whatsnew/3.3.html)
- Ewing's own page describes two proposals with prototypes: Yield From, "A mechanism for one generator to delegate to another.", and Cofunctions, "A new type of function for writing generator-based coroutines." It names no other language. [Greg Ewing, yield-from](https://www.csse.canterbury.ac.nz/greg.ewing/python/yield-from/)
- PEP 3152 "Cofunctions": Gregory Ewing, header created 13-Feb-2009, `Python-Version: 3.3`, Rejected. "A new keyword ``codef`` is introduced which is used in place of ``def`` to define a cofunction." "``cocall f(*args, **kwds)`` is semantically equivalent to ``yield from f.__cocall__(*args, **kwds)``". "This proposal builds on the 'yield from' mechanism described in PEP 380". (PEP source) [PEP 3152](https://peps.python.org/pep-3152/)
- PEP 3152's rejection: Guido van Rossum, python-dev, 24 Apr 2015, "PEP 492 vs. PEP 3152, new round": "I just can't get used to this aspect of PEP 3152, so I'm rejecting it." "We must see `await` as a refinement of `yield from`, not as an alternative." [python-dev 2015-April/139503](https://mail.python.org/pipermail/python-dev/2015-April/139503.html)

### Inferences
- `yield from` has no cited foreign precedent in the primary sources read. Its stated ancestry is Python-internal: earlier `yield *` proposals for flattening, PEP 342's trampoline pattern, and framework conventions such as `yield Return(value)`.
- PEP 255 in 2001 already mentioned Icon's `return expr` and deferred it "in the absence of compelling uses"; PEP 380 supplied the use (lightweight threads returning results) without citing Icon.
- The naming choice (`yield from` over `yield *`) was made on readability; JavaScript later chose `yield*` (see section 7 gaps).
- The PEP gives 26 June 2011 as the acceptance date, while the linked message is dated 25 June 2011 (CEST). Treat the acceptance as 25-26 June 2011.

### Gaps
- I did not find a 2009 post by Guido on python-ideas responding to the proto-PEP; his position in 2009 is not documented here. The delay from 2009 to 2011 (from memory: the Python 3 language moratorium, PEP 3003) is not confirmed in a source read here.
- The earlier `yield *` proposals PEP 380 alludes to are not identified by date or author in the PEP, and I did not locate them.
- PEP 3152's header gives the same created date as PEP 380 (13-Feb-2009); from memory the cofunctions PEP was posted in 2010. Not resolved.
- Ewing's `yield_from.html` sub-page and his `yield from` tutorials (cited by PEP 3156) were not read.

## 5. PEP 479, PEP 492, PEP 525, PEP 530, PEP 533: what later PEPs cite

### Takeaway
PEP 492 is the first generator-lineage PEP that credits other languages for the design as a group: "async/await is not a new concept in programming languages", listing C#, ECMAScript 7, Hack/HHVM, Dart, Scala, and a C++ proposal. PEPs 479, 525, 530, and 533 cite no other language; they cite earlier Python PEPs.

### Cited Findings
- PEP 479 "Change StopIteration handling inside generators": Chris Angelico and Guido van Rossum, created 15-Nov-2014, `Python-Version: 3.5`. "when ``StopIteration`` is raised inside a generator, it is replaced with ``RuntimeError``." "This PEP was accepted by the BDFL on November 22." Transition plan: "Python 3.5: Enable new semantics under ``__future__`` import" (`from __future__ import generator_stop`), "Python 3.6: Non-silent deprecation warning.", "Python 3.7: Enable new semantics everywhere." (PEP source) [PEP 479](https://peps.python.org/pep-0479/)
- PEP 479's rationale points at PEP 380 and `contextlib`: the old behavior is a problem for "the ``yield from`` construct of :pep:`380`, as it breaks the abstraction", and its lead example is a `@contextlib.contextmanager` generator. An alternative considered and rejected was "Converting the exception inside next()". No other language is named (PEP source searched). [PEP 479](https://peps.python.org/pep-0479/)
- What's New in Python 3.5: "PEP written by Chris Angelico and Guido van Rossum. Implemented by Chris Angelico, Yury Selivanov and Nick Coghlan." [What's New in Python 3.5](https://docs.python.org/3/whatsnew/3.5.html)
- PEP 492 "Coroutines with async and await syntax": Yury Selivanov, created 09-Apr-2015, `Python-Version: 3.5`, Post-History 17-Apr through 05-May-2015; "PEP 492 was accepted by Guido, Tuesday, May 5, 2015". "Python 3.5 was released on September 13, 2015." "PEP written and implemented by Yury Selivanov." [PEP 492](https://peps.python.org/pep-0492/); [What's New in Python 3.5](https://docs.python.org/3/whatsnew/3.5.html)
- The language-credit passage, exact (section "Why "async" and "await" keywords"): "async/await is not a new concept in programming languages: * C# has it since long time ago [5]_; * proposal to add async/await in ECMAScript 7 [2]_; see also Traceur project [9]_; * Facebook's Hack/HHVM [6]_; * Google's Dart language [7]_; * Scala [8]_; * proposal to add async/await to C++ [10]_; * and many other less popular languages. This is a huge benefit, as some users already have experience with async/await, and because it makes working with many languages in one project easier (Python with ECMAScript 7 for instance)." (PEP source) [PEP 492](https://peps.python.org/pep-0492/)
- PEP 492's abstract makes the same point: the change keeps Python competitive "as many other languages have adopted, or are planning to adopt, similar features". [PEP 492](https://peps.python.org/pep-0492/)
- PEP 492's Python ancestry, exact: "This specification presumes knowledge of the implementation of coroutines in Python (:pep:`342` and :pep:`380`).  Motivation for the syntax changes proposed here comes from the asyncio framework (:pep:`3156`) and the "Cofunctions" proposal (:pep:`3152`, now rejected in favor of this specification)." (PEP source) [PEP 492](https://peps.python.org/pep-0492/)
- Bridge to generators: "A new function `coroutine(fn)` is added to the `types` module." It sets the `CO_ITERABLE_COROUTINE` flag so that generator-based coroutines can be awaited. "Plain generators cannot yield from native coroutines: doing so will result in a TypeError." "The behavior of existing generator-based coroutines in asyncio remains unchanged." [PEP 492](https://peps.python.org/pep-0492/)
- Keywords: `async` and `await` were soft in 3.5 and 3.6; "In 3.7 we will transform them to proper keywords." (PEP source) [PEP 492](https://peps.python.org/pep-0492/)
- Async generators were excluded in 3.5: "While it is possible to implement coroutine-generators, we believe that they are out of scope of this proposal." [PEP 492](https://peps.python.org/pep-0492/)
- PEP 525 "Asynchronous Generators": Yury Selivanov, created 28-Jul-2016, `Python-Version: 3.6`, "accepted by Guido, September 6, 2016". Rationale cites PEP 255: "Regular generators (introduced in :pep:`255`) enabled an elegant way of" writing iterators, and "Essentially, the goals and rationale for :pep:`255`, applied to the" asynchronous case. No other language is named. [PEP 525](https://peps.python.org/pep-0525/)
- PEP 525 API: "`agen.asend(val)`: Returns an *awaitable*, that pushes the `val` object in the `agen` generator." "`agen.athrow(typ, [val, [tb]])`: Returns an *awaitable*, that throws an exception into the `agen` generator." "`agen.aclose()`: Returns an *awaitable*, that throws a `GeneratorExit` exception into the generator." Finalization: "Add two new methods to the `sys` module: `set_asyncgen_hooks()` and `get_asyncgen_hooks()`." [PEP 525](https://peps.python.org/pep-0525/)
- PEP 525 dropped `yield from` for async generators: "it would require a serious redesign of the generators implementation." and "`yield from` is also less critical for asynchronous generators"; "to compose asynchronous generators a simple `async for` loop can be used". Performance claim: "asynchronous generators are **2x** faster than an equivalent implemented as an asynchronous iterator." (a second passage says "about **2.3x faster**"). [PEP 525](https://peps.python.org/pep-0525/)
- PEP 530 "Asynchronous Comprehensions": Yury Selivanov, created 03-Sep-2016, `Python-Version: 3.6`, "accepted by Guido, September 6, 2016". It "proposes to add asynchronous versions of list, set, dict comprehensions and generator expressions." No other language is named. (PEP source) [PEP 530](https://peps.python.org/pep-0530/)
- "Python 3.6 was released on December 23, 2016." PEP 525 and PEP 530 each: "PEP written and implemented by Yury Selivanov." What's New 3.6 states the lifted restriction: in 3.5 "it was not possible to use `await` and `yield` in the same function body." [What's New in Python 3.6](https://docs.python.org/3/whatsnew/3.6.html)
- PEP 533 "Deterministic cleanup for iterators": Nathaniel J. Smith, BDFL-Delegate Yury Selivanov, created 18-Oct-2016, status Deferred. "We propose to extend the iterator protocol with a new ``__(a)iterclose__`` slot, which is called automatically on exit from ``(async) for`` loops, regardless of how they exit." "This is especially valuable for asynchronous generators." It specifies "``__aiterclose__`` calls ``self.aclose()``". No other language is named in the passages searched. (PEP source) [PEP 533](https://peps.python.org/pep-0533/)

### Inferences
- The direction of credit reverses in 2015. Through PEP 380, Python PEPs cite research and niche languages (Icon, Sather/CLU, Ruby) or nothing. PEP 492 cites mainstream contemporaries, with C# first, and gives cross-language familiarity as a design benefit.
- `await` is defined by Guido as "a refinement of `yield from`" (section 4), and native coroutines kept the generator machinery (`send`, `throw`, `close`), so async/await in Python is syntactically borrowed and mechanically inherited from PEP 342 and PEP 380.
- PEP 479 is a repair to an interaction among PEP 234 (`StopIteration` as end signal), PEP 255, PEP 343's `contextmanager`, and PEP 380. It is purely internal history.
- PEP 533's problem (cleanup of a suspended generator nobody resumes) is the same problem PEP 255 named in 2001 as the reason for the `try/finally` restriction and PEP 325 attacked in 2003.

### Gaps
- Python 3.7's release date (27 June 2018, from memory) was not confirmed in a fetched source, nor was a What's New 3.7 statement that PEP 479 became the default and `async`/`await` became reserved; the PEPs state the plan, not the outcome.
- I did not read PEP 533 in full; "no other language" there rests on a keyword search (C#, JavaScript, Rust, RAII), not a full reading.
- PEP 492's language list gives URLs only; the PEP does not say which language's design was actually followed for `async for` and `async with` (from memory, these have no direct C# 5 counterpart). No primary statement found.
- The python-dev and python-ideas threads of April-May 2015 were not read beyond Guido's 24 April post.

## 6. Twisted, Tornado, and asyncio (PEP 3156) as users of generator coroutines

### Takeaway
Frameworks adopted each generator feature soon after it shipped: Twisted's `inlineCallbacks` required Python 2.5 (PEP 342), Tornado added `tornado.gen` in 2011, and Guido's asyncio was specified as "a higher-level scheduler based on `yield from` (PEP 380)". PEP 3156 credits Twisted, Tornado, and Greg Ewing's tutorial by name, and PEP 492 in turn cites asyncio as its motivation.

### Cited Findings
- Twisted: Itamar Shtull-Trauring's post of 16 Feb 2007, "inlineCallbacks: Twisted 2.5's generator-based Deferred microthreads-thingie", says it was "written by James Knight based on code by Chris Armstrong", "requires Python 2.5", and "Essentially this allows one to "wait" for a Deferred's result." Error handling: "just use try/except around the yield." Predecessor: "Previous versions of Twisted have deferredGenerator, but the syntax isn't as nice." [twisted-python 2007-February/014869](https://twisted.org/pipermail/twisted-python/2007-February/014869.html)
- Returning a value from an `inlineCallbacks` function required a helper, `returnValue()`, in the same module (2008 list reply; search-result summary). This is the "yield Return(value)"-style wart Ewing and Eby argued about in March 2009. [twisted-python 2008-January/049082](https://twisted.org/pipermail/twisted-python/2008-January/049082.html); [python-dev 2009-March/087583](https://mail.python.org/pipermail/python-dev/2009-March/087583.html)
- Before Twisted, PEP 342 itself named GTasklet and `peak.events` as libraries that "already implement similar scheduling capabilities, but must currently use awkward workarounds". [PEP 342](https://peps.python.org/pep-0342/)
- Tornado 2.1, released September 20, 2011, added `tornado.gen`: "A generator-based interface to simplify writing asynchronous functions." The release notes do not mention `inlineCallbacks`; the same release added a bridge between Tornado's event loop and Twisted's reactor. [Tornado 2.1 release notes](https://www.tornadoweb.org/en/stable/releases/v2.1.0.html)
- PEP 3156 "Asynchronous IO Support Rebooted: the "asyncio" Module": Guido van Rossum, BDFL-Delegate Antoine Pitrou, created 12-Dec-2012, Post-History 21-Dec-2012, header `Python-Version: 3.3`, replaces PEP 3153. Abstract: "The proposal includes a pluggable event loop, transport and protocol abstractions similar to those in Twisted, and a higher-level scheduler based on ``yield from`` (:pep:`380`)." (PEP source) [PEP 3156](https://peps.python.org/pep-3156/)
- PEP 3156 on coroutines: "Coroutines use the ``yield from`` syntax introduced in :pep:`380`, instead of the original ``yield`` syntax." On transports: "Transports and protocols are strongly influenced by Twisted and PEP 3153." (PEP source) [PEP 3156](https://peps.python.org/pep-3156/)
- PEP 3156 Acknowledgments, exact: "Apart from :pep:`3153`, influences include :pep:`380` and Greg Ewing's tutorial for ``yield from``, Twisted, Tornado, ZeroMQ, pyftpdlib, and wattle (Steve Dower's counter-proposal).  My previous work on asynchronous support in the NDB library for Google App Engine provided an important starting point." It also thanks "a Skype session with Steve Dower and Dino Viehland; email exchanges with and a visit by Ben Darnell" and "several Twisted developers, including Glyph, Brian Warner, David Reid, and Duncan McGreggor", and cites "numerous discussions on python-ideas from September through December 2012". (PEP source) [PEP 3156](https://peps.python.org/pep-3156/)
- Interoperability was a goal: it "should be easy for (Python 3.3 ports of) frameworks like Twisted, Tornado, or even gevents to either adapt the default event loop" or supply their own. (PEP source) [PEP 3156](https://peps.python.org/pep-3156/)
- PEP 492 closes the loop: "Motivation for the syntax changes proposed here comes from the asyncio framework (:pep:`3156`)", and it reports integration work with Tornado ("into the Tornado web server") and Cython. (PEP source) [PEP 492](https://peps.python.org/pep-0492/)

### Inferences
- The sequence is: PEP 342 (2005) enables `inlineCallbacks` (Twisted 2.5, 2007) and trampolines; their warts (`returnValue()`, manual forwarding) feed PEP 380 (2009-2011); PEP 380 enables asyncio (2012-2013); asyncio's confusion between generators and coroutines motivates PEP 492 (2015).
- Steve Dower and Dino Viehland (Microsoft, from memory) appear in PEP 3156's acknowledgments, a plausible but unstated path by which C#'s async/await experience reached Python before PEP 492. The PEP does not say this.

### Gaps
- asyncio's first release in the standard library (Python 3.4, March 2014, provisional; from memory) is not confirmed here; the PEP header says 3.3 because the package ("Tulip") targeted 3.3.
- I found no Twisted primary source that names PEP 342 or `send()` as the enabling feature; "requires Python 2.5" is the documented fact, and the link to PEP 342 is an inference.
- `deferredGenerator`'s introduction date and Twisted version (from memory: Twisted 2.0, 2005, on Python 2.2-2.4 plain generators) are unconfirmed.
- Whether Tornado's `gen` module was modeled on `inlineCallbacks` is not stated in the release notes read.
- The "wattle" counter-proposal by Steve Dower was not read.

## 7. Documented statements that another language copied Python (list for other researchers)

### Takeaway
The clearest primary statement is Brendan Eich's 2006 post on JavaScript 1.7, which says he was "infusing JS with Pythonic generators and iterators" and answers "Why borrow from Python" directly. PHP's 2012 generators RFC lists Python's PEPs first among its resources and compares its choices with Python point by point.

### Cited Findings
- JavaScript 1.7 (Mozilla, 2006): Brendan Eich, "Python and JavaScript", 19 February 2006: he has been "infusing JS with Pythonic generators and iterators, including array comprehensions." He asks "Why borrow from Python for iteration, generators, and comprehensions?" and quotes a wiki note: "Given the years of development in Python," ... "we would rather follow than lead." [Brendan Eich, 2006](https://brendaneich.com/2006/02/python-and-javascript/)
- JavaScript, secondary: a 2007 blog post says "JavaScript has borrowed some nice features of Python, namely generators and multiple-value returns." and notes the feature shipped in Firefox 2.0. [bluxte.net, 2007](https://www.bluxte.net/musings/2007/02/28/generators-javascript-17/). Jeremy Hylton (a Python core developer) also blogged on it in February 2006 (not read). [Jeremy Hylton, 2006](https://jeremyhylton.blogspot.com/2006/02/generators-in-javascript.html)
- PHP 5.5: Nikita Popov's generators RFC, dated 2012-06-05, status Implemented. On detecting generator functions by the presence of `yield`: "All existing generator implementations in other language (that I know of) also use automatic detection." "This includes Python, JavaScript 1.7 and C#." On priming: "This is required in Python and also the reason why coroutines in Python usually use some kind of decorator" that primes the coroutine. On syntax: "Python also has parentheses requirements for expression-use of `yield`." Its "Further resources" list begins with "Implementation in Python:" and links PEP 255, PEP 289, PEP 342, PEP 380, and PEP 3152, then JavaScript (Harmony, SpiderMonkey) and C#. [PHP RFC: Generators](https://wiki.php.net/rfc/generators)
- ECMAScript Harmony / ES6: the PHP RFC notes that Harmony departed from Python-style automatic detection: "The only exception to this is the generator support as defined by ECMAScript Harmony". Search-result summaries (not read in full) describe SpiderMonkey's older generators as "based on Python's design". [PHP RFC: Generators](https://wiki.php.net/rfc/generators); [esdiscuss, generator use-cases](https://esdiscuss.org/topic/generator-use-cases)
- Reverse direction, for contrast: Python's own PEP 492 says Python took `async`/`await` from others, "C# has it since long time ago", and PEP 342 says its `yield` extensions resemble Ruby's "intentionally". [PEP 492](https://peps.python.org/pep-0492/); [PEP 342](https://peps.python.org/pep-0342/)

### Inferences
- Two generations of borrowing are documented: Python 2.2/2.5 generators to JavaScript 1.7 (2006) and PHP 5.5 (2012), each with `send`-style two-way generators traceable to PEP 342; then C# async/await (2012) back into Python 3.5 (2015).
- The PHP RFC shows PEP 342's design visible abroad even in its rough edges: the priming requirement is cited as a Python property to avoid.

### Gaps
- The ES6 generators proposal page (wiki.ecmascript.org `harmony:generators`, Dave Herman) could not be fetched (archive blocked), so whether it credits Python, PEP 380, or `yield from` for `yield*` is unconfirmed. From memory it does cite Python; treat as unverified.
- The PHP RFC page did not state the shipping version in the text read (PHP 5.5, from memory); PHP 7's later `yield from` RFC was not read.
- Not checked for Python credit: C# 2.0 iterators (2005), Lua coroutines, Kotlin, Rust generators/coroutines RFCs, Dart `sync*`/`async*`, Swift, Julia, CoffeeScript. Other researchers cover these; none is asserted here.
- No Python primary source read here claims that another language copied Python's generators; all such statements above come from the borrowing side.
