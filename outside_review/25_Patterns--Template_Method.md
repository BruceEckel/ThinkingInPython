**1. The Anchored Algorithm (Decorator application caveat)**
* **Target Text:** 
```markdown
If you want the interpreter to refuse an override,
the [`__init_subclass__()` technique](17_Techniques--Metaprogramming.md#making-a-class-final)
also works with methods.
```
* **Issue:** The `__init_subclass__` technique reads the `__final__` attribute set by `typing.final` at runtime. However, if a reader applies `@final` to a `@classmethod`, `@staticmethod`, or `@property`, PEP 591 requires it to be the outermost decorator. Because those descriptor objects reject arbitrary attribute assignment, `typing.final` silently swallows an `AttributeError` and fails to set `__final__`, causing this runtime check to silently fail to protect the method. 
* **Instruction:** Add a caveat immediately after the target text: "(Be aware that this runtime check only works for regular methods. If you apply `@final` to a `@classmethod`, `@staticmethod`, or `@property`, PEP 591 requires it to be the outermost decorator; because those descriptor objects reject arbitrary attribute assignment, `typing.final` silently fails to set `__final__` on them.)"

**2. Don't Start the Engine in the Constructor (C++ vs Python dynamic dispatch)**
* **Target Text:**
```markdown
Calling `super().__init__()` first, in the usual style,
runs the engine on a half-initialized object:
```
* **Issue:** The book targets experienced programmers coming from languages like C++ and Java. C++ programmers might be surprised by this uninitialized-state trap because C++ explicitly prevents it: calling a virtual function from a base class constructor in C++ resolves to the base class's implementation, precisely to avoid dispatching to a subclass before it is constructed. Highlighting that Python behaves like Java here connects directly with the reader's prior knowledge.
* **Instruction:** Replace the target text with: "Calling `super().__init__()` first, in the usual style, runs the engine on a half-initialized object (C++ avoids this trap by dispatching to the base class's method during base construction, but Python behaves like Java and dispatches to the subclass's override, crashing on missing attributes):"

**3. Don't Start the Engine in the Constructor (Dataclass compatibility)**
* **Target Text:**
```markdown
The reliable repair changes the framework.
Separate construction from starting,
and have the client call `run()` explicitly on a fully built object.
```
* **Issue:** In modern Python, readers frequently reach for `@dataclass` to simplify subclasses like `Greeter`. However, the `__init__` generated by `@dataclass` does not call `super().__init__()`. If a framework relies on its constructor to start the engine, a dataclass subclass will silently bypass the engine start entirely. This gives a compelling, Python-specific reason why separating construction from `run()` is the robust design.
* **Instruction:** Append a sentence to the target text noting the dataclass interaction: "The reliable repair changes the framework. Separate construction from starting, and have the client call `run()` explicitly on a fully built object. (This separation also aligns with modern Python: if a subclass uses `@dataclass`, its generated constructor skips calling `super().__init__()`, which would silently fail to start a constructor-based engine.)"

## Verdicts

Applied in commit 19d48dbf, after each item was tested against the chapter and run under `uv run`.

1. Applied, with a different fix. The mechanism is half wrong: on 3.15.0rc2, `@final` over `@classmethod` and `@staticmethod` sets `__final__ = True` on the wrapper, and only `@property` comes out without it. But `near_miss.py`'s check accepted an override of all three, because `getattr(super(cls, cls), name)` returns a bound method, the bare function, or the property, none carrying the marker. The chapter now says "a second `@final` instance method" and adds two sentences naming the three cases and why the check misses them; the reviewer's PEP 591 parenthetical is not used.
2. Rejected. The chapter isn't wrong: `premature_engine.py` shows the `AttributeError` its marker prints, and chapter 25 makes no C++ or Java comparison anywhere. The parenthetical is added context, and its "behaves like Java" is loose (Java's fields are default-initialized, so the override reads `null` rather than failing on a missing attribute).
3. Rejected. The claim holds (a `@dataclass` subclass of a framework whose `__init__()` prints left the print unrun), but it describes a different failure, the engine never starting, and the chapter's listings define their own `__init__()` and use no data class. The section already makes its point that separating construction from `run()` is the reliable repair.
